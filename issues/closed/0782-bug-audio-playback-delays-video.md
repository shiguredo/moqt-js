# 音声を再生すると映像の表示が遅れるのを、音声と映像の遅延を別々に決めて修正する

- Created: 2026-10-01
- Completed: 2026-10-01
- Branch: feature/fix-av-sync-video-delay
- Polished: {YYYY-MM-DD}
- Reporter: @voluntas

## 目的

moqt-devtools で音声の再生を有効にすると映像の表示が遅れる (利用者の確認)。同じ経路・同じ
時間帯で 2 つの購読を比べると、映像の表示の遅延が 50 ms 前後増えていた。音声を再生しても
映像の表示が遅れないようにする。

## 現状

配備 relay、publisher と subscriber を同じ Chromium で動かし、subscriber を 2 つ繋いで
片方だけ音声を再生した実測 (2026-10-01、同じ経路・同じ時間帯。表示の遅延は中央値):

| 条件           | 音声 OFF | 音声 ON  | 差                |
| -------------- | -------- | -------- | ----------------- |
| 経路が良いとき | 101.1 ms | 101.3 ms | +0.2 ms (変更後)  |
| 経路が悪いとき | 62.4 ms  | 117.7 ms | +55.3 ms (変更前) |
| 経路が悪いとき | 68.1 ms  | 128.1 ms | +60.0 ms (変更後) |

- `src/playbackTimeline.ts` の `sharedDelayMs` は `max(音声の遅れ (下限 80 ms), 映像の遅れ)`
  を共有の再生遅延とし、`presentationDelayMsOf` が両方のトラックに同じ値を与えていた。
  同期は厳密になるが、音声の jitter buffer が大きいほど映像も遅れる
- 音声の遅れは経路の揺らぎから決まる量であるのに、固定の下限 80 ms と「2 つの大きい方」で
  決めていた。経路が悪いときは 80 ms でも足りず、目標を過ぎて届いた音を捨てて遅延を
  抑えていた (実測で 90 秒に 770 個 = 毎秒 8.5 個、17% の音が欠ける)
- 音の目標の間隔と長さが同じとき (Opus の 20 ms を 20 ms ごとに並べるとき)、浮動小数点の
  誤差で音が 1 つおきに捨てられる不具合もあった (別 issue)
- 遅延を抑えるために音を捨てるか、音を守るために映像を遅らせるかのどちらかしか選べず、
  どちらも利用者の不満になる

## 設計方針

### 映像と音声の遅延を別々に決める

- 表示の遅れをトラックごとに求める。共有しないのは、A/V 同期に必要なのが「2 つの表示時刻が
  揃うこと」であり「2 つの遅延が同じであること」ではないためである
- 音声は到着の遅れの分布から求める
  - 直近 2 秒の窓で最も早く届いた観測を基準にした相対遅延を求め、500 ms ごとの最大値だけを
    20 ms バケット (100 個) のヒストグラムへ入れる。ヒストグラムは忘れ係数 0.983 で古い
    観測を忘れ、最初の数回は重み 2 で速く収束させる
  - 目標は 0.95 分位のバケットから `(1 + バケット) × 20 ms` とする。これは「音が途切れる
    確率が 5% 未満になる遅延」である。観測が無い間は 80 ms から始める
  - 一定の遅れは揺らぎではないため目標を上げない (窓の中の最小の遅れを基準にするため)
- 映像は現行どおり、揺らぎの百分位から求める

### 2 つの遅延の差を相対制御で抑える

- ずれ (映像の遅延 - 音声の遅延 + 経路の相対遅延) が 30 ms 未満の間は遅延を変えない
- 超えたときだけ片側を 1 秒に 1 回、最大 80 ms 動かす。動かしたら平均を 0 に戻す (行き過ぎない)
- 動かすのは片側だけにする。余分な遅延がある側を先に削り、無ければもう片方を遅らせる
- 映像の遅延は `targetLatency` を下回らない
- 定数 (30 ms / 80 ms / 1 秒 / 平均 4 サンプル) と計算は libwebrtc の
  `video/stream_synchronization.cc` の `ComputeDelays` と同じにする。映像が音声より最大
  30 ms 先行できるのはこの不感帯のためであり、映像が音声の jitter buffer の遅延へ
  引きずられ続けることを防ぐ
- 2 つのトラックの基準の差が閾値を超えたとき (TIMESTAMP が壁時計からずれているとき) は
  同期しない。現行のフォールバックをそのまま残す

### 遅れて届いた音を捨てず、波形の周期で詰めて目標へ戻す

- 目標を過ぎて届いた音・前の音と重なる音は捨てない。今から鳴らせる最も早い時刻 (今 + 余裕、
  または前の音の終わり) へずらして鳴らす
- ずらした分は、波形の周期 (ピッチ) 1 つ分を削る時間圧縮で詰めて目標へ戻す。周期は音の
  第 1 チャンネルを 4 kHz へ間引いた自己相関から求め、切れ目の前後の相関が 0.9 より
  大きいときだけ操作する (波形が繰り返していない場所で切ると耳につくため)。詰められなかった
  分は遅れとして残り、次の音で持ち越す
- 1 つの音で詰める量は音の長さの半分までにする。詰められないまま目標から 500 ms 以上
  離れたら、一度捨てて目標へ戻す (経路の停止などから回復するため)
- 目標より先 (未来) に並びすぎた音は今までどおり捨てる
- ニーズ: 音を捨てると 20 ms の無音が混ざって聞こえる。時間圧縮は波形の繰り返しを 1 つ
  削るだけであり、聞こえにくい

### targetLatency と他の経路

- `targetLatency` (draft-ietf-moq-msf-01 §5.2.8) は `StreamSynchronization` の基準の遅延に
  渡し、2 つのトラックの表示の遅れの下限にする
- 音声だけを購読しているとき、壁時計の TIMESTAMP を持たない音は、現行どおり到着基準の
  並べ方にフォールバックする

## 完了条件

- 音声を再生したときの映像の表示の遅延が、経路が良いときに音声を再生しないときと同程度に
  なること (配備 relay で、同じ経路・同じ時間帯の 2 つの購読を比べて確かめる)
- 経路が悪いときに、音声の遅延が経路の揺らぎに応じて上がり、映像がその 30 ms 以内に
  収まること。音を捨てないこと (毎秒 8 個の欠落が 0 になること)
- 音声の目標遅延が到着の遅れの分布から決まること (一定の遅れでは上がらず、揺らぎが大きい
  ときだけ上がること)
- 遅れて届いた音が、目標へ戻ること (遅れが積み上がらないこと) をテストで固定する
- 2 つのトラックの基準の差が閾値を超えたときは同期せず、映像の表示時刻が未来へ伸びないこと
- `vp check` / `tsc --noEmit` / `vp test run` が通ること

## 解決方法

- `src/streamSynchronization.ts` (新規): 2 つのトラックの遅延を相対的に制御する。ずれは
  「映像の遅延 - 音声の遅延 + 経路の相対遅延」で求め、30 ms 未満の間は動かさず、超えたときだけ
  片側を 1 秒に 1 回 80 ms まで動かす (平均は 4 サンプル、動かしたら 0 に戻す)。定数と計算は
  libwebrtc の `video/stream_synchronization.cc` の `ComputeDelays` と同じにした
- `src/audioDelayManager.ts` (新規): 音声の jitter buffer の目標遅延を到着の遅れの分布から
  求める。直近 2 秒の窓で最も早く届いた観測を基準にした相対遅延を、500 ms ごとの最大値だけ
  20 ms バケット (100 個) のヒストグラムへ入れ、0.95 分位から `(1 + バケット) × 20 ms` を
  目標にする。忘れ係数 0.983、最初の数回は重み 2 で速く収束させ、観測が無い間は 80 ms にする
- `src/playbackTimeline.ts`: 表示の遅れをトラックごとに決めるようにした。音声は
  `AudioDelayManager`、映像は従来の百分位である。同期は `SYNC_INTERVAL_MS` (1 秒) ごとに
  両方のトラックへ新しい観測があるときだけ行う。`targetLatency` は `setTargetBufferingDelay`
  に渡して両方のトラックの遅れの下限にした。2 つのトラックの基準の差が閾値を超えたときは
  同期せず、大きい側の表示時刻を返さない (従来のフォールバックをそのまま残した)
- テスト: `src/playbackTimeline.test.ts` / `.prop.ts` を新しい規則に合わせ、不感帯・片側だけの
  変更・`targetLatency` の下限・一定の遅れでは目標が上がらないこと (到着の遅れの分布から
  決まること) を固定した。`src/playoutBuffer.test.ts` / `.prop.ts` と
  `src/createMediaSubscriber.test.ts` も新しい API に合わせた
- 実測 (配備 relay、購読を 2 つ繋いで片方だけ音声を再生し、同じ経路・同じ時間帯で比べた):
  経路が良いときは、音声を再生したときに増える映像の表示の遅延が 49.8 ms から 0.2 ms に
  なった。経路が悪いときは音声の遅延が到着の揺らぎに応じて上がり (約 120 ms)、映像はその
  30 ms 以内に収まる。これは表示時刻を揃えるために必要な遅れである (音を捨てれば映像を
  早くできるが、毎秒 8 個の音が欠ける)
- `vp check` と全 3525 テストが通った
