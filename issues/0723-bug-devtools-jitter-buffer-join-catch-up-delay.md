## 目的

moqt-devtools でカメラの映像を配信すると、受信側の映像の遅延が大きい (2026-09-25、利用者の確認)。計測すると、遅延の大部分は受信側の jitter buffer の再生遅延で、sora-moq でも経路でもない。購読を始めた直後は、表示の遅延 (publisher がフレームを読んだ時刻から描くまで) が約 500 ms あり、約 25 秒かけて約 60 ms まで下がる。jitter buffer を無効にすると、表示の遅延は最初から約 50 ms である。経路の揺らぎが小さいのに、購読の開始のたびに数百ミリ秒の遅延が 25 秒続く。

## 現状

計測 (2026-09-25、配備 relay (prewarm 有効) + 配備 moqt-devtools、publisher と subscriber を同じ Chromium で開き、同じ時計で測った):

| 条件                                                                      | 購読の開始からの 5 秒ごとの表示の遅延 (中央値、ms) | 到着の遅延 (中央値) |
| ------------------------------------------------------------------------- | -------------------------------------------------- | ------------------- |
| 偽カメラ (20 fps、keyframeInterval 60 = 3 秒の Group)、jitter buffer 有効 | 487, 387, 287, 188, 102, 60, 57, 57, 57            | 42 ms               |
| 偽カメラ、jitter buffer 無効                                              | 48, 47, 49, 50, 50                                 | 45 ms               |
| dummy (30 fps、2 秒の Group)、jitter buffer 有効                          | 531, 429, 329, 232, 130, 71, 72                    | 53 ms               |

- 再生遅延 (`playoutDelayMs`) は購読の開始の直後に約 490 ms になり、毎秒 20 ms ずつ下がって、約 25 秒後に約 20 ms で落ち着く。符号化 (読んでから encoder の出力まで) は 1 から 2 ms、復号は 1 から 2 ms で、どちらも遅延の原因ではない
- 購読を始めると relay は cache から Group の先頭以降を送る (prewarm の relay、moqt-draft-21 Section 7.1)。dummy の計測では、最初のフレームは TIMESTAMP から 957 ms 遅れて復号の出力に届き、以降のフレームは実時間の約 2 倍の速さで届いて、約 0.9 秒 (54 枚) かけて遅れが 57 ms まで下がった (live に追いついた)。追いつく途中のフレームの届く間隔は多くが 16 から 40 ms で、フレーム間隔 (33 ms) の半分以上ある
- `devtools/src/utils/playoutBuffer.ts` の `PlayoutBuffer.observe` は、最初のフレームと、前のフレームからフレーム間隔の半分より短い間隔で届いたフレームだけを再生遅延の目標 (`learningOffsets`) から除く。追いつく途中のフレームの多くはこの判定をすり抜け、遅れ (最大 500 ms まで) が揺らぎとして学習される
- 学習した揺らぎは 10 秒の窓 (`PLAYOUT_WINDOW_MS`) に残り、再生遅延の目標 (30 fps で 96.7 パーセンタイル) を押し上げる。窓から抜けた後も、再生遅延は毎秒 20 ms (`PLAYOUT_DELAY_DECAY_MS_PER_SECOND`) でしか下がらない
- 購読の Group の後半の欠落 (sora-moq 側で調査中) は、この遅延とは別の事象である。上の計測でも 1 回ずつ起きたが、再生遅延の推移には関係しない

偽カメラは Chromium の `--use-fake-device-for-media-stream` で、実際のカメラより絵が単純 (差分フレーム約 3 KB) である。実際のカメラでの符号化の遅延 (`latencyMode` の既定 "quality") は、この計測では確かめていない。

## 設計方針

- 購読の開始と基準の取り直し (`restart`) の後は「追いつき中」とし、その間に届いたフレームの揺らぎは再生遅延の目標に使わない (基準の遅れの記録には使う)。追いつき中は、届くフレームが遅れの最小値を下げ続ける。遅れの最小値が一定の時間、一定の幅より大きく下がらなかったら、追いつき中を終える
- 判定は TIMESTAMP と受信側の時刻の差 (遅れ) の推移だけで行い、publisher と subscriber の時計のずれに依らない。SUBSCRIBE_OK の LARGEST_OBJECT で cache から届く Object は見分けられるが、購読の後に publish されて cache の配信の後ろで待った Object も遅れて届くため、それだけでは足りない
- 追いつき中の判定の幅と時間は、実測の届き方 (上の dummy の計測の復号の出力の時刻の列) をテストの入力にして決める。live に追いついた後の経路の揺らぎで追いつき中に戻らないよう、判定は開始と取り直しの後だけにする
- 購読の途中の揺らぎの学習 (最初のフレームとまとまって届いたフレームを除く、上限を超える揺らぎを除く) は変えない

## 完了条件

- 実測の届き方 (cache から実時間の約 2 倍で追いつき、その後は live) を積んだ PlayoutBuffer の単体テストで、追いついた後の再生遅延が live の揺らぎの程度に収まることを固定する。修正前はこのテストが失敗することを確かめる
- 購読の途中で経路の遅延が跳ねた場合は、従来どおり再生遅延が上がることを既存のテストで確かめる
- 配備 relay で、購読の開始から 5 秒後の表示の遅延が、jitter buffer 無効のときとの差 100 ms 以内に収まることを確かめる
- `vp check` と全テスト (vitest) が通る
