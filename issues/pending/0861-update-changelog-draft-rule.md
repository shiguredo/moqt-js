# ドラフト期間中の CHANGES.md の扱いとリリース時の記録方法を定める

- Created: 2026-10-14
- Completed: {YYYY-MM-DD}
- Branch: feature/update-changelog-draft-rule
- Refreshed: 2026-11-14

## 目的

`CODEBASE.md` の「MOQT RFC ドラフト中の特別ルール: CHANGES.md を更新しない」は、ドラフト期間中の変更履歴の扱いと、ドラフト期間が終わったときの記録方法を定めきれていない。変更を入れるたびに CHANGES.md を更新するかの判断が割れ、実際に 0858 では更新の可否をユーザーへ確認する必要があった。61e1d576 が追記した `[FIX]` エントリは 46ca1373 で削除され、当初の併存は解消している。
現在の `## develop` は draft-23 対応の 1 行だけで、ルールと実績は一致している。残るのは、ドラフト期間中の変更をリリース時にどう記録するかを決め、ルールに明記することである。ルールを狭めて `[FIX]` だけを記録するか、ルールを維持してリリース時の扱いを明記するかを決める。

## 現状

- `CODEBASE.md` の「MOQT RFC ドラフト中の特別ルール」は `CHANGES.md を更新しない` と定めている
- `CHANGES.md` は 8d54b822 (`RFC ドラフト中は変更履歴を残さない`) で 3219 行が削除され、同じコミットで `CODEBASE.md` にルールが追加された。
  以降の `## develop` には 61e1d576 (`基準の共有の解除を往復の検出で判断する`、2026-10-14) が `[FIX]` エントリを 1 件追記したが、46ca1373 (`変更履歴を draft-23 対応に更新する`、2026-11-07) がその `[FIX]` エントリを削除し、`## develop` を「Media over QUIC Transport draft-23 対応」の 1 行にした
- 現在の `## develop` に `[FIX]` エントリは無く、「ドラフト中は一切更新しない」と「利用者に見えるバグ修正は `[FIX]` で記録する」の併存は 46ca1373 で解消している。ルールと実績は一致している
- 0858 の修正 (音声の符号化形式をマイクの取り出した形式に追従させ、`start()` の失敗条件を増やす) は利用者に見える挙動の変更だが、このルールに従って CHANGES.md には記録していない
- ドラフト期間が終わった時点で、ドラフト中に入れた変更の履歴を拾い直す手順は CODEBASE.md にも CHANGES.md にも無い
- `shiguredo-changelog` は「変更履歴は派生元ブランチとの最終的な差分のみを記載すること」と定めている。ドラフト期間中に個別の変更を記録しない現在のルールはこの方針と整合する。`[FIX]` だけを記録する場合は、この一般規則に対する例外を追加することになる

## 設計方針

どちらかに揃える。判断はユーザーが行う。

- ルールを狭める: ドラフト中でも `[FIX]` だけは記録する (利用者に影響する修正の履歴を残す)。`[CHANGE]` / `[ADD]` / `[UPDATE]` はドラフト中には記録せず、リリース時に `shiguredo-changelog` の「最終的な差分のみ」に従ってまとめて書く。`shiguredo-changelog` の「最終的な差分のみ」に対する例外を追加する
- ルールを維持する: `## develop` の `[FIX]` エントリは取り消したまま (46ca1373 で実施済み) とし、ドラフト期間中の変更をリリース時にどう記録するか (ドラフト期間終了時にまとめて書く / 書かない) をルールに明記する。ドラフト期間終了時にまとめて書く場合は、`shiguredo-changelog` の「最終的な差分のみ」に従い、ドラフト期間中の個別の変更ではなく、リリース時点の最終的な差分を書く

決めた内容を `CODEBASE.md` に反映し、`CHANGES.md` の `## develop` がそのルールと一致していることを確認する。`AGENTS.md` から参照される規約として矛盾が残らないようにする。

## 完了条件

- ルール (更新しない / `[FIX]` だけ記録する) が決まり、`CODEBASE.md` の記述がそれに一致していること
- `CHANGES.md` の `## develop` の内容が決めたルールと一致していること (記録するなら 0858 などドラフト中の修正を追記し、記録しないなら 61e1d576 のエントリを取り消す。取り消しは 46ca1373 で実施済み)
- ドラフト期間中の変更をリリース時にどう扱うかが、`CODEBASE.md` または `CHANGES.md` を読めば分かること
- `vp check` が通ること (ドキュメントのみの変更でも整形検証の対象)

## pending にした理由

設計判断待ちである。ルールを狭めて `[FIX]` だけを記録するか、ルールを維持してリリース時の扱いを明記するかを決める必要がある。`CODEBASE.md` の現在のルールと `CHANGES.md` の `## develop` は一致しており、当初の矛盾は 46ca1373 で解消している。しかし、どちらのルールを正とするかは公開される変更履歴の方針を変えるため、ユーザーの判断を待つ。
無人 CI ではユーザー確認が取れないため、判断が済むまで pending とする。再開時は、決めたルールを `CODEBASE.md` に反映し、`CHANGES.md` の `## develop` をそれに合わせて更新し、`vp check` を通す。
