# CHANGES.md の develop セクションを規約に適合させる

## 目的

`CHANGES.md` の `## develop` が `shiguredo-changelog` の規約から外れている。規約は「派生元ブランチとの最終的な差分のみを記載すること」「開発ブランチ内の中間状態の修正は記載しないこと」を定め、`.rst` / `.md` ファイルの変更は変更履歴に反映しないとしている。また、issue 番号は `shiguredo-issues` が `CHANGES.md` への記載を禁止している。このままリリースすると、利用者に意味の伝わらない変更履歴が出る。

## 現状

2026-09-29 に `CHANGES.md` を確認した結果は次のとおり。`## develop` には 497 エントリある。

- issue 番号 (`(#0NNN)` 形式) が 70 箇所残る。異なる番号は 66 で、`#0316` が 5 回登場する
- 開発中に追加して同じブランチ内で取り消した変更のエントリが残る
  - GOAWAY の Request ID は「削除する」と「追加する」の両方がある
  - `Object Forwarding Preference` の enum を「追加する」エントリがあるが、後に「未使用の export を削除する」で消えており、`src/` に `ObjectForwardingPreference` は存在しない
- `### misc` が develop 内に 4 回出現する。種別順序 (CHANGE → ADD → UPDATE → FIX) も守られておらず、種別が何度も入れ替わる (種別順序違反は 24 箇所)。さらに、現在の `### misc` にはライブラリの動作を変える FIX なども含まれており、規約が `### misc` を「機能に直接影響しない変更のサブセクション」と定める使い方からも外れている
- 担当者行 `- @voluntas` が無いエントリが 10 件ある。`- @voluntas` を 2 回書いているエントリが 1 件あり、同じ見出しのエントリが重複している例 (`HIGH_LEVEL_API.md を現コードに合わせる`) もある

## 設計方針

- 直近リリース (`## 2026.2.0`) との最終的な差分だけを残す。追加と削除が同じブランチ内で完結している変更のエントリは削除する
- issue 番号を削除する
- 機能に直接影響する変更 (公開 API・プロトコル・メディア処理など) は、セクション先頭に CHANGE → ADD → UPDATE → FIX の順で並べる
- 機能に直接影響しない変更 (ドキュメント追加・リファクタリング・テスト整備など) は、セクション末尾の `### misc` 1 つだけにまとめ、misc 内も CHANGE → ADD → UPDATE → FIX の順で並べる
- 各エントリの最後に担当者行を 1 つだけ置く
- 同じ変更内容のエントリが複数ある場合は内容を統合して 1 つにする。ただし `.md` / `.rst` ファイルの変更のみのエントリ (`HIGH_LEVEL_API.md を現コードに合わせる` など) は規約により変更履歴に記載しないため、統合ではなく削除する

## 完了条件

- `## develop` から issue 番号が消えている
- 中間状態の記述が統合または削除され、現存しない API のエントリが残っていない
- `### misc` がセクション末尾に 1 つだけあり、機能に直接影響する変更が misc に混ざっていない
- セクション先頭のエントリ群と `### misc` 内の両方で CHANGE → ADD → UPDATE → FIX の種別順序が守られている
- 全エントリに担当者行が 1 つずつある
