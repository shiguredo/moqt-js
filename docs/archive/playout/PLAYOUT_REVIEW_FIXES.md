## 指摘への修正

| 指摘                        | 対応                                                                                                                                                                       |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 4-1 空の揺らぎ分布          | 500 ms 超の観測しか残らない場合、映像の直前の学習遅延を保持する。初回の未学習 0 ms と分け、キュー上限による切り下げは維持した                                              |
| 4-2 同じ購読の decoder 復旧 | Group / Object の位置を保持して次のキーを待つ。復旧・再構成の完了まで入力を止め、古い完了は世代で除外する。構成を変更した最初のキーも復号し、古い Group の構成は適用しない |
| 4-3 再同期後の深さ          | 最も早く再開できる時刻を維持し、後続音声の時間伸長で目標の深さへ戻す。実際の予約深さを映像の同期先へ反映する                                                               |
| 4-4 出力切替の競合          | 同じ AudioContext 内の切替を世代付きで直列化する。古い失敗で最新の切替を止めず、開始中に変わった選択も適用してから有効にする                                               |
| 4-5 直接試験                | 有効学習開始から 1,999 / 2,000 ms の不感帯、圧縮の適用量と後続予約、欠落区間内の上限制約を追加した                                                                         |
| 4-6 固定待ちと CI           | 収録の終了フレームと予約の drain を待つ。実リレーの試験は 2 分割し、各試行 8 分、再試行込み 16 分を 20 分のジョブへ割り当てた                                              |

DevTools には、購読前に再生を有効にした場合や再購読時に、新しい入口の AudioWorklet の
準備を待たず音声を渡す別の不具合があった。入口を公開してから準備を待ち、途中で入口や
停止状態が変わった場合は古い graph だけを解放する。共有 AudioContext は閉じない。

短い音の終端では、停止通知が出力位置より遅れて届くと補間中の波形を急に 0 へ切っていた。
実クラスで約 0.278 の段差を再現し、直前の実出力から 2 ms で減衰するよう修正した。
停止通知の重複で減衰をやり直さず、終了処理も減衰完了まで待つ。
E2E のしきい値は緩めていない。

全体試験の再実行では、リセット後の短音の振幅は正常だが、収録した実音のサンプル数が
不足する別の失敗も再現した。出力前後を同時に記録すると、旧 drain は 52.4 ms 待って
10 ms の音を鳴らしたと報告する一方、AudioContext.currentTime は 0.1333 秒、
実音の予約終端は 0.1496 秒だった。resume の Promise が解決しても実出力時計はすぐには
追いつかず、壁時計だけの完了判定が約 16.3 ms 早かった。

drain は実出力位置を予約と同じ時計へ戻して未再生量を確認し、実音の終端がまだ描画されて
いない間も完了しないようにした。上限時間は維持し、上限で切る量も実出力位置から数える。
短音の試験は、実際の予約終端を描画する前に drain が返らないことも直接検査する。
収録の完了は予約終端からも求め、失敗が単なる再試行で隠れないようにした。

## 再同期後の回復

再同期時に `max(最早時刻, 到着 + 50 ms)` へ戻す案は採用しなかった。
出力の先行量が無い入力では、再開までに 40 ms の無音を追加するためである。
まず届いた音を再開し、その後に不足する深さだけを増やす。

伸長には、NetEq の
[PreemptiveExpand::CheckCriteriaAndStretch](https://webrtc.googlesource.com/src/+/031cc215615895d7ae039d4098c2716d7acf2dc3/modules/audio_coding/neteq/preemptive_expand.cc)
の、15 ms の位置で強く相関する周期を重ね合わせる方式を採用した。
直前の実音 10 ms と今回の実音を使い、将来の入力は待たない。
これは NetEq 全体の移植ではなく、既存の浮動小数点 PCM の周期判定と組み合わせた実装である。

- 遅着で基準を取り直した場合に限り、後続音声を伸長する。通常の到着の揺れでは始めない。
- 1 回の要求は今回の音の長さと不足分の小さい方までとする。実適用量だけを基準へ戻す。
- 音声の先頭と末尾を保存し、全チャンネルで相関を確認する。周期性が弱い場合は加工しない。
- 無音は延長できる。適用できる音が無い間は浅い状態が続くため、回復時間の上限は保証しない。
- 音声の予約深さは有効な実出力時計から求める。新しい観測が無い場合は従来の予算を使う。

出力の先行量が 0 の直接試験では、50 ms から 10 ms に落ちた状態から、
新たな穴を作らず実適用した伸長量に従って 50 ms へ戻ることを確認した。
圧縮も適用率 0 / 0.5 / 1 を含め、要求と実適用が違っても後続の予約が連続することを確認した。

## その他の指摘

- 映像の重複 timestamp は FIFO で複数の入力情報を保持する。実 VP9 の 120 出力で、入力情報の欠落と残存が無いことを確認した。音声の重複時の設定とは分離した。
- decoder の復旧・再構成後は未出力の映像入力を消し、同じ timestamp の新しい出力が旧位置を引かないようにした。既に復号した表示待ちは維持する。
- 同じ失敗した映像構成を Object ごとに再試行せず、異なる構成なら復旧を試みる。
- Opus の timestamp 復元失敗は、直接 / Worker とも出力を閉じ、error へ 1 回通知する。通知先の例外で未処理の rejection を残さない。
- Worker へ渡す decode 要求を型で検査し、転送するバッファは独立した ArrayBuffer にする。
- 時刻なしと媒体時刻 0 を区別し、TIMESCALE の変換を購読者から実 Opus decoder まで確認した。2.5〜60 ms の raw Opus の実復号も維持した。
- 映像の毎秒 20 ms の遅延低下という旧不変条件、旧 GainNode / HTMLAudioElement 前提の説明を整理した。過去の計測件数と識別子は当時の値を保ち、最新報告へ案内した。
- 測定ガードは実 AudioContext を作ったことも確認する。入力ロード前の失敗は、Context を確保していないことを別に検査する。
- 実リレーの映像試験は 640 × 360 とし、映像と音声の待機を含むケースの総 timeout を 90 秒へ揃えた。

`AudioData.duration` はフレーム数とサンプルレートから求まるため、復元時に失われるという
指摘は採用していない。根拠は [WebCodecs の AudioData 属性](https://w3c.github.io/webcodecs/#dom-audiodata-duration)
である。また、通常の経路で到達しない pending の負値を理由とする防御処理は追加していない。
raw Opus の投入順の対応は、検証した 1 パケット 1 出力の形式に限る。出力を黙って欠落させる
任意の decoder までずれないことを確認したわけではない。
`prepare-playout-delay-variants.mjs` の基準 `a011728e` は、採用前の候補を再現するため維持した。
最新の起動判定を含む製品コードの比較は、今回のように比較用の source root を明示して行う。

## Chrome での比較

macOS / arm64 の Google Chrome 156.0.8078.79 で、Julius / Kyoko の日本語 6 秒、
44.1 / 48 kHz、正常到着 / 周期的な 60 ms の停滞 / 0〜30 ms の揺らぎ /
途中から恒常的に 60 ms 遅くなる段差を各 3 回収録した。合計 48 条件、17,077 パケットである。
受信 transform で同じ Opus パケットを WebRTC、修正前、修正後へ複製し、同じ AudioContext で
出力を収録した。44.1 kHz は出力のレート変換を含む対照であり、通常の Opus 出力は 48 kHz を使う。

全 48 条件でパケット対応と保存パケットの再復号を照合し、PCM の最大差分は 0、収録欠落は 0、
Chrome の出力統計の underrun は 0 回 / 0 ms だった。
正常到着と 0〜30 ms の揺らぎでは、追加した伸長は全試行 0 ms だった。

次表は、原点の校正が安定した試行の、各出力の遅延 p50 の最小〜最大である。
標本を混ぜた分布や、音響出力までの end-to-end 遅延ではない。
出力ごとに採用窓が異なるため、この表だけで優劣を決めず、後述の同じ参照位置の差も確認する。

| 周期的な 60 ms の停滞 | 9 / 12            | 61.3〜69.5 ms  | 61.7〜69.9 ms   | 107.2〜129.1 ms |
| 0〜30 ms の揺らぎ     | 9 / 12            | 68.4〜71.1 ms  | 67.4〜72.4 ms   | 73.3〜97.8 ms   |

校正を棄却した 10 条件は隠さず null のまま保持した。Kyoko / 48 kHz の正常、周期停滞、
揺らぎの各 3 回と、同じ音源・レートの段差の 2 回目である。復号参照と入力の局所照合が
10 窓以上成立し、遅延の中央 80 % が 2 ms 以内に収まる条件を満たさなかった。
校正の棄却は収録そのものの無効とは分ける。
全 48 条件の局所照合は、修正後が 5,664 窓採用 / 823 窓棄却、修正前が 5,625 / 862、
WebRTC が 5,725 / 762 だった。条件ごとの採用率は修正前後が 56.8〜100 %、
WebRTC が 49.2〜100 % であり、照合できない区間まで同じ品質だったとは言えない。

同じ参照位置で両出力を照合できた窓の差で比較すると、修正後 − 修正前の遅延差の各試行 p50 は、
正常 −1.79〜+0.07 ms、周期停滞 −0.10〜+0.40 ms、揺らぎ 0〜+1.33 ms、
段差 0〜+6.94 ms だった。段差後に浅いままの状態を戻す分の遅延は増えるが、
再開時へ 40 ms の無音を足す修正にはしていない。

段差後の実予約深さは、音源開始から 3〜5.7 秒の区間で、各試行の p50 が
修正前 44.5〜49.8 ms、修正後 49.7〜52.5 ms だった。実際に伸長した合計は 3.67〜15.15 ms。
出力の先行量が存在する実機では、再同期後の深さも直接試験の 10 ms とは異なる。
`pushAudio` を含むメインスレッドの処理の各試行 p95 は 0.20〜0.40 ms だった。
これは AudioWorklet の処理時間の測定ではない。

高相関の前後区間から、参照音声が活動中と確認できた完全無音は、修正前後とも全条件 0 ms。
ただし活動を判定できない無音は残り、修正後では条件ごとに 0〜216.4 ms を数えた。
これを音切れ 0 の証明や音質の優劣と同一視しない。相関と振幅も MOS や日本語会話の聴感評価ではない。

## 検証と残る範囲

- 単体テスト / PBT: 263 ファイル、4,329 件成功。
- Chromium E2E: 全 261 件成功。最終 drain 修正後に全体を再実行した。
- 短フレームの開始 / リセット / 補間: 12 条件を各 5 回、60 回成功。振幅、段差、活動サンプル数のしきい値は維持した。
- production E2E: 全 12 件成功。
- `vp check`: format / lint / 型検査が成功。SDK と DevTools のビルド、`git diff --check` も成功。
- 実リレーの CI 選択は通常試験を 16 / 15 件に分割し、集合の重複 0、欠落 0 を確認した。1 worker を保ち、手動の調査試験 11 件は CI の分割対象から除く。

新しい回帰試験では、実 AudioContext / AudioWorklet / WebCodecs と実クラスを使った。
API の置き換えや decoder のモック・スタブを追加していない。

最終コードでは、Chrome で音声予約と canvas の描画を同時に測る A/V 11 条件も再実行し、
修正前後の全収録が有効であることを確認した。通常の日本語は音声遅延 p50 / p95 とも
69.5 ms、同期ずれの絶対値 p95 は 2.37 ms、補間できない穴は 0 ms だった。
一方、長い停滞の穴は残る。

(`2026-10-31T15-13-29.218Z-2083-webrtc`)。パケット再復号差分、収録欠落、出力 underrun は
全条件 0。段差後の予約深さ p50 は修正前 47.0〜49.0 ms、修正後 49.8〜53.1 ms だった。
この追加収録では Kyoko の照合採用窓は減り、44.1 kHz が修正前 112 / 124 窓に対し
修正後 83 / 124 窓、48 kHz が 105 / 125 窓に対し 81 / 125 窓だった。
48 kHz の修正後は遅延 p50 が 45.0 ms、p95 が 109.7 ms と大きく分かれた。
段差の前後で遅延が変わり、照合窓にも偏りがあるため、低い p50 だけを改善の根拠にしない。
時間伸長後の聴感が WebRTC と同等であることは、この計測だけでは確定していない。

Bluetooth 機器の音響出力と実際の会話の聴取は未確認である。今回の出力波形の測定は
Chrome 内部の収録であり、Bluetooth のドライバーや無線区間を含まない。
実リレーの接続情報はローカルに無いため、新しいコードでの実リレーの完走時間と CI の成功は
未確認である。以前の CI 失敗を直したと推定するだけで合格とは扱わない。
