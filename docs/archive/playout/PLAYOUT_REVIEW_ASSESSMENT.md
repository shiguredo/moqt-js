# playout レビューの現行コードでの再検証

過去の調査記録。本文の実装と「現行」は記録時点のもの。
現在の説明は [音声と映像の再生](../../PLAYOUT.md)、記録の一覧は [調査記録](../README.md) を参照すること。

この記録は修正前の評価である。実施した修正と再計測は
[playout レビューへの対応](PLAYOUT_REVIEW_FIXES.md) を参照する。

確認日: 2026 年 10 月 31 日。対象は develop の `99a8c10c`。
提示されたレビューの対象 `e75d866f` の後に、`8927c50c` と `99a8c10c` が追加されている。
この記録では重要な指摘 6 件を現行コードと照合し、実クラスと実 Chrome で確認した範囲を分ける。
製品コードと既存テストは変更していない。

## 判断

重要な指摘の問題箇所は現在も残っている。ただし、再同期を単純に以前の式へ戻す案、
固定待ちだけを CI 失敗の原因とする判断、旧測定値の一括更新はそのまま採用しない。
また、レビュー対象後に追加した AudioWorklet の準備が DevTools の別経路で抜けている。
まず、この再生できない経路と現在の CI 失敗を解消する必要がある。

| 指摘                           | 現行コードでの確認                                                                                | 対応の考え方                                                                                                 |
| ------------------------------ | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 4-1 映像の遅延が 0 になる      | 再現した。600 ms の遅着で有効な分布が空になり、学習遅延が 40 ms から 0 ms へ変わった              | 分布が空の場合と、実際に 0 ms と学習した場合を区別する。空では直前値を保持し、現在のキュー上限は別途適用する |
| 4-2 decoder 復旧で位置が消える | reset と requireKeyFrame の差を実クラスで再現した。現行の呼び出しと既存テストは reset のまま      | 同一購読の復旧では位置を保持する。reset の完了中に入力を通さないことと、再構成中の世代も併せて確認する       |
| 4-3 再同期後に深さが減る       | 実 scheduler で初期 50 ms、遅着後は後続も 10 ms になる列を再現した                                | 再開時刻と定常の深さの回復を分けて比較する。推奨式への単純な差し戻しを先に確定しない                         |

| 4-5 直接試験が不足している     | 指摘された境界と圧縮適用時の直接試験、欠落中の assert は現在も不足している                        | 1,999 / 2,000 ms、実際に圧縮した後続予約、欠落区間そのものを固定する                                         |

## 実クラスでの再現

`PlayoutTimeline`、`AudioPlayoutScheduler`、`VideoDecodeOrder` を通常の Vite ビルダーで変換し、
実装を差し替えずに入力列を渡した。時計 API や decoder を模した代替実装は使っていない。
これは予約と状態遷移の確認であり、スピーカーの出力や映像表示を再現した測定ではない。

### 映像の空の学習分布

`src/playout/timeline.ts` の observe は、旧基準に対する揺らぎが 500 ms を超える値を除外する。
映像側は空の percentile の 0 をそのまま代入し、音声側だけが空を null として区別する。
修正時の回帰試験では、40 フレームの初期観測、40 ms の揺らぎ 60 フレーム、
600 ms の遅着 60 フレームと区間を分け、40 ms の学習値を持った分布が空になる境界を固定した。
旧評価の 0 / 40 ms を混在させた入力だけでは、分布が空になる前の正常な減少も含み得るため、
その値の変化だけを空の分布の影響と断定しない。

この値は映像自身の学習結果である。catalog の下限や音声との同期の補償がある場合に、
最終表示遅延も必ず 0 ms になるとまでは言えない。回復後の影響時間も到着列による。
空の分布を正常な 0 と同一視する問題は、これらとは別に修正すべきである。

### 再同期後の音声の深さ

arrivalDelaySeconds を 0.05、20 ms の音声、now と arrivalSeconds が一致する条件で、
到着を 0、0.2、0.22、0.24、0.26、0.28 秒とした。
開始から到着を引いた値は、最初が 50 ms、その後はすべて約 10 ms だった。
`src/playout/audioPlayout.ts` の scheduleByArrival が最早時刻へ anchor を移した後、
深さを戻す方向の制御が無いことを確認できる。

実機では now と arrivalSeconds に出力バッファの先行量があるため、常に実出力が 10 ms になるという意味ではない。
また、この再現だけではレビューの A/V ずれの推定値全体を実出力で確認したことにはならない。

推奨式の max(最早時刻, 到着 + 50 ms) へ戻すと、この入力では復帰が 40 ms 後ろへ動く。
穴を増やさずに定常の深さを戻す案、推奨式へ戻す案、現行を同一入力で比較する必要がある。
復帰中の実適用値を同期と統計へどう反映するかも含め、音声だけの連続性と A/V を両方測る。

### decoder の復帰

Group 2 / Object 10 のキーを通した後、reset すると Group 1 / Object 0 のキーも通った。
requireKeyFrame では同じ旧キーは stale となり、Group 2 / Object 11 の後続キーは通った。
現行の handleVideoDecoderError と reconfigureVideoDecoder は reset のままで、
`src/createMediaSubscriber.media.test.ts` も旧 Group の再通過を期待している。

復号器だけが参照を失ったときに購読位置まで消す理由は無い。
一方、新しい購読や配信の世代が変わった場合には reset が必要であり、すべての reset を機械的に置換しない。

## 実 Chrome の出力切替

実 AudioContext の setSinkId に、存在しない機器と既定の機器を続けて要求した。
API は置き換えず、Chrome 156 の実 Promise の完了を記録した。

- 失敗時に閉じない場合: 旧要求が NotFoundError、新要求が成功し、Context は running。
- 現行の失敗処理と同様に旧失敗で閉じる場合: 新要求も InvalidStateError になり、Context は closed。

レビューに記載された「新要求の成功後に旧要求が失敗する」という順序は、この試行では観測していない。
ただし、最新の選択が既に要求済みなのに旧失敗で再生を止める問題は確認できる。
現行の audioPlayback の参照比較は Context の世代だけを守り、同じ Context 内の要求を区別できない。
この試行はネイティブ API と close の関係を確認したもので、DevTools の UI 全体の競合試験ではない。

## レビュー対象後に見つかった準備の欠落

`devtools/src/hooks/useSubscriber.ts` の createSubscriberMediaPlayout は入口を新規作成し、
`audioPlaybackController.ts` の attachPlaybackToPlayout で既存 Context を付ける。
この経路は setAudioOutput だけで、prepareAudio を待たない。

一方、現行の AudioPlayoutSession は最初の pushAudio より前の準備を必須とし、
未準備なら AudioOutputRenderer.assertReady がエラーを返す。
toggleAudioPlayback 側に追加した準備だけでは、購読前に再生を有効にする場合や入口の作り直しを覆えない。
この問題は今回の出力側への移行で作り込んだものであり、先に直す必要がある。
準備の完了を待つ範囲と、待機中に購読が変わった場合の世代管理を一緒に設計する。

## 現在の CI と再試験

確認した先端 `99a8c10c` の [ci](https://github.com/shiguredo/moqt-js/actions/runs/41193596214) は、
非 relay の E2E が 246 件成功、2 件失敗だった。

- 圧縮後の欠落の試験: gapCount が期待 0 に対し 1。
- 120 サンプルの initial の試験: 最大段差が約 0.1344、期待は 0.006 未満。

同じ 2 件をローカルの Chromium で各 3 回実行し、6 件とも成功した。
これは CI の失敗を否定する結果でも、固定 sleep が唯一の原因である証拠でもない。
特に gapCount は、終端を明示しない場合に最後の実音以降も集計する現在の意味と、
検査したい欠落区間を分けて確認する必要がある。
短い音の段差は対象サンプルが取得されているため、単なる未収録と断定しない。

[実リレーの e2e-test](https://github.com/shiguredo/moqt-js/actions/runs/41193596231) も失敗している。
ログでは DevTools の再購読や音声再生の試験が複数失敗し、受信・復号は進むのに
playedMs が 0、鳴らせなかった音が error として増える観測が両試行に残っている。
これは上記の未準備経路と整合するが、全失敗の原因をその一点と特定したわけではない。

試行の実行区間は、初回が約 9 分 13 秒、再試行が約 9 分 12 秒で、完了の集計まで到達していない。
ジョブ全体は約 19 分であり、「9 分を 2 回なら必ず 20 分に収まらない」とは言えない。
ただし余裕は小さく、ジョブ上限だけ延長しても各試行の 9 分制限は変わらない。
まず実際の失敗と完走時間を確認し、必要ならテストを分割して試行とジョブの予算を揃える。

## 修正提案の補足

- 旧 GainNode の残存や同一波形の continuation 分岐の指摘は、出力側への移行で対象の経路が削除済みである。
  旧版の行番号だけを根拠に修正しない。
- buffer.prop.ts の毎秒 20 ms までという assert、同一 timestamp の映像入力の 1 件保持、
  DevTools の HTMLAudioElement 前提の説明は現在も残っており、整理が必要である。
- Opus の出力対応が欠けた場合の扱いと restore 内の例外通知は、音声の耐障害性の別項目として検証する。
  一方、「restore が duration を落とす」という指摘は採用しない。
  AudioData.duration は numberOfFrames / sampleRate から求まる読み取り専用の値であり、
  再構成時にも両方を保存している。
  根拠は [WebCodecs の AudioData 属性](https://w3c.github.io/webcodecs/#dom-audiodata-duration) にある。
- 過去の測定時の件数や比較元の識別子は、一律に現行の値へ書き換えない。
  現行動作を説明する文書と、当時の測定記録を分け、最新報告への案内と識別子の対応を補う。

## 対応する順序

1. DevTools の入口作り直し時の準備を修正し、購読前の再生有効化と再購読を実ブラウザーで確認する。
2. 現行 CI の波形と統計の失敗を切り分ける。収録範囲と完了条件を明示し、しきい値の緩和で通さない。
3. 同一購読の decoder 位置保持、出力切替の世代管理、映像の空の分布を回帰試験付きで修正する。
4. 到着基準の再同期を同一入力で比較し、定常の深さと復帰の連続性、A/V の実出力を両立する案を選ぶ。
5. 境界値試験、古い不変条件と説明を整理し、現行の操作手順と統計を文書へ反映する。
