# playout の低遅延化に向けた論文調査と比較

2026-10-30。日本語音声と QUIC Datagram の条件で、起動時の遅延と通常の揺らぎを分けて調べた記録である。
通常の jitter の窓を短くした案では、回復が速くなっても予約上の隙間が増えることを確認した。

## 確認した一次資料

- [Moon, Kurose, Towsley (1998), Packet audio playout delay adjustment: performance bounds and algorithms](https://an.kaist.ac.kr/~sbmoon/paper/intl-journal/1998-acm-multimedia-voip.pdf)
  は、与えられた到着列と遅着による欠落数の制約に対する最小平均遅延の限界を求め、最近の分位点とスパイク検出を組み合わせる。§4.2 では、スパイク中の値を通常の分布へ残さず、現在の遅れへ追従する。
- [Ramjee ら (1994), Adaptive Playout Mechanisms for Packetized Audio Applications in Wide-Area Networks](https://www.cs.columbia.edu/~hgs/papers/Ramj94_Adaptive.pdf)
  は、急激な遅延の変化への追従を含む複数方式を実測した到着列で比較している。
- [WebRTC NetEq の DelayManager の既定値](https://webrtc.googlesource.com/src/+/dd414f9a218bd7f19cdff8a594733cd190488fa2/modules/audio_coding/neteq/delay_manager.h)
  と [UnderrunOptimizer](https://webrtc.googlesource.com/src/+/dd414f9a218bd7f19cdff8a594733cd190488fa2/modules/audio_coding/neteq/underrun_optimizer.cc)
  を確認した。比較対象とした部分は 500 ms ごとの最大相対遅延、20 ms の階級、忘却係数 0.983、95 百分位である。

論文の限界値は特定の到着列と欠落制約に対する値であり、未来の到着を知らないブラウザ向けの固定値ではない。
また、talkspurt ごとに無音区間を調整する方式を、そのまま連続した Opus と A/V 同期へ移せるとは扱わない。
NetEq の候補も部分的な独立実装であり、起動時の重み補正、並べ替え最適化、時間伸長を含む NetEq 全体の比較ではない。

## 再現した問題と採用する範囲

Chrome の実 DevTools で、日本語 Julius と canvas を実 QUIC で配信した。
起動直後、最初は音声の復号出力が約 51〜60 ms で届き、その後約 200 ms の停止を挟み、約 245〜252 ms 古い出力が返った。
続く新しい出力は約 53〜77 ms へ戻ったが、再生遅延は直ちに戻らなかった。

時間軸は起動中に 250 ms ごとに最小遅延の変化を確認する。停止中も最小値は正常時の値を保つ。
このため、停止後の古い出力が返った瞬間を「追いついた」と判定し、その値を通常の jitter の分布へ入れていた。
映像側の大きな分布へ音声を合わせることで、届いた音が既に新しくなった後にも待ちが増えた。

修正は初期の完了判定に限定した。最小値が安定していても、通常より長い到着間隔で古い出力が返った場合は、もう 250 ms だけ確認する。
延長は 1 回に制限する。繰り返す揺らぎを学習しない状態へ固定しない。
媒体の欠落により媒体間隔と到着間隔が同じだけ開く場合や、遅い経路で一定の周期を保つ場合は通常の学習へ進む。

通常の 2 秒窓、50〜100 ms の音声予算、出力時計の補償、時間圧縮、補間、フェードはこの修正では変えない。
音声の振幅や無音を判定条件に使わず、無音時の映像進行にも依存を加えない。

## 実測した改善と限界

比較元は `a011728e8c01563b35ecf5c345535d0a6c209e1e` とした。以下の 11 条件はそれぞれ 10 秒である。
媒体の最初の 1 秒を除いた音声の出力予定と canvas の描画の p95 を示す。単位は ms である。
日本語の Julius は実録音、Kyoko、Eddy、Grandpa は日本語の読み上げ音声を使い、すべて実 Opus の符号化と復号を通した。
正弦波の条件は、符号化を通さない合成 PCM を使う。
短い音源は必要な長さまで繰り返している。
実 QUIC と DevTools の送信入力は 6 秒の AudioBuffer をループする条件であり、20 秒や 60 秒の連続した原発話ではない。
一方、この 11 条件のうち長い読み上げ音源は、先頭から 10 秒分を連続して投入している。

### 同じ AudioContext での照合

別試行の出力時計による差を避けるため、追加で 2 つの実 playout に同じ AudioContext、Opus 復号済みの日本語 PCM、到着列を同時に与えた。
フレームを渡す順を交互に入れ替え、音声の収録点と canvas は別にした。
この比較は実回線の再試行ではなく、保存した到着列の再投入である。
2 組を同時に動かす計測負荷もあるため、別試行の絶対値とは分けて読む。

通常の 60 秒の到着列では、音声 p95 は修正前 137.9 ms、修正後 136.8 ms、回復できない予約の隙間は 46.4 → 58.8 ms だった。
起動時の停止と末尾の遅着を含む 22 秒の到着列では、音声 p95 は 242.9 → 138.5 ms、映像は 236.7 → 152.6 ms、同期ずれの絶対値 p95 は 21.2 → 13.8 ms だった。
後者の時間圧縮は 151.1 → 84.3 ms、回復できない予約の隙間は 363.4 → 365.7 ms であり、隙間が完全に同じとも、すべて減ったとも扱わない。
この修正は起動時の停止後に待ちを保持する問題への対処であり、通常時の遅延を恒常的に下げる制御ではない。
この 2 件の実行識別子は `2026-10-29T19-06-00.842Z-58654-av` と `2026-10-29T19-07-19.584Z-58982-av` である。
修正後ソースは境界条件のコメントを訂正した `cace693c5066620415ac94b5ed58b810be73f447f0dcb3726698dcce80333420` で、両方とも再生失敗、予約境界の段差の閾値超え、収録連番の欠落は 0 だった。

### 音声の下限を増やす案

50 ms の下限だけを 60 ms または 70 ms に変えた候補も作った。
実 Chrome の 60 秒の到着列を別の AudioContext で順に再投入した試行では、60 ms 候補の総遅延と予約の隙間がともに小さくなった。
ただし、この差には出力時計と実行時刻の揺らぎも含まれるため、同じ AudioContext での比較を追加した。

60 秒の通常到着と 22 秒の停止を含む到着を使い、2 本の作成順を 50 ms → 60 ms、60 ms → 50 ms と入れ替えて各 1 回同時比較した。
同時比較の p95 は、通常到着で音声 137.0〜140.8 ms、映像 138.6〜139.8 ms、停止を含む到着で音声 134.0〜134.9 ms、映像 138.7〜141.6 ms だった。
60 ms 候補による回復できない予約の隙間の削減は通常到着で 7.7〜17.2 ms / 60 秒、停止を含む到着で 14.8〜16.1 ms / 22 秒だった。
一方、起動時の 2 秒の到着列の同時比較では、音声 p95 は 118.8 → 129.4 ms に増えた。
この下限は待ちが小さい場面にも作用するため、今回の既定値は 50 ms を維持した。60 ms を音質と遅延の最適値だとは扱わない。
70 ms 候補も別 Context での 22 秒の再投入では隙間を減らしたが、既定値としては採用していない。

同時比較は `2026-10-29T19-07-49.627Z-59122-av`、`2026-10-29T19-09-10.030Z-59851-av`、`2026-10-29T19-09-39.743Z-59994-av`、`2026-10-29T19-10-58.292Z-60213-av` に保存した。
60 ms のソースは `0fe4ec520c75322fa94e163435e49b668f2e1f8c4529248156291516cf54266a` である。

## 試作して採用しなかった方式

日本語 Kyoko の同じ PCM と、1.2 秒ごとに 80 ms 分の音声が 60 ms 遅れる到着列を使い、各 10 秒を反復した。
到着時刻は同じ規則で作り、実 AudioData と実 VideoFrame を、実 AudioContext と canvas へ投入している。
音声 API の代用品は使っていない。

| 方式          | 試行数 | 予約で回復できない隙間の合計 |  時間圧縮の合計 | 同期ずれの絶対値 p95 |
| ------------- | -----: | ---------------------------: | --------------: | -------------------: |
| 現行の 2 秒窓 |      3 |                34.7〜36.1 ms |   41.5〜42.1 ms |         6.8〜12.1 ms |
| 500 ms 窓     |      3 |              404.7〜407.6 ms | 412.9〜415.2 ms |        33.5〜40.6 ms |

隙間と時間圧縮は起動を含む累積値、同期ずれは媒体の最初の 1 秒を除いた対応組の分布である。
音の隙間は予約の統計であり、その合計を可聴ノイズの長さや物理的な無音時間へ置き換えない。

500 ms 窓は映像の遅延が解消した後の回復を速める一方、次の揺らぎまでに履歴を忘れる。
2 秒以降の区間でも、繰り返す遅着のたびに音声の隙間と時間圧縮が増えた。
初期の不感帯の学習完了だけが早まったことでは説明できない。遅延の回復時間だけを見て採用しない。

スパイク中の分布学習を全期間にわたって止める試作も、120 ms の遅延が繰り返す条件で悪化した。
10 秒間の回復できない隙間は現行の約 417 ms に対し約 867 ms、同期ずれの絶対値 p95 は約 24 ms に対し約 90 ms になった。
このため、起動後のスパイクを一律に除外する処理は製品へ追加しない。

NetEq の区間最大値を参考にした候補は、正常な到着で音声の遅延を約 13 ms 増やした。
実 QUIC の試行では回復できない隙間が減る条件もあったが、今回の起動時の誤学習への修正としては、待ちを恒常的に増やす方式を選ばなかった。
出力残差の平滑化を外す候補も比較したが、起動時の遅延の原因は残り、予約間の隙間が増えた試行があった。

追加確認を映像だけへ限定する案も試した。同じ 22 秒の到着列では、音声 p95 が約 135 ms から約 168 ms に増えた一方、回復できない予約の隙間の差は約 1〜2 ms だった。
このため、音声と映像の両方へ限定的な追加確認を適用した。

## 測定値の区間

DevTools の計測では、購読開始前から復号出力の到着、音声の出力予約、canvas への描画をフレームごとに保存する。
音声は `getOutputTimestamp()` の対応を使った出力予定時刻であり、スピーカーや AirPods の音響ループバックではない。
映像は canvas へ描く処理を終えた時刻であり、ディスプレイの走査完了の実測ではない。

全フレームの分布、最初の出力から 3 秒の分布、それ以降の分布を別に出す。
音声予約の呼び出し時刻と、実際に鳴ると推定する時刻を混ぜない。停止時点で出力時刻が来ていない予約も別に数える。
音声と映像は直前の音声の媒体時刻から同じ媒体時刻へ換算し、40 ms より離れた組を同期評価に使わない。

終了時点の 10 秒窓の p95 だけでは、起動時の大きな遅延が消えたり、逆に解消した遅れが窓へ残ったりする。
過去に見えた約 235 ms を定常値とも単なる表示上の問題とも決めつけず、起動時と継続時の記録で判定する。

各実行はソース全体、測定コード、音源、再投入する到着列の SHA-256 を保存する。
測定の開始前と終了後でソースと音源が一致すること、未処理例外がないことも採用条件にする。
実 DevTools は 500 ms ごとの音声と映像の進行を検査し、再投入の測定は収録量、再生数、実表示数、対応する A/V の組が最低数を満たすことを検査する。

レビューで、収録 Worklet の例外がページの例外へ通知されない経路も確認した。
[Web Audio §1.32.4.2](https://webaudio.github.io/web-audio-api/#dom-audioworkletnode-onprocessorerror) に従い、各収録器の `onprocessorerror` を別に監視し、途中まで十分な PCM があっても当該測定を不採用にする。
実 Worklet の `process()` に例外を起こすブラウザテストで、ページ例外 0 件と収録器の例外 1 件を確認した。
以下の追加確認は、この監視を有効にして行う。上の先行試行とは計測コードのハッシュが異なる。

### 収録器の例外監視を加えた最終確認

同じ AudioContext で修正前と修正後を同時に測った。p95 の単位は ms、媒体時刻の最初の 1 秒を除いている。

| 到着列                 | 音声 p95 修正前 → 修正後 | 映像 p95 修正前 → 修正後 | 同期ずれの絶対値 p95 修正前 → 修正後 |
| ---------------------- | -----------------------: | -----------------------: | -----------------------------------: |
| 公開した起動 2 秒      |            266.5 → 155.0 |            277.1 → 161.4 |                          86.0 → 27.2 |
| 停止と末尾の遅着 22 秒 |            242.1 → 133.5 |            239.1 → 141.5 |                          19.4 → 10.4 |
| 通常到着 60 秒         |            139.6 → 140.1 |            142.1 → 142.0 |                          12.5 → 12.2 |

回復できない予約の隙間は、順に 183.6 → 181.9 ms、364.8 → 373.4 ms、48.9 → 51.0 ms だった。
再投入の 3 条件すべてで再生失敗、予約境界の段差の閾値超え、収録連番の欠落、収録器の例外は 0 だった。
この確認でも、通常到着への恒常的な改善や、予約の隙間の解消は得られていない。
先行する別 Context の 2 秒試験の修正後 120.0 ms と、この同時比較の 155.0 ms を同じ計測条件の値とは扱わない。

実行識別子は `2026-10-29T19-22-04.820Z-65177-av`、`2026-10-29T19-22-09.430Z-65211-av`、`2026-10-29T19-22-39.291Z-65363-av` である。

同じ収録エラー監視を実 QUIC の 3 条件にも加え、各 20 秒で確認した。分布は計測開始後の最初の 1 秒を除く。

| 条件                                   | 音声 p95 | 映像 p95 | 回復できない予約の隙間 / 20 秒 | 予約境界の段差の閾値超え |

独立損失は 2,009 Datagram 中 90 個を落とし、2 Object が欠落した。連続損失は 1,004 Datagram 中 60 個を落とし、60 Object が欠落した。
再生失敗、収録連番の欠落、収録器の例外は全条件で 0 だった。
連続損失の出力波形の最大差分は入力と同じ約 0.175 だったが、閾値超え 6 件を無視して無雑音とは扱わない。
起動時の待ちを直しても、届かない内容の復元と連続損失時の品質は残る課題である。
実行識別子は `2026-10-29T19-23-58.407Z-65564-avRelay` である。

6 件の閾値超えを確認した後、同じ 3 Object 連続損失を、修正前、修正後、修正後、修正前の順に各 20 秒、計 4 回追加した。
この 4 回では閾値超えはすべて 0 件だった。回復できない予約の隙間は修正前 871.6〜955.0 ms、修正後 846.0〜927.8 ms、音声 p95 は修正前 117.9〜124.5 ms、修正後 133.3〜134.7 ms だった。
各試行の入力の到着と出力時計は異なる。通常の到着列の同時比較も踏まえ、この差を起動判定による恒常的な変化とは断定しない。
出力波形の最大差分は、4 回とも各試行の入力の最大差分以下だった。先行試行の 6 件は再現しなかったが、無雑音の証明とはしない。

## 再投入する方法

起動時の到着列の最初の 2 秒を、[相対時刻の fixture](../scripts/fixtures/playout-startup-arrivals.json) として保存した。
各行はトラック、媒体時刻、復号出力の到着時刻で、単位は ms である。接続先、絶対日時、音声データは含めない。
この再投入では回線を使わず、日本語の実 Opus 往復と実 Web Audio に同じ到着条件を与える。
回線を使った検証とは区別する。

日本語音源を準備した後、基準の複製と候補を次のように比較できる。
基準は `a011728e8c01563b35ecf5c345535d0a6c209e1e` とし、結果へハッシュを記録する。

```sh
vp exec node scripts/prepare-playout-delay-variants.mjs investigation-logs/delay-variants

PLAYOUT_SOURCE_ROOT=investigation-logs/delay-variants/baseline \
PLAYOUT_VARIANT=baseline PLAYOUT_AV_SECONDS=2 \
PLAYOUT_AV_TRACE_FILE=scripts/fixtures/playout-startup-arrivals.json \
vp exec node scripts/investigate-playout-audio.mjs av

PLAYOUT_VARIANT=candidate PLAYOUT_AV_SECONDS=2 \
PLAYOUT_AV_TRACE_FILE=scripts/fixtures/playout-startup-arrivals.json \
vp exec node scripts/investigate-playout-audio.mjs av
```

同じ AudioContext で比較する場合は、比較元と比較先のソースを同時に指定する。

```sh
PLAYOUT_SOURCE_ROOT=investigation-logs/delay-variants/baseline \
PLAYOUT_COMPARE_SOURCE_ROOT=src PLAYOUT_VARIANT=paired \
PLAYOUT_AV_SECONDS=2 \
PLAYOUT_AV_TRACE_FILE=scripts/fixtures/playout-startup-arrivals.json \
vp exec node scripts/investigate-playout-audio.mjs av
```

`PLAYOUT_SOURCE_ROOT=src` と `PLAYOUT_COMPARE_SOURCE_ROOT=investigation-logs/delay-variants/startup60` を併用すると、起動判定を揃え、下限だけを 50 ms と 60 ms で比較できる。
各収録は Worklet 内の収録連番と `currentFrame` の両方を保存する。
今回の Chromium では `currentFrame` の重複と直後の飛びも観測したため、収録メッセージの欠落は Worklet 内の収録連番で判定する。
これを DAC や Bluetooth の物理的な出力欠落を検出する計器とは扱わない。

通常の 11 条件は `PLAYOUT_AV_TRACE_FILE` を指定せず `av` を実行する。
実 QUIC の損失試験は `PLAYOUT_RELAY_URI` を環境変数で指定して `avRelay` を実行する。
5 % の独立損失と 2 コピー、3 Object の連続損失と 1 コピーを含む。

実 DevTools の購読経路は `investigate-devtools-latency` で測定する。
`PLAYOUT_BROWSER_CHANNEL=chrome` で Chrome、`PLAYOUT_STARTUP_STALL_MS=220` で 5 回目の音声予約直後に実際のメインスレッド負荷を与える。
通常の観測では後者を指定しない。負荷で既に届かなくなった音の時間を、処理の変更だけで取り戻せるとは扱わない。
