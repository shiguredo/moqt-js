# A/V 再生の低遅延化の計測

計測日: 2026-10-29。比較元は `1c0dbcb9`。音声波形の修正に続き、到着が回復した後も
音声と映像に待ちが残る制御を調べた。単に待ちを削ると音切れが増えたため、到着、実出力の
時計、予約、描画、波形を記録して採用案を選んだ。

## 採用した変更

- 音声と映像の到着の揺らぎを直近 2 秒から求める。送受信時計と経路の最小遅延を求める
  10 秒の窓とは分ける
- 音声の自動予算を `clamp(揺らぎ + 出力の先行量, 50, 100)` ms にする。先行量は実際の
  `getOutputTimestamp()` と `currentTime` から測り、直近 1 秒の p95 を使う
- 共有できる時間軸では、現在の到着の分布と音声予約から同期の補償を引き直す。過去の
  共有の表示時刻を下限として保持しない
- A/V の目標時刻を使う予約の圧縮の不感帯は、最初の 2 秒は 20 ms。その後は到着の
  揺らぎに応じて 5〜20 ms にする。到着基準の予約は 20 ms を保つ
- 音声だけの到着基準の再生は、前段階で検証した 50 ms の予算を保つ

`AudioDelayEstimator` と `AudioDelayFeedback` を削除した。前者の区間最大のヒストグラム、
後者の穴や圧縮による上限拡大と保持に、同期の保持と映像の緩やかな減衰が重なっていた。
実出力の先行量を直接測ることで、別の上限を育てる制御が不要になった。
未使用の `shiftPlayoutEnd` も削除し、実際に予約した終端は `confirmPlayoutEnd` で確定する。
旧制御固有のテストは削除し、実 scheduler、DSP、時間軸を通す回復テストと、予算、欠落、
時計、リセットのテストを残した。

時計のドリフトの検出、基準の共有解除と復帰、出力時計の fallback、catalog の明示下限、
PLC、波形の時間圧縮は必要であり残した。出力の残差の 250 ms の平滑化も、即時反映との
比較で悪化を観測したため残した。

## 計測方法

Node.js v26.13.0、Chromium 156、macOS arm64 で実行した。ブラウザの音声処理は実 API を使い、
モックとスタブは使わない。

制御した到着列では、実際に Opus を符号化 / 復号した日本語 PCM を `AudioData` として渡し、
`VideoFrame` を 30 fps で生成する。音声は 48 kHz、20 ms、映像は canvas に実際に描く。
入力には Julius の日本語発話と、Kyoko、Eddy、Grandpa の合成発話を使う。
配信前の時計と経路の遅延は 20 ms とし、追加の揺らぎと停滞を与える。各ケースは 10 秒。

- 音声の媒体遅延: 媒体の TIMESTAMP から、実出力時計で換算した予約の開始まで
- 映像の媒体遅延: 媒体の TIMESTAMP から、canvas の描画まで
- 同期ずれ: 同じ TIMESTAMP を持つ音声予約と映像描画の差。異なる媒体時刻を補間しない
- 波形: 実 AudioWorklet の出力を Float32 で収録し、隣接サンプルの最大段差を求める
- 穴: 再生の計器が数える、補間で埋まらなかった予約間の長さ

通常の分布は最初の 1 秒を除き、回復後の値は末尾 2 秒から求める。音声 50 fps と映像
30 fps の共通 TIMESTAMP は 100 ms ごとに現れ、通常の同期ずれの分布は 90 組になる。
復号後の入口へ渡す列は、各トラック内の出力順を保つ。順序を保たなかった初期の jitter と
video-step の結果は採用比較から除外し、`baseline-ordered` を比較元にした。

これはブラウザ内の予約と描画の計測であり、スピーカーの音響出力、ディスプレイの発光、
実写の口と声のずれを外部機器で計測したものではない。日本語の発話を使っているが、
発話内容の正解率や主観的な聴取品質の試験でもない。

## 実 QUIC Datagram の A/V 計測

既存のリレーのローカル実行を通し、実高レベル Publisher / Subscriber、Worker の Opus / VP8
符号化と復号、MediaStream、実 canvas、HTMLVideoElement を使った。音声は 64 kbps、
映像は 320 × 180、30 fps。各条件の収録は約 20 秒で、両実装を順に走らせた。
公開接続先で接続終了と handshake 失敗を観測した試行は比較表へ含めない。

損失は、実 QUIC で届いた音声 Datagram の一部を、重複排除と復号の前で落として注入する。
独立 5 % と、50 Group ごとに 3 Group の連続欠落を使う。QUIC の ACK と輻輳制御に影響する
物理的なパケット損失は再現していない。音源の capture と経路の到着は実行ごとに変わるため、
因果比較には先の制御した到着列を重視する。

音声の波形は、受信側の実 AudioContext へ pass-through の AudioWorklet を接続して収録する。
この接続は測定前に行い、その後の最初の 1 秒も遅延の分布から除く。出力は元の
MediaStream の出力先へ流す。収録ブロックへ通しのサンプル番号を付け、6 試行すべてで
収録メッセージの欠落は 0 と確認した。

初期の TrackProcessor による収録では、480 サンプルのブロックの timestamp に約 ±2.9 ms の
揺れがあり、正負の差が相殺していた。これをすべて収録欠落と数える集計は不適切だったため、
最終の波形比較は AudioWorklet の処理順とサンプル番号を使う。ブラウザの currentFrame も
繰り返しと次の飛びを対で観測したため、生値は保存するが収録の欠落の判定には使わない。

表の遅延と絶対同期ずれは p95、穴は計器の累積 (ms)。音声と映像の capture は異なる周期のため、
同期ずれは 20 ms 以内の隣接音声の予約を映像の媒体時刻へ換算した推定値であり、
先の同一 TIMESTAMP の比較とは区別する。HTMLVideoElement の表示コールバックは
各試行 544〜601 回あり、canvas と別に実 MediaStream の消費も継続していた。

| 日本語と損失条件          |     音声遅延 |     映像遅延 | 絶対同期ずれの推定値 |              穴 |
| ------------------------- | -----------: | -----------: | -------------------: | --------------: |
| Kyoko、正常               |  76.1 → 81.3 |  84.8 → 85.3 |           11.0 → 9.6 |         0 → 5.0 |
| Kyoko、独立 5 %、2 重送信 | 128.8 → 71.8 | 133.8 → 80.0 |            8.4 → 8.8 |     59.4 → 37.1 |
| Julius、3 Group 連続欠落  | 129.0 → 71.8 | 133.7 → 69.0 |           10.0 → 5.7 | 1032.2 → 1241.9 |

独立損失では 102 Datagram を落とし、全コピーを失った Group は 2 件だった。連続欠落は
66 Group。いずれも購読全体の数で、収録前の開始処理中も含む。実装候補の音声の追加破棄は 0。
正常時の 5.0 ms の穴と、連続欠落で穴が約 210 ms 増えたことは改善扱いにしない。
低い予算では、次の音が届くまでに補間を予約できる区間が短くなる交換条件が残る。

正常と連続欠落の出力の最大段差は、入力の比較値以下だった。独立損失の候補では出力 0.0783、
入力 0.0741 で上回った。入力の比較値はフレーム内部と TIMESTAMP が連続する境界の最大であり、
これだけで聴感上のクリックを断定できないが、追加の不連続が無いことも確認できていない。
受信した 20 ms の音声にも、TIMESTAMP が 17.299 ms / 22.701 ms 刻みになる区間があった。
送信時刻と capture の追跡、および局所の波形の照合は残る課題である。

## 再現と記録

計測の入口は `investigate-playout-audio.mjs`。到着を制御する段階は `av`、実 QUIC を通す
段階は `avRelay` を指定する。入力音声は `prepare-playout-japanese.mjs` で用意する。

- `PLAYOUT_SOURCE_ROOT`: `av` / `avRelay` で比較するソース一式。別ディレクトリの Git
  スナップショットも使える。他のモードで別のソースを指定した場合は測定を開始しない
- `PLAYOUT_VARIANT`: 保存結果の案の名前
- `PLAYOUT_AV_SECONDS`: 1 ケースの秒数 (整数 2〜120)。`av` は既定 10 秒、`avRelay` は既定 20 秒
- `PLAYOUT_CASE_FILTER`: ケース名による絞り込み
- `PLAYOUT_RELAY_URI`: 実リレーの接続先
- `PLAYOUT_SERVER_CERTIFICATE_HASH`: 開発用証明書を使う実リレーの公開 SHA-256 ハッシュ (base64)

実行ごとの JSON、WAV、環境情報は調査ログに保存する。同名ケースの再実行では、実行ごとの
記録を残したうえで最新結果も更新する。ソースの Git リビジョンだけでは未コミットの候補を
特定できないため、選択した `src` 全体のファイル別 SHA-256 と一覧のハッシュ、計測
スクリプト、日本語の入力 WAV と manifest のハッシュも環境情報へ記録する。
`sourceRevision` は計測を実行する作業ツリーの HEAD であり、別の比較用ソースの
リビジョンを示さない。音源準備が現在の `src` を参照する場合は、そのハッシュも別に残す。
初期の案の比較はソースのコピーと案名で対応付け、後の実リレー計測では選択したソース自体の
ハッシュを記録するよう修正した。比較中にソースを変更して再読み込みを起こした結果は使わない。

日本語入力の準備は旧 DSP の比較から分離した。復号の件数、順序、フレーム長を検査し、
不足する音声を合成トーンで代替しない。実表示と音声に対応する A/V の組が十分にない
収録も正常な結果として保存しない。ケースごとに実行時間の上限を設け、ブラウザの起動や
終了が失敗した場合も計測用サーバーを解放する。実際のブラウザ起動失敗で、子プロセスが
残らないことも確認した。

## 残る限界

180 ms の途絶そのものを、常時 50〜100 ms の予算だけで消すことはできない。実装候補でも
その区間には約 169 ms の穴が残り、回復途中の音声遅延は 200 ms を超える場合がある。
100 ms は自動予算の上限であり、通信、復号、既存の予約、出力機器を含む実遅延の保証ではない。
catalog の明示下限と A/V の同期の補償も別に扱う。

Datagram の欠落では、補間で元の発話を復元できない。長い有声音の繰り返しや消音、
子音の消失は残る。PLC の品質と、実デバイスを使った日本語の聴取試験、外部機器での
リップシンク計測は引き続き必要である。
