# Chrome の音声の出力側補間と負荷の改善

記録日: 2026 年 10 月 31 日。

## 変更の目的

前回の [続き音による改善](CHROME_AUDIO_CONTINUATION_IMPROVEMENT.md) では、
繰り返す遅着に対する活動中の数値上の無音を抑えた一方、
正常到着でも毎回 100 ms の予測音を生成していた。
実 Chrome の投入処理の p95 は約 0.7〜1.1 ms であり、短縮判断の差も残った。
今回はその版を比較対象に固定し、出力の連続性と短い遅延を維持しながら、この負荷を取り除く。

## 出力側の実装

実音は AudioBufferSourceNode で予約し、Chrome の標準のレート変換を使う。
AudioWorklet は正常区間の PCM をそのまま通し、実際の未着時にだけ補間する。
入力側の 20 ms と描画量子の長さを同一視せず、実際に要求されたサンプル数で処理する。
末尾の実 PCM を 30 ms のリングバッファへ残し、有声成分の周期補間と非周期成分の線形予測を使い分ける。
予測の上限は 100 ms、実音への復帰のクロスフェードは 2 ms とする。
正常な受信ごとの予測音、取り消すための別バッファ、メインスレッドの補間履歴を削除した。

補間、実音への復帰、停止を同じ出力時計で判断する。
再生周期を作るメインスレッドのタイマーは使わない。
タイマーを使う待ちは、出力の準備と、既存の drain の完了確認だけである。
実音の位置や既定の目標 50 ms を補間のために後ろへ動かさない。
音声の破棄によって追いつく処理も追加しない。

[NetEq の GetAudio / Expand / Merge](https://webrtc.googlesource.com/src/+/031cc215615895d7ae039d4098c2716d7acf2dc3/modules/audio_coding/neteq/neteq_impl.cc)
にある、出力時に欠落を判断して補間し、実音へ戻す考え方を部分的に採用する。
これは上流全体の移植ではない。位置を相関で合わせる Merge、符号化パケットのバッファ、
コーデック内部の PLC / FEC、適応遅延制御の置き換えは含まない。

## 初回処理と数値演算の負荷

最初の出力側実装を Chrome のトレースで調べると、初回の欠落時に最大約 8.6 ms の処理があった。
128 サンプルの時間だけを目安にすると、44.1 kHz は約 2.90 ms、48 kHz は約 2.67 ms であり、
平均や p95 が小さいことだけでは締め切りを満たしたとは判断できない。

初回の解析、未着、復帰をモジュールの登録時に準備し、媒体の投入前に待つ。
この準備の信号は出力へ接続せず、再生する音声の履歴へも引き継がない。
また、非周期音の固定 12 次の積和は、小さい Wasm カーネルへ移した。
動的確保をせず固定領域を再利用し、返す PCM は別の所有配列へコピーする。
JavaScript と同じ順の浮動小数点演算を行い、積和融合による結果の変更も許さない。
予測の係数、励振の種、音量制約と減衰は変えない。

保存済みの実 Opus 復号 PCM 4,020 フレームから生成した 19,296,000 サンプルについて、
変更前の JavaScript と変更後の結果を実 Chrome で照合した。
最大サンプル差と不一致サンプル数はいずれも 0 だった。

通常の SDK ビルドには C コンパイラーを要求しない。
カーネルを変更するときは、wasm32 対応の LLVM clang を PLAYOUT_WASM_CC に指定し、
`vp exec node scripts/generate-audio-predictor-wasm.mjs` で同梱するバイト列を再生成する。
元の C ソースの SHA-256 を生成物へ記録する。
単一係数の減衰の解析解、固定領域の上限、結果の所有権も実 Wasm の単体テストで確認する。

## 計測で見つけて修正した問題

### 起動時の時計

高速化した初期化では、起動直後の暫定時計で最初の予約を固定し、
実出力時計が有効になった後も余分な遅延が残る例があった。
周期性のない音では時間圧縮が適用されず、wallClock の試験の遅延 p95 が 84.8〜85.6 ms に残った。
稼働中の Context の準備では、正の contextTime と performanceTime を持つ実出力時計を待つ。
修正後の同じ試験は 6 回とも成功し、p95 は約 50.9〜53.7 ms になった。
補間の質や時間圧縮のしきい値を変えて、この時計の問題を隠さない。

### 描画時計の一量子の遅れ

100 個の連続 source を実 OfflineAudioContext で描画する試験に、まれな振幅低下が残った。
計器を追加すると、隣接する process に同じ currentFrame が渡る例があった。
微小な正弦波を含む別入力でも確認し、入力 PCM は異なり、次の 128 サンプルへ進んでいた。
同じ入力の再処理だと仮定して出力を繰り返す対処は適切でない。

処理したサンプル数でもカーソルを進め、報告時計の一時的な遅れで再生位置を後退させないようにした。
時計が追いついた後も、正常区間の入力 PCM を変更しない。
修正を外すと失敗する回帰試験を追加し、実ブラウザーの連続音も 10 回再試験した。

確認した [Chromium の BaseAudioContext](https://chromium.googlesource.com/chromium/src/+/b2e94aa80b41a036f86ef7d0ca8d78563d98a73a/third_party/blink/renderer/modules/webaudio/base_audio_context.cc)
では、UpdateWorkletGlobalScopeOnRenderingThread の SetCurrentFrame はグラフのロックを取得できた場合に呼ぶ。
この実装は観測と整合するが、計測に使った Chrome の内部版を特定したものではない。

### 境界と初期化

- モノラルの後続予約で共有出力を先にモノラル化すると、先行する逆相ステレオが消えた。
  出力のチャンネル数を早期に減らさず、形式の変更は出力側で接続する。
- ネイティブのレート変換がバッファ外をゼロとして読まないよう、64 サンプルの端点の延長を置く。
  source は実音の終端で止め、延長を追加の音声として再生しない。
- 非有限 PCM と準備前の入力を、予約と時間軸の変更より先に拒否する。
- 停止の通知を繰り返しても、予測音の停止位置を延長して再開しない。
- モジュールの登録と制御の受理を、実プロセッサーからの応答で確認する。
  実時間より速い Offline の描画でも、固定時間の待ちで受理を推測しない。
- AudioContext / MediaStream を差し替える旧試験を削除し、実 Chrome のライフサイクル試験へ移した。

## 比較の条件

前回の最終ソースを SHA-256 `02c61e0e0c817193c4a83888483c5e70223bc96cf53c31d196140d610fb3f98c` に固定する。
現行 SDK、比較版、Chrome WebRTC に同一の Opus ペイロードを渡し、同じ出力時計で PCM を収録する。
Julius / Kyoko の日本語音声を各 6 秒、正常到着、0〜30 ms の遅着、繰り返す 60 ms の遅着、
44.1 / 48 kHz の出力で各 3 回、計 36 条件を順番に測定する。
保存したパケットの再復号、原音の独立描画、入力の同一性、測定中のソースの固定も検証する。

投入時の実時計に小さな差があると、時間圧縮の判断も変わり得る。
その影響と処理方式の変更を分けるため、実際の scheduler の全入力を保存する。
収録後に両版の実 scheduler と実時間圧縮へ、同じ保存 PCM と同じ時計を渡し、開始時刻と長さを照合する。
計測器のパケット照合では、大きな絶対時刻の 1 ULP に相当する約 0.24 µs の逆行も観測した。
許容幅は浮動小数点の隣接値の丸めだけとし、より大きい逆行は拒否する。
記録した配送時間の差分は丸めず、そのまま残す。
API の置換、偽の時計、代替デコーダーは使わない。
この照合は再生判断の検証であり、実時間の A/B で観測した差を取り消す根拠にはしない。

活動中の数値上の無音、局所相関による遅延、採用窓と未分類区間の定義は
[WebRTC との比較](CHROME_WEBRTC_PLAYOUT_COMPARISON.md) と同じである。
相関は雑音量や MOS を表さず、活動中の無音が 0 であることだけで、聴感上の音切れやギザギザが消えたとは判断しない。

## 実出力の underrun の確認

出力 PCM の無音だけでは、デバイスへ音を渡す締め切りを逃したことを判定できない。
Chrome 156 で公開される AudioContext.playbackStats も収録する。
約 1 秒の更新制限があるため、発声前に totalDuration の増加を確認し、発声後も新しい報告を取得してから停止する。
この差分から underrunEvents と underrunDuration を求める。初期化前の古い値を始点にしない。
当初の測定器ではトレース付きの 2 件が発話区間へ混ざったが、実トレースの位置は起動後約 15 ms、発話前だった。
初期化時の値と発声区間を分けて再収録し、生の前後の報告も残した。
未対応の環境は unsupported として残し、0 件へ置き換えない。

確認した [AudioPlaybackStats の実装](https://chromium.googlesource.com/chromium/src/+/b2e94aa80b41a036f86ef7d0ca8d78563d98a73a/third_party/blink/renderer/modules/webaudio/audio_playback_stats.cc)
では Duration の単位は秒であり、集計時に ms へ換算する。
共有する AudioContext 全体の値なので、複数の比較経路のどれに原因があるかを、この値だけで決めない。
Bluetooth の音響出力の録音や聴感の検証とも区別する。

## 識別と再実行

比較版のソースは保存したローカルスナップショットに固定する。

- 比較版: `02c61e0e0c817193c4a83888483c5e70223bc96cf53c31d196140d610fb3f98c`
- 計測した本体: `74494cc465c2c4f6e0e4fba461dc1344f5000dc9ba0518e226ffd9f24a4b94f5`
- 統計の型コメントを更新した最終ソース: `f9cd18e6e1d41bc4181ffdc3618db6fea093076ac6a89dfbbd48c87509fa98d5`

計測後の本体の変更は、AudioPlayoutTimingSnapshot の説明だけである。
SDK を再ビルドし、配布する JavaScript 11 ファイルすべての SHA-256 が計測版と一致することを確認した。
実行時のコードを変えず、旧予約計測と出力側の統計の意味を合わせた。

収録の識別子は次のとおり。

- `2026-10-31T09-26-16.020Z-56620-webrtc`
- `2026-10-31T09-29-05.470Z-56747-webrtc`
- `2026-10-31T09-31-54.822Z-56958-webrtc`

集計モジュールは `c4c4b40ef073729e407b0413e977acfca6a498c1f39040282f4eefb2e2543659`、
波形の照合は `471d1b825493c5ad7b504d21e783e1c0d4a963ec24ae3da34481aa03e00a0298`、
保存パケットの検査は `44e9549958c7a3e4649051481a0d5370933015dd9956361723528e6bac5860f1` に固定した。

再実行は investigate-playout-audio.mjs の webrtc モードを使う。
PLAYOUT_BROWSER_CHANNEL を chrome、PLAYOUT_AV_SECONDS を 6、PLAYOUT_COMPARE_SOURCE_ROOT を比較版へ設定し、
12 条件を 3 回、順に実行する。収録後に summarize-webrtc-playout.mjs へ各実行の保存先を渡す。
生の Float32 PCM、WAV、Opus ペイロード、実時計と予約、ソースと計測器のハッシュを保存する。

## 統計の意味と API の移行

低レベルの createMediaPlayout は、実 Context の resume の後、最初の pushAudio の前に prepareAudio を待つ。
出力を作り直したときも準備を待つ。SDK と DevTools はこの初期化を内部で行う。
利用手順は [高レベル API](HIGH_LEVEL_API.md#音声出力の準備) に記載する。

実際に描画した補間と、補間できなかった区間は AudioWorklet から非同期に通知される。
従来の「次の到着時または停止時に使用量を確定する値」と集計時点が異なる。
終端を明示しない測定では DTX や発話後の無送信期間も含む。
未補間区間のカウンター全体を、活動中の音切れの長さとは扱わない。
旧到着時予約の比較用メタデータを、現行出力の制御や補間実績に混ぜない。

## 検証と残る範囲

単体テスト・PBT 4,318 件と実 Chrome の再生 E2E 84 件が成功した。
production ビルドの E2E 12 件、フォーマット、lint、型検査、SDK と DevTools のビルドも成功した。
補助の波形測定器も実 Chrome で 100 条件を実行した。
実 PCM の透明性、メインスレッドの 60 ms の停止、低い声、レート変換、短いフレーム、
停止と再開、A/V 同期、チャンネル形式の変更、初期化失敗と無効入力を含む。

Bluetooth の実機の聴感と音響出力、長時間のドリフト、実回線の損失・順序逆転は、この比較の検証範囲外である。
今回の実リレー検証は、接続先の環境設定がないため実施していない。
100 ms の予測を超える途絶を保証するものでもない。
これらと NetEq 全体との差を残したまま、Chrome WebRTC と同等の音質を達成したとはしない。
