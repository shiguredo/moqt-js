# 音声再生の現状

更新日: 2026-10-29。現行実装 `86cdefe1` の再生経路、計器、確認済みの制約をまとめる。
公開 API の定義は [高レベル API](HIGH_LEVEL_API.md)、採用案の A/B と棄却した調整は
[A/V 再生の低遅延化の計測](AV_LOW_LATENCY_INVESTIGATION.md)、波形の修正は
[音声の出力波形の測定と改善](AUDIO_PLAYOUT_QUALITY_INVESTIGATION.md) を参照すること。

## 再生の仕組み

- 受信した音声 Object を復号し、`MediaPlayout` へ渡す。raw Opus の入力 `TIMESTAMP` は
  直接 / Worker の復号出力へ戻し、Datagram で失った媒体の位置を保持する
- 壁時計の `TIMESTAMP` を持つ音声と映像は、復号出力の到着から基準の遅れと揺らぎを求める。
  基準は直近 10 秒の最小値、揺らぎは別の直近 2 秒の分布を使う
- A/V を時間軸で揃える音声の自動予算は、到着の揺らぎと実出力時計の先行量の合計から
  通常 50〜100 ms に決める。`AudioDelayEstimator` と `AudioDelayFeedback` は削除した。
  穴や圧縮を理由に 160 ms へ上限を広げる制御は持たない
- 音声だけの購読と、時間軸を使わない再生は、到着基準の 50 ms の予算を使う。
  50 ms は常時の再生待ちの設定であり、通信、復号、既存の予約、出力機器を含む遅延の保証ではない
- 遅れた音は波形の周期性を使って圧縮し、欠落は圧縮前の履歴から補間する。
  A/V の目標時刻を使う予約では、圧縮の不感帯を最初の 2 秒は 20 ms に保ち、その後は
  到着の揺らぎに応じて 5〜20 ms にする。到着基準の予約の不感帯は 20 ms のまま使う
- 補間と実音はクロスフェードで接続する。開始と途絶には `GainNode` のフェードを使い、
  後続が届いたら途絶用のフェードを取り消す。通常のフレーム境界へ周期的なフェードを入れない
- A/V 同期は先行する側を不感帯 5 ms まで合わせる。時計の基準の差の補償は 100 ms までで、
  既知のバッファ差と出力の残差は別に補償する。基準を共有できる間は現在の必要量を引き直し、
  過去の共有表示時刻を下限として保持しない。予約の残差の 250 ms の平滑化は維持する
- 復号器が遅れ続けた場合は `AudioReceiveCatchUp` が再構築の必要を通知する。
  媒体の欠落の補間と、復号の遅れからの追いつきは別の処理である
- 再生の `AudioContext` は復号フレームのレートへ合わせる。Chromium の Opus は 48 kHz で
  復号されるため、Catalog の `samplerate` が 44100 でも 48 kHz で再生する

catalog の `targetLatency` は、A/V と映像の表示待ちの明示下限として別に扱う。
音声だけの再生は到着基準の予算を優先する。`preDecodeDelayMs` による意図した保持も別であり、
自動予算が 50 ms であることと、配送全体が 50 ms で完了することは同じではない。

## パケット欠落と冗長化

音声の配送は既定で Datagram。`AudioPublishOptions.redundancy` で同じ Object を 1〜3 回送り、
受信側が同じ識別子の 2 回目以降を捨てる。ライブラリの既定は 1、devtools の既定は 2 である。
Subgroup 配送では冗長度 2 以上を指定できず、`start()` がエラーになる。

独立損失では複数コピーが有効だが、同じ Group の全コピーが連続して失われる条件は防げない。
補間は波形を作る処理であり、失った発話の内容を復元する処理ではない。
間隔を空けた冗長送信や FEC は実装していない。

## 計器の読み方

次の表の値は `MediaPlayout.getStats()` から読む。自動予算と、実際の待ちを分けて確認する。

| 計器                                                       | 意味                                                                        |
| ---------------------------------------------------------- | --------------------------------------------------------------------------- |
| `audio.delay.jitterMs`                                     | 到着の揺らぎの百分位。未観測なら null                                       |
| `audio.delay.outputLeadMs`                                 | 有効な出力時計で観測した、予約できる最早位置の先行量の p95。未観測なら null |
| `audio.delay.targetMs`                                     | 音声に適用した自動予算。catalog の明示下限と A/V 同期の補償は含まない       |
| `audio.timing.startDelayMs`                                | 復号出力の到着から予約の開始までの分布                                      |
| `audio.timing.gapMs` / `audio.timing.boundaryStepMax`      | 補間で埋まらない穴の累積と、バッファ境界の最大段差                          |
| `audio.compressedMs` / `audio.concealedMs`                 | 圧縮した長さと補間した長さの累積                                            |
| `avSync.delays.audio` / `avSync.delays.video`              | 基準の遅れ、自分の予算、同期が足した待ち、表示遅延の内訳                    |
| `avSync.delays.audioDelay`                                 | 時間軸が推定した予算。音声に適用した予算は `audio.delay` で確認する         |
| `avSync.delays.audioPlayoutCorrectionMs` / `avSync.skewMs` | 音声の予約の残差と、予約 / 表示の同期ずれ                                   |

`MediaSubscriber` の `getStats()` は音声の計器を `audio.playoutTiming`、加工量を
`audio.playoutCompressedMs` / `audio.playoutConcealedMs` として返し、A/V の内訳は `avSync.delays` に持つ。
`MediaPlayout` の `audio.delay` を、そのまま `MediaSubscriber` のフィールドとして扱わないこと。
devtools の表示用スナップショットでは音声の予算は `audio.audioDelay` にある。
旧統計からの移行は [高レベル API](HIGH_LEVEL_API.md#旧音声遅延制御からの移行) を参照すること。

## 確認した結果

制御した到着列は日本語の実音声を実 Opus へ通し、`AudioContext` の予約と canvas の描画を
記録した。実リレーでは Worker の符号化 / 復号と QUIC Datagram を通した。

| 条件                            | 音声の結果                                | 映像の結果                    |
| ------------------------------- | ----------------------------------------- | ----------------------------- |
| 180 ms の停滞が去った後         | 末尾の遅延 p95 は約 188 ms から 70〜73 ms | 約 188〜193 ms から 77〜81 ms |
| 映像だけを 3 秒間遅らせる       | 末尾 2 秒の p95 は再実行で 72.1〜101.7 ms | 90.2〜107.4 ms                |
| 実 Datagram の 3 Group 連続欠落 | 媒体遅延 p95 は約 129 ms から 72 ms       | 約 134 ms から 69 ms          |

連続欠落の実リレー計測では、穴の累積が約 1,032 ms から 1,242 ms に増えた。
低い予算では事後に補間を予約できる区間が短くなる交換条件がある。独立欠落の 1 条件では
出力の最大段差 0.0783 が入力の比較値 0.0741 を上回った。音声の追加破棄は 0 だったが、
全条件での無雑音や品質の非劣性を確認したものではない。

2026-10-29 の実装時点では、単体テスト / PBT 4,266 件、Chromium E2E 190 件、
配布用ビルド E2E 10 件が成功し、CI の実リレー検証も成功した。計測条件、集計区間、
正常完了した試行間の変動は [A/V の計測報告](AV_LOW_LATENCY_INVESTIGATION.md) に残す。

## 残る制約

- 常時 100 ms 未満と完全な無雑音は未達。長い途絶や非周期音の内容は補間で戻せない
- ブラウザ内の音声予約と描画を測った値であり、スピーカーの音響出力と画面の発光を測った
  物理的なリップシンクではない。規格の許容値を満たしたという判定にも使わない
- 実 QUIC の追加損失は受信後、重複排除と復号の前で注入した。回線上の損失による
  輻輳制御の変化は再現していない
- 予約できる最早位置を過ぎた穴は事後には埋められない。`boundaryStepMax` には正常な発話の
  大きな変化も入るため、クリックの有無は局所の波形と合わせて確認する
- 受信 `TIMESTAMP` が 17.299 ms / 22.701 ms 刻みになる区間も観測した。送信時刻と capture の
  追跡、および局所の波形の照合は未完了である
- 44.1 kHz と 48 kHz の不一致は実 API で再現と計器の検証をしたが、実機での聴感、
  Bluetooth の経路、低性能端末の処理負荷は未検証である
- 停止時の drain は `stop` で最大 300 ms、`close` とピア起点の `close` で最大 150 ms。
  残った音は計器へ記録して打ち切るため、任意の長さの末尾を鳴らし切る保証ではない

旧上限 160 ms、音声だけの 140 ms の下限、穴による上限拡大の測定は、
[過去の遅延調査](AUDIO_PLAYOUT_LATENCY.md) と
[過去の無音の穴と末尾の調査](AUDIO_PLAYOUT_GAPS_AND_TAIL.md) に保存している。
