# 音声と映像の再生

再生の設定と現在の制約をまとめる。
過去の測定値は [調査記録](archive/README.md#再生)、API の型と所有権は
[再生 API (MediaPlayout)](MEDIA_PLAYOUT.md) を参照すること。
フレーム境界の波形破損と再欠落への対応は [2026-11-06 の見直し](PLAYOUT_AUDIO_REVIEW.md) にまとめた。

## 再生する経路

`createMediaSubscriber` は受信、復号、再生を内部で組み立て、音声と映像を MediaStream として出力する。
Object の受信と WebCodecs の復号を自分で組み立てる場合は、`createMediaPlayout` に
復号済みの AudioData / VideoFrame を渡す。両方とも同じ時間軸と再生の実装を使う。

```text
受信した Object → 任意の復号前遅延 → WebCodecs → MediaPlayout
                                                   ├─ 音声の予約 → AudioWorklet → 出力
                                                   └─ 映像の表示待ち → 描画 / MediaStream
```

DevTools の音声は AudioContext の出力機器へ直接接続する。高レベル API の音声は
MediaStream として返すため、アプリケーションが接続する audio 要素などの出力も確認する。

復号前に TIMESTAMP の種類と Object の位置を記録する。復号の出力だけでは、壁時計、
媒体時刻、時刻なしを判定できず、Object の位置も取得できないためである。
raw Opus の入力時刻は直接復号と Worker 復号の出力へ戻し、パケット欠落による媒体時刻の跳びを保つ。

## 遅延の予算

| 対象                            | 現在の決め方                                                          |
| ------------------------------- | --------------------------------------------------------------------- |
| 時計と経路の基準                | 壁時計の TIMESTAMP と復号出力の到着の差から、直近 10 秒の最小値を使う |
| 到着の揺らぎ                    | 初期の追いつきとまとめた復号を除き、直近 2 秒の分布を使う             |
| A/V の音声の自動予算            | 揺らぎと実出力時計の先行量を合わせ、通常 50〜100 ms に収める          |
| 音声だけ / 時間軸を使わない再生 | 到着基準の目標を 50 ms にする                                         |
| catalog の `targetLatency`      | A/V と映像の表示遅延の明示下限として扱う                              |
| 購読側の `preDecodeDelayMs`     | 圧縮済み Object を復号前に保持する追加遅延として扱う                  |

50 ms は自動予算の設定であり、通信、符号化、復号、同期の補償、出力機器までを含む
実遅延の上限ではない。`targetLatency`、復号前遅延、音声の出力先行量も別に読む。
意図した保持の API と上限は [購読側の再生遅延](PLAYOUT_DELAY.md) にある。

AudioContext の currentTime は、実際に鳴る位置より先に進む。予約時は
`getOutputTimestamp()` と performance.now() の対応を使い、その先行量を二重に足さない。
出力時計が未確立の間は currentTime で代用し、代用値を実出力の観測として学習しない。

## 音切れからの回復

遅着した音は、遅れたという理由だけでは捨てない。予約の順序と連続性を保ち、余分に溜まった
分を波形の周期性を使って時間圧縮する。圧縮できる量は遅れ、音の長さ、予約の余裕で制限し、
実際に削れた量だけを後続の予約へ反映する。周期性が弱い音は無理に圧縮しない。

到着基準の予約が遅着で浅くなった場合は、届いた音を最も早い時刻で再開する。
再開時に目標の待ちを足して穴を延ばさず、後続の適用可能な音を時間伸長して深さを戻す。
通常の揺らぎだけで伸長を始めることはない。伸長できる波形が無い間は浅い状態が続く。

未着の間の補間は、出力側の AudioWorklet が実際の欠落を見て生成する。
実音の PCM と予約位置は同じメッセージで渡し、制御だけが先に届く経路を作らない。
出力サンプルの位置から入力 PCM を読み、連続する次フレームの先頭も線形補間に使う。
入力と出力のレートが同じ場合も端数の開始位置を保ち、通常のフレーム境界で位相を取り直さない。
欠落時だけ最大 100 ms の続き音を作る。
実音へ戻るときと停止時は短く接続する。通常のフレーム境界ごとにはフェードを入れない。
補間は波形を作る処理であり、失った発話の内容を復元する処理ではない。

NetEq からは、出力側の未着判定、Expand / Merge の考え方、Accelerate、
PreemptiveExpand の周期の重ね合わせを部分的に採用している。
上流全体の移植やビット一致ではなく、コーデック内部の PLC / FEC と同等でもない。
採用の判断と未完了の範囲は [A/V 同期と再生の判断](AV_SYNC_DECISIONS.md) にまとめている。

復号器自体に音が溜まった場合は、音声を再生段で捨てても復号器の待ちは減らない。
`AudioReceiveCatchUp` が入力の遅れと意図した保持を差し引いて復号の詰まりを判定し、
呼び出し側へ復号器の再構築を通知する。補間と復号器の追いつきは別の処理である。

## 映像と同期

基準を共有できる間は、音声と映像の現在の表示時刻から先行側の待ちを決め直す。
不感帯は 5 ms、時計の基準の差の補償は最大 100 ms とし、既知のバッファ差と出力の残差は
別に補償する。過去の共有表示時刻を下限として保持しない。
基準を共有できない間は、音声の新鮮な実予約深さを映像の合わせ先に使う。

映像の学習分布が上限超過の観測だけになった場合は、空の分布を正常な 0 ms とみなさず、
直前の学習値を現在のキュー上限の範囲で保持する。
decoder の復旧と再構成では購読位置を保ち、次のキーフレームを待つ。
同じ timestamp の複数出力は入力順で対応づけ、復旧で破棄した未出力の対応は消す。

## 欠落と冗長化

音声は既定で Datagram を使い、`AudioPublishOptions.redundancy` で同じ Object を
1〜3 回送る。受信側は同じ Group ID / Object ID の 2 回目以降を捨てる。
ライブラリの既定は 1、DevTools の既定は 2 である。
Subgroup 配送では冗長度 2 以上を指定できない。

全コピーが失われる連続欠落は、この重複送信だけでは防げない。
FEC と時間を空けた冗長送信は未実装であり、[検討中の設計](proposals/AUDIO_FEC.md) として分けている。

## 準備と停止

再生 API を直接使う場合は、最初の pushAudio より前に `prepareAudio()` の完了を待つ。
AudioContext や再生の入口を作り直した場合も準備が必要である。
再生開始、出力切替、購読の停止が重なった場合は、古い非同期処理の完了で新しい出力を変更しない。

停止時の `drainAudio()` は、壁時計だけでなく実出力位置と予約終端の描画を確認する。
通常の停止は最大 300 ms、終端の close は最大 150 ms 待ち、残りを「切った量」として記録する。
任意の長さの予約を鳴らし切る保証ではない。
所有権と正確な呼び出し順は [再生 API のライフサイクル](MEDIA_PLAYOUT.md#ライフサイクル) を参照すること。

## 計器と既知の制約

自動予算は `MediaPlayout.getStats().audio.delay`、実際の予約待ちと欠落は `audio.timing`、
同期の内訳は `avSync.delays` で確認する。MediaSubscriber では予約の計器を
`audio.playoutTiming`、DevTools のスナップショットでは自動予算を `audio.audioDelay` で読む。
同じ階層のフィールドとして扱わない。

長い停滞の穴、Bluetooth の無線区間、スピーカーとディスプレイを含む物理的な遅延は、
ブラウザー内の計器だけでは解消も確認もできない。常時 100 ms 未満と完全な無雑音は未達である。
切り分けは [音声再生の診断](AUDIO_GLITCH_CAUSES.md)、測定の採否は
[再生の計測](PLAYOUT_MEASUREMENT.md) を参照すること。
