# DevTools の実出力経路と A/V 遅延

2026-10-29、マイクとカメラを使った実機で「音質は改善したが、約 500 ms 遅れる」という
報告を受けた。音質処理を維持し、出力経路の余分な待ちを減らす変更と計測の記録である。

## 利用者の統計から確認できた待ち

同じ購読の 2 回の統計では、次の値が記録されていた。遅延は終了時点の窓の p95、
outputLeadMs と同期ずれはコピー時点の値である。全観測の p95 と混同しない。

| 項目                   | 最初の統計 | 後の統計 |
| ---------------------- | ---------: | -------: |
| 音声の受信後の再生待ち |   278.7 ms | 203.9 ms |
| 音声の outputLeadMs    |   195.6 ms | 195.9 ms |
| 映像の到着遅延         |    72.2 ms |  68.5 ms |
| 映像の復号時間         |     3.7 ms |   3.8 ms |
| 映像の表示待ち         |   277.6 ms | 202.4 ms |
| 映像の表示遅延         |   326.6 ms | 249.8 ms |
| 内部の同期ずれ         |    -2.7 ms |   5.3 ms |

後の統計では、音声の基準 40.4 ms、再生予算 100 ms、再生の残差補償 107.1 ms に対し、
映像に 164.2 ms の同期用の待ちを加えていた。到着と復号よりも、受信後の待ちが大きい。
ただし、この統計だけで体感の約 500 ms 全体を説明したとは扱わない。

## 出力経路の変更

旧 DevTools は、予約した音を MediaStream にして別の audio 要素で再生していた。
Context の出力時計を使う予約の後に、もう一つの再生経路が入り、そのバッファは
Context の予約時刻だけでは計測できなかった。出力デバイスを選んだ場合も、Context と
audio 要素が異なるデバイスを使い得る構成だった。

現在は Context の destination へ直接出し、出力デバイスも同じ Context の setSinkId で選ぶ。
再生の開始、停止、購読の再作成では、これまでと同様に予約と時計の対応を取り直す。
非対応のブラウザでは既定出力を使え、明示した出力機器を選べない場合はエラーにする。
選んだ機器を黙って無視しない。

機器の切り替えに失敗した場合は再生を無効にして出力だけを閉じ、購読と復号の接続は保つ。
復号前遅延を 500 ms に設定した実購読で、存在しない機器の選択を実ブラウザに拒否させ、
既定出力に戻して再生を有効にすると音声の復号と再生、映像の表示が再び進むことを検証する。
既に再生している途中の変更と、再生開始時の機器選択の両方を対象にする。
購読停止用の処理を呼んでいた変更前の失敗処理では、この条件で音声が復帰しなかった。

復号レートに合わせる設定と、圧縮、補間、接続のフェードは変更していない。
ライブラリの MediaStream を返す API も変更していない。

## 出力の計器

旧 audio 要素の waiting / stalled / error の計器を削除し、次の値を表示とコピーへ追加した。

- baseLatencyMs: Context から出力システムへ渡すまでの処理遅延
- outputLatencyMs: ブラウザが報告する出力機器の推定遅延。未対応または未再生なら null

機器の推定値は running になった直後にも更新されるため、購読中は統計の周期で読み直す。
先に再生を有効にしてから購読した場合も、稼働中の Context の値を消さない。
これらは音響ループバックの実測値ではない。outputLeadMs は予約できる最早時刻までの
先行量であり、outputLatencyMs と同じ意味ではない。

## 実波形での出力経路の比較

同じ設定の Context、48 kHz、同じ振幅 0.3 のサンプルを使い、Worklet が波形を受け取る位置を測った。
MediaStream と audio 要素の captureStream を経由する経路では約 20.7 ms、直接つなぐ経路では
0 ms の差だった。両方の検出振幅は 0.300000012 だった。

これはブラウザ内の波形の受け渡しの比較であり、スピーカーや Bluetooth の物理遅延ではない。
この 20.7 ms を利用者の約 500 ms の原因全体としたり、別環境の改善量へ置き換えたりしない。

## 実 DevTools と実 QUIC での計測

合成音と canvas、日本語 Julius の実 AudioBuffer と canvas を実 QUIC で配信し、実 DevTools の
購読・再生・表示を各 20 秒観測した。偽のマイク・カメラや API の置き換えは使っていない。
日本語音源の配信には公開の publisher API を使い、受信側は UI の実際の再生経路を通した。

終了時点の窓の統計、未処理例外、再生件数とソースのハッシュを実行ごとに保存する。
音声の受信後の待ちと、媒体時刻からの映像の表示遅延は異なる区間の値である。
そのまま音声と映像の総遅延として比較したり、別の分位点を足したりしない。

Chromium 156.0.8078.4 の最終試行は次の値だった。音声と映像を途中で捨てて低遅延に
見せないよう、再生と表示の件数も記録した。未処理のページ例外は両方とも 0 件である。

| 入力                    | 音声の受信後の待ち p95 | 映像の表示遅延 p95 | 終了時の内部同期ずれ | 再生 / 表示フレーム |
| ----------------------- | ---------------------: | -----------------: | -------------------: | ------------------: |
| 合成音と canvas         |                75.2 ms |           121.6 ms |             -0.24 ms |         1,027 / 616 |
| 日本語 Julius と canvas |                92.5 ms |           150.2 ms |             -0.44 ms |         1,047 / 633 |

出力システムの処理遅延は 5.3 ms、機器の推定遅延は 32 ms と報告された。
直前の正常な試行も保存しており、日本語の映像 p95 は約 118〜150 ms と実行間で変わった。
合成音の配信は DevTools 自身、日本語の配信は 320×180 / 30 fps の VP8 と Opus Datagram である。

既存の実 AudioContext と canvas の A/V 計測でも、日本語、音声 5 % 欠落、180 ms の
到着停滞、揺らぎ、映像の段差を含む 7 条件を再実行した。全条件で採用条件を満たし、
音声の再生側の破棄と未処理例外は 0 件だった。この試行の出力の最大隣接段差は、
各入力の最大隣接段差を上回っていない。ただし途絶した発話の内容を復元できたという
意味ではなく、音声 5 % 欠落では約 312 ms の未回復の穴が残った。

手元の修正前の環境では、音声の受信後の待ち p95 が約 73 ms、映像の表示遅延 p95 が
約 118 ms であり、利用者の約 500 ms は再現していない。別の試行との差を出力変更による
改善量とは扱わない。実機で 100〜200 ms 前後に収まるかは、更新後の同じ機器と接続条件で
確認する必要がある。

## 無音時の映像の進行

2026-10-30、マイクが無音だと映像が止まり、話すと動くという報告を追加で調べた。
映像の復号と表示周期には、音声の振幅や発話を開始条件とする判定はない。
ただし、コードの確認だけでは停止の不具合を否定できないため、実 DevTools の配信と購読を
実 QUIC リレーへ接続して確認した。

Chrome 156.0.8078.74 の実ウィンドウで、VP9、1280×720、30 fps、キーフレーム間隔 10 秒を使った。
音声は実 Web Audio の合成音、映像は動く canvas である。音声トラックの `enabled` を変更して
無音と有音を切り替え、`stop()` で途絶も作った。API の置き換えや偽のマイクは使っていない。

| 音声の状態       | 音声再生 | 観測時間 | 表示フレーム | 平均表示 fps |
| ---------------- | -------- | -------: | -----------: | -----------: |
| 音声トラックなし | OFF      |  6.12 秒 |          183 |         29.9 |
| 音声トラックなし | ON       |  6.11 秒 |          182 |         29.8 |
| 無音             | ON       |  6.15 秒 |          181 |         29.4 |
| 有音へ復帰       | ON       |  6.10 秒 |          183 |         30.0 |
| 再び無音         | ON       |  6.11 秒 |          183 |         30.0 |
| 音声トラック停止 | ON       |  6.11 秒 |          184 |         30.1 |
| 音声トラック停止 | OFF      |  6.11 秒 |          183 |         29.9 |

各条件を 500 ms 間隔で読み、すべての区間で映像の送信、受信、復号呼び出し、表示が
15 fps 以上進み、canvas の画素も更新された。復号エラーは全条件で 0 件だった。
最初の無音区間の復号後のピークは約 -100〜-92.6 dBFS、有音へ復帰した区間は約
-14.0〜-10.4 dBFS であり、音声の切り替えも成立している。

この測定では無音に依存する停止は再現していない。実際のマイクとカメラを使う既存実装の
ページでは復号エラーの蓄積も観測されており、音声の有無との因果関係はまだ決まっていない。
合成入力での成功を、報告された実機の停止の解消として扱わない。

追加の停止ログから調べた送信前の破棄と復号失敗後の復旧は、
[映像停止の調査](VIDEO_FREEZE_INVESTIGATION.md) に記録している。

## 再現

investigate-devtools-latency.mjs を実行する。接続先は PLAYOUT_RELAY_URI、音源は
PLAYOUT_SPEECH_SOURCE (tone / julius / kyoko / eddy / grandpa)、観測秒数は
PLAYOUT_AV_SECONDS (整数 10〜120、既定 20) で指定する。PLAYOUT_HEADED=1 で実ウィンドウを使う。
日本語の音源は既存の prepare-playout-japanese.mjs で事前に用意する。

生データには接続先を保存しない。音源、処理コードのハッシュ、出力経路の実波形比較、
統計の時系列を残す。音声の再生件数と映像の表示件数を満たさない場合、または未処理の
ページ例外がある場合は、正常な測定として扱わない。

2026-10-30、起動中の累積件数だけでは、その後の停止を見逃すことを確認し、判定を見直した。
計測の開始と終了の差分で再生と表示のレートを確かめ、各 500 ms の区間で両方が進むことを
要求する。非表示のページ、復号エラー、観測間隔が 1.5 秒以上に伸びた試行も採用しない。
起動に失敗した場合は、無効な Stop ボタンを待って元のエラーを隠さない。

連続波形の収録にも、現在の直接出力から AudioWorklet へ分岐する経路を使う。
元の出力は保ち、計測の分岐の gain を 0 にする。MediaStream と audio 要素を再び挟まない。
ネットワークを通さない振幅 0.25 の対照音でも、実サンプルの長さと振幅を確認する。

出力時計と機器遅延の意味は [Web Audio API](https://webaudio.github.io/web-audio-api/#dom-audiocontext-getoutputtimestamp)
に従う。仕様は策定中であり、ブラウザの対応状況や値の精度は変わり得る。
