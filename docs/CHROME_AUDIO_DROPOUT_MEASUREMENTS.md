# Chrome の音声の途切れと予約期限の計測

記録日: 2026-10-31

再生方式の変更を選ぶ前に、予約上の空白と実際の出力を照合した。
今回追加したのは計測コードであり、前回の時間圧縮の修正を含む再生コードは固定した。
Bluetooth 機器を通した音響測定ではない。

## 何を検証したか

保存した同じ Opus 復号 PCM と要求到着列を再利用し、Chrome の実 AudioContext で再生した。
入力は日本語の Julius と Kyoko で、各 335 フレーム、1 フレームは 20 ms、48 kHz の mono である。
正常到着、0〜30 ms の遅着、繰り返す 60 ms の遅着を含む 4 種類の保存済み記録を使った。

要求到着時刻は同じでも、実時間での投入時刻と出力時計は反復ごとに変動する。
投入時刻の誤差を全フレームで保存し、同じ到着を完全に再現したとは扱わない。
さらに、実スケジューラーへ採取した時計、入力と確定した伸縮量を戻し、判断を再現できるか検査した。

音声のみの再生と、音声と映像を同期する再生を分けた。
同期ありの対照条件では、映像は規則的な 30 fps の到着列を生成し、実 VideoFrame を実 canvas へ描画した。
音声の到着列は保存した実測を使う。映像の到着も実回線から記録した条件ではない。

## 録音を信用するための照合

再生の実メソッドへ必ず委譲する記録処理を付け、次の情報を採取した。

- 予約判断に渡った時計、媒体時刻、到着の基準と目標
- 時間圧縮と補間の要求、実際に適用した長さ
- 実 AudioBuffer の PCM、開始、終了と envelope
- 補間関数の呼び出しと生成結果
- 実際の投入時刻と処理時間

同じ Worklet に、入力の照合信号、SDK の出力、予約区間を示す独立した信号、
復号 PCM の参照再生とその予約信号を収録した。予約信号は各バッファと同じ区間だけ 1 を出す。
これにより、発話が元から静かな区間と、再生するバッファがなかった区間を区別した。
参照再生だけには 200 ms の余裕を置いた。SDK の再生予算に追加した値ではない。

採取したバッファと実際に適用された envelope を、独立した実 OfflineAudioContext でも再生した。
SDK の出力、参照再生、入力の照合信号をそれぞれ全サンプルで比較した。
この照合は録音経路の整合性を検証する。聴感の品質評価は別に必要である。

収録の連番、Worklet の例外、ページ例外、収録範囲、予約信号の内部の不一致も採否へ反映した。
予約信号の境界の前後 2 サンプルは量子化の比較から分け、その数を残した。
SDK の PCM の比較は、境界を含む全サンプルを対象とした。
currentFrame の重複は別の計器に残し、独立した連番と PCM の照合で収録の欠落と区別した。

PCM16 へ量子化する前の Float32 で分析し、試聴用の PCM16 WAV と、mono の little endian Float32 も保存した。
測定中のソース変更、無効な保存記録、長さの違う PCM と非有限のサンプルは正常結果として採用しない。

## 空白を区別する基準

予約上の空白は、次の 3 区間へ分けた。

1. 次のバッファを予約する処理の時点ですでに過去の区間
2. その時点から 10 ms の予約余裕の範囲にある区間
3. 予約余裕の先にも残っている区間

10 ms は今回固定した AudioPlayoutScheduler の値である。
補間生成やコピーの前の時計と、実バッファの接続時の時計も残し、処理中の時計の進みを分けた。
AudioContext の時計は量子単位で進むため、その差をそのまま CPU の処理時間とは扱わない。

空白の前後の元の復号フレームの RMS も調べた。
少なくとも片方が -60 dBFS を超える場合を数値上の活動区間として集計した。
これは音声活動検出器でも、聞き取れる音切れの判定でもない。
静かな区間の予約空白を、そのまま発話中の音切れの量にしないための補助的な分類である。

## 計測結果

Google Chrome 156.0.8078.79 / macOS arm64 で、4 種類の入力記録を各レートで 3 回ずつ、
音声のみと同期ありの計 48 条件で測った。合計 16,080 フレームである。
48 条件すべてが採否の条件を満たした。

SDK の PCM、参照 PCM と照合信号の再レンダリング誤差は、全条件で最大値 0 だった。
予約信号の内部の不一致、空白の内側の非ゼロサンプル、実スケジューラーの判断の再現失敗はすべて 0 件だった。
予約区間から算出した累積の空白と、出力の予約信号から数えた空白の差は最大約 0.074 ms だった。
差にはバッファの開始と終了のサンプルへの量子化が含まれる。

表の範囲は 44.1 / 48 kHz と各 3 回の反復の最小値から最大値を示す。

スピーカーやイヤホンまでの音響的な遅延ではない。

正常到着の小さな空白の隣接 PCM は、数値上の活動区間に入らなかった。

音声のみの Julius の長い遅着では、約 109〜122 ms が予約の接続時点ですでに過去で、

同期ありの短い遅着では、予約余裕の先にも最大約 4.4 ms が残り、補間の生成を断った記録があった。

同期ありの長い遅着では、既存の制御の最終予算は 100 ms に達している。

## 観測から分かったこと

音声のみの短い遅着の反復では、補間関数の呼び出しは 0 回だった。
空白は予約余裕の範囲内にあり、実出力の内側の PCM も 0 だった。
これらを、周期性の解析が失敗した例や、すべての区間がすでに過去だった例として説明できない。

具体例では、予約判断とバッファの接続時の時計は 1.904000 秒だった。
前の音の終了は 1.913376 秒、次の音の開始は 1.914000 秒であり、
約 0.624 ms の予約空白が残った。この時点で、前の音の終了までは約 9.376 ms あった。
スケジューラーの補間要求は 0 秒で、補間関数は呼ばれていなかった。
隣接する元の PCM の RMS の大きい方は約 0.0498 だった。

音声のみの長い遅着では、すでに過去の空白と予約余裕内の空白の両方が残った。
短い空白と長い空白を同じ原因として扱うと、修正の対象を誤る。
また、正常到着で一部の反復に現れた小さな予約空白は、発話前のほぼ無音の区間だった。

10 ms の余裕に入る区間があることから、その全量を安全に埋められるとは結論しない。
実際の処理中に出力時計が進むことや、補間の接続で別の雑音を加える可能性も検証が必要である。
一定周期で取り出す方式への変更が必須だという判断も、今回の結果だけでは行わない。

## 検証と再実行

計測器の検証では、原音の無音、途中の収録欠落、重複する予約、収録範囲外の予約、
異なる長さの PCM、非有限値と壊れた入力記録を扱う試験を先に追加した。
モックやスタブは使っていない。
単体テストと PBT は 4,300 件成功し、vp check と型検査も成功した。

保存済みの有効な WebRTC 比較記録を PLAYOUT_AUDIO_TRACE_FILE に指定し、
investigate-playout-audio.mjs の deadlines モードを使う。
PLAYOUT_BROWSER_CHANNEL は chrome、PLAYOUT_REPEAT_COUNT は 3 とする。
出力レートは 44.1 / 48 kHz の両方を測定する。
元の入力記録と実行記録を summarize-playout-deadlines.mjs に渡すと、入力ハッシュと結果の件数を検査して集計できる。
別の音源を指定した場合や、反復が未完了の場合は失敗する。
音声と映像の同期を使う場合は、さらに PLAYOUT_DEADLINE_AV を 1 にする。

実時間の測定は同時に走らせず、他のビルドや全テストとも並行させなかった。
ソース、計測コードと入力記録の SHA-256 を実行ごとに残した。

## 次に確かめる対象

その後の採用方針は [Chrome の音声再生への NetEq の採用](NETEQ_PLAYOUT_ADOPTION.md) に記録した。
独自方式の優位性は未確認のため、NetEq の仕組みを基準とする。
低遅延と雑音の削減を同時に検証し、バッファの増加だけで空白を減らした結果とは分ける。

予約余裕内の空白、すでに過去の空白と、補間を生成できなかった空白を別の回帰条件にする。
修正候補の評価でも、同じ入力を使って空白、波形の接続と遅延を同時に計測する。
補間した長さや予約空白の減少だけを、音質改善の証拠にはしない。

この測定は復号後の playout を対象とする。
WebTransport / QUIC のパケット損失、順序逆転、デコーダーに滞留する音声、
Bluetooth 機器の実出力経路は別途確認が必要である。
