# Chrome の音声再生への NetEq の採用

## 判断

2026 年 10 月 31 日時点で、独自方式が NetEq より優れているという測定結果はない。
低遅延と雑音の削減を同時に満たす基準として、NetEq の仕組みを採用する。
独自の処理を残す場合は、同じ入力と同程度の実出力遅延で、その処理の利点を検証する。
予約空白だけを減らした結果や、バッファを増やした結果を音質の優位性として扱わない。

これは採用する方式の判断であり、現行 SDK が NetEq と同等の再生を実装済みという意味ではない。
比較を先に進めた後、未着時の出力と実音への復帰に着手した。
当初の実装と再計測は CHROME_AUDIO_CONTINUATION_IMPROVEMENT.md に、
出力側への移行と負荷削減は [AudioWorklet での改善](CHROME_AUDIO_RENDERER_IMPROVEMENT.md) に記録する。

## 部分的に採用した仕組み

AudioWorklet が出力時計で実際の未着を判断し、必要なときだけ最大 100 ms の続き音を生成する。
正常区間は Chrome の標準レート変換後の PCM をそのまま通す。
次の到着やメインスレッドのタイマーを待たず、既定の目標 50 ms を増やさない。
当初の「正常到着のたびに続き音を準備し、後で取り消す」経路とメインスレッドの補間履歴は削除した。

続き音は周期の確かさに応じて周期補間と線形予測による非周期音の合成を使い分ける。
実音への復帰は短いクロスフェードで行う。
これは Expand / Merge の考え方の一部を採用したもので、上流とビット一致する移植ではない。
実音の位置を相関で合わせる Merge、符号化済みパケットからの再生判断、
コーデック内部の PLC / FEC、適応遅延制御の置き換えは未完了である。

## 確認した上流実装

WebRTC のコミット `031cc215615895d7ae039d4098c2716d7acf2dc3` を固定して確認した。
以下の説明は、この版に対するものである。計測に使用した Chrome 内部の WebRTC の版と同一とは限らない。
表の SDK は、続き音を準備する改善前の比較対象である。

| 仕組み           | 上流の実装                                                                         | 改善前の SDK との差                                                        |
| ---------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 到着と再生の分離 | `InsertPacket` で符号化済みパケットを保存し、`GetAudio` で 10 ms の音声を取り出す  | 復号済み PCM が到着すると、その場で次の `AudioBufferSourceNode` を予約する |
| 再生時の判断     | 次に必要なタイムスタンプ、パケットバッファ、同期バッファ、前回の動作から処理を選ぶ | 到着時の判断と再生予約が結び付いている                                     |
| 遅延の調整       | 到着履歴、バッファ量、遅着、順序逆転を考慮して目標を更新する                       | 音声のみは 50 ms の予算で、音声と映像の同期では別の遅延制御を使う          |
| 時間伸縮         | `Accelerate` と `PreemptiveExpand` を使い、余剰と不足の両方を調整する              | フレーム内の短縮が中心で、不足時の時間伸長はない                           |
| 欠落補間         | 対応するデコーダーの PLC を試し、利用できなければ `Expand` を使う                  | WebCodecs の復号後に、過去の PCM を使う独自の補間を行う                    |
| 実音への復帰     | `Merge` が補間音と到着した実音の位置、レベルを合わせて接続する                     | フェードと周期反復だけでは、この処理全体を再現していない                   |

根拠は [NetEq の概要](https://webrtc.googlesource.com/src/+/031cc215615895d7ae039d4098c2716d7acf2dc3/modules/audio_coding/neteq/g3doc/index.md)、
[NetEqImpl](https://webrtc.googlesource.com/src/+/031cc215615895d7ae039d4098c2716d7acf2dc3/modules/audio_coding/neteq/neteq_impl.cc)、
[DecisionLogic](https://webrtc.googlesource.com/src/+/031cc215615895d7ae039d4098c2716d7acf2dc3/modules/audio_coding/neteq/decision_logic.cc)、
[DelayManager](https://webrtc.googlesource.com/src/+/031cc215615895d7ae039d4098c2716d7acf2dc3/modules/audio_coding/neteq/delay_manager.cc) である。

[Expand](https://webrtc.googlesource.com/src/+/031cc215615895d7ae039d4098c2716d7acf2dc3/modules/audio_coding/neteq/expand.cc) は有声成分だけでなく、無声成分、雑音と予測フィルターを扱う。
[Merge](https://webrtc.googlesource.com/src/+/031cc215615895d7ae039d4098c2716d7acf2dc3/modules/audio_coding/neteq/merge.cc) は補間音と実音の相関を使って位置を合わせる。
過去の 1 周期を繰り返す処理を入れただけで、NetEq の欠落補間を採用したとはしない。

[Accelerate](https://webrtc.googlesource.com/src/+/031cc215615895d7ae039d4098c2716d7acf2dc3/modules/audio_coding/neteq/accelerate.cc) は約 30 ms の入力を要求する。
現在の 20 ms フレームごとの短縮とは解析する区間も異なる。
相関のしきい値だけを合わせても、同じ処理にはならない。

固定した版の `DelayManager` は内部目標を 80 ms から開始する。
これは Chrome の実出力遅延が 80 ms であることを意味しない。
遅延の制約、フィールドトライアル、出力経路を含むため、その数値を SDK の総予算へ直接移さない。

## ブラウザーで実装する境界

符号化済みパケットの投入と、出力時計に合わせた取り出しを分離する。
音声は到着のたびに予約する方式から、出力側が必要な長さを取り出す方式へ移す。
パケットの並べ替え、復号、時間伸縮、補間、復帰を同じ再生カーソルで扱う。
メインスレッドのタイマーで音声の取り出し周期を作らない。

AudioWorklet の描画単位と NetEq の 10 ms の取り出し単位の間には、余りを保存するバッファが必要になる。
44.1 / 48 kHz の出力、48 kHz の Opus、時計のずれを扱い、変換の都合で音声を捨てたり重複させたりしない。
現在は実音を AudioBufferSourceNode で予約し、標準のレート変換後を AudioWorklet へ渡す。
未着時の補間と復帰は AudioWorklet 側へ移したが、
パケットと復号から一体に取り出す接続部分は未実装である。

[WebCodecs の AudioDecoder](https://www.w3.org/TR/webcodecs/#audiodecoder-interface) は非同期の復号 API であり、
明示的に欠落フレームの PLC や Opus の FEC を要求する操作を公開していない。
復号済み PCM だけをキューに置く方式では、コーデック内部の PLC を含む NetEq 全体を再現できない。
Opus のデコーダーを含む上流 NetEq の組み込みと、その必要部分の移植を比較し、
ビルド、配布サイズ、実時間処理、ライセンス、回帰試験まで確認して実装形態を決める。
名前に NetEq が含まれる別実装を、上流との一致を検証せず採用しない。
AAC の経路と、音声と映像の同期も別途検証する。

## 比較用の入力を固定する計測

これまでの予約空白の測定は、[Chrome の音切れの測定](CHROME_AUDIO_DROPOUT_MEASUREMENTS.md) に記録している。
48 条件、16,080 フレームの予約判断を保存し、出力 PCM と独立した再構成の一致を確認した。
短い遅着には、まだ未来に残っている空白でも補間が呼ばれない例があった。
この結果は現行方式の問題を示すが、NetEq より高音質の代替方式を示してはいない。

初回の計測では、`playout-webrtc-comparison.mjs` に符号化済み Opus の保存と再復号の照合を追加した。
実 PeerConnection の送信変換で、実際に送るフレームのペイロード、RTP タイムスタンプ、通番と解放時刻を保存する。
同じペイロードを SDK にも渡し、Chrome 内の実 WebRTC と同じ出力時計で収録する。
収録後に別の実 AudioDecoder を作り、保存したペイロードだけから全 PCM を再度復号して、元の復号出力と照合する。

`playout-encoded-opus-trace.mjs` は、ペイロードがない古い記録、パケットと PCM の件数不一致、
通番の欠落、不正なバイト列、タイムスタンプ不一致、解放時刻の逆行を拒否する。
RTP の 32 bit タイムスタンプの折り返しも試験する。
API のモックやスタブは使わない。

解放時刻は、送信変換からフレームを出す直前の時刻である。
受信側 NetEq の `InsertPacket` の時刻や WebTransport / QUIC の受信時刻ではない。
今回の遅着パターンは順序を保つ変換で作っており、ネットワークの損失や順序逆転を再現していない。
また、保存したパケットからの再復号は WebCodecs の検証であり、単体の上流 NetEq に再投入した試験ではない。

## 今回の測定結果

Google Chrome 156.0.8078.79 / macOS arm64 で、日本語音声の Julius と Kyoko を各 6 秒使用した。
正常到着、0〜30 ms の遅着、繰り返す 60 ms の遅着を、44.1 / 48 kHz の出力で確認した。
全 12 条件が有効で、各 335 パケット、合計 4,020 パケットを保存した。
保存した符号化済みペイロードの合計は 562,210 byte だった。

別の実デコーダーによる再復号では、全 4,020 フレームのタイムスタンプ、長さ、PCM の各サンプルが一致した。
最大サンプル差は全条件で 0、デコーダーのエラーと不一致フレームは 0 件だった。
JSON に保存した後も全 12 記録を読み直し、入力の検査と再復号結果の件数を再確認した。
原音の収録と独立した OfflineAudioContext の出力との差も全条件で 0 だった。
これで固定できたのは比較入力であり、NetEq と同等以上の音質を確認した結果ではない。

実行識別子と SHA-256 は次のとおり。

- 実行識別子: `2026-10-31T03-09-57.297Z-90666-webrtc`
- 再生コード: `8d36f15b4eb6e24ea1a3b01970332540e7ba06c9523073490a6514134f6200ca`
- 音源: `a40a2221245c040dc47e48c8994bd3fa2e1d4116dd63d105642ce61eef059579`
- 比較用モジュール: `6b26deb539e43ee3f4b1c0e4b44306b1bc04924f98366ebfa88f457d46261772`
- パケット検査用モジュール: `abeed32d2a250abfc81036b72174937e7ee4b1d2326473210d1279eea86d4632`

各条件の記録には、全ペイロード、投入と解放の時刻、復号 PCM、実再生の統計とブラウザーの情報を保存した。
再実行には PLAYOUT_BROWSER_CHANNEL を chrome、PLAYOUT_AV_SECONDS を 6 として、
investigate-playout-audio.mjs の webrtc モードを使う。
計測中はソースを固定し、他の実時間計測、ビルドや全テストと同時に走らせなかった。

測定後の単体テストと PBT は 4,302 件成功した。vp check と型検査も成功した。

その後、方式の変更より比較と計測を先に進める指示に従い、受信変換で同じ Opus を複製する測定へ進めた。
36 条件による Chrome の実 WebRTC と現在の SDK の比較結果は、CHROME_WEBRTC_PLAYOUT_COMPARISON.md に記録した。
遅着時には連続性と遅延の差があり、現時点で同程度の実出力遅延における優位性は未確認である。

## 実装の採用を確認する条件

- 同じ符号化済み入力と到着列で、現行方式と NetEq の出力を比較する
- 入力から出力までの遅延と、その分布を比較する。目標バッファの数値だけを揃えて同じ遅延とはしない
- 正常到着、短い遅着、連続欠落、順序逆転、投入の停止、時計のずれを分ける
- 空白の長さだけでなく、補間中の波形、実音への復帰、音量の変化、短縮と伸長を確認する
- 日本語の有声区間、無声区間、子音と母音の接続を含めて比較する
- 44.1 / 48 kHz と音声と映像の同期、切断後の再開で回帰を確認する
- Bluetooth の実出力と聴取を確認する。ヘッドレス Chrome の機器出力前の PCM だけで症状の解消を宣言しない

上記の確認が終わるまでは、雑音の削減や遅延短縮の達成、NetEq への置き換えの完了として扱わない。
