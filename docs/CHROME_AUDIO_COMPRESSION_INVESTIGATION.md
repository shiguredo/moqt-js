# Chrome の日本語発話と時間圧縮の調査

記録日: 2026-10-31。対象は Google Chrome 156.0.8078.79 / macOS arm64。

日本語の発話がギザギザに聞こえ、Bluetooth 出力で発生しやすいという報告を受けた。
既存の低遅延の設定を保ち、時間圧縮が発声の変化へ与える影響を調べた。
以下はブラウザ内の PCM の測定であり、Bluetooth 機器を通した聴感評価ではない。
報告された症状の原因を特定したとも、WebRTC と同じ音質に到達したとも扱わない。

## 同じ Opus パケットを使う比較

Web Audio から日本語の音源を実 PeerConnection へ入力し、WebRTC のエンコーダーが生成した
Opus のフレームを複製した。元のフレームは変更せず、実 WebRTC の受信側へ送る。
複製だけを AudioDecoderWrapper の Worker 復号へ渡す。
[WebRTC Encoded Transform §2 / §5](https://www.w3.org/TR/webrtc-encoded-transform/)
の RTCRtpScriptTransform を使う。これは策定中の仕様であり、実装は変わり得る。

復号した同じ PCM を SDK の修正前後へ渡し、呼び出し順をフレームごとに反転する。
同じ AudioContext の Worklet に、次の 5 経路を収録する。

1. 符号化前の原音。
2. 実 WebRTC 受信側の音声。
3. 修正後の SDK。
4. 復号 PCM を加工せず、200 ms の余裕を持って予約した参照音声。
5. 修正前の SDK。

200 ms は比較用の参照経路だけの値である。SDK の目標遅延は従来の 50 ms のままとする。
WebRTC と SDK は同じ符号化内容を使うが、RTP と Worker メッセージの配送時刻まで同じではない。
修正前後の SDK は同じ復号コールバックで投入しても、呼び出し中に実時計が進む。
そのため、再生予約の比較と、同じ圧縮上限を与えた純粋な DSP の比較を分ける。
WebTransport / QUIC の接続、パケット損失や順序逆転を再現する試験ではない。

原音は既存の Julius 公開音声と Kyoko の読み上げ音声を各 6 秒使った。
到着パターンは正常、発声開始から 1 秒後以降の 0〜30 ms の遅着、同じく 1.2 秒ごとの
区間に加える 60 ms の遅着とする。後続を追い越させず、遅着後はまとめて渡す。
各パターンを 44.1 / 48 kHz の出力 Context で測定した。Opus の復号は 48 kHz、mono とする。

## 録音の採否

リモートの track を Web Audio に繋ぐだけでは、Chrome の受信処理が音声を取り出さない条件があった。
初期の試作では WebRTC の録音が無音だったため、比較結果を採用しなかった。
最終の測定では音声要素で受信を駆動し、その要素の出力を消音したうえで、同じ track を Worklet へ接続する。
録音のピークに加え、受信統計の jitterBufferEmittedCount と totalAudioEnergy で動作を確かめる。

Worklet の currentFrame には、連続する呼び出しで同じ値を返した後に飛ぶ観測があった。
これを PCM の欠落と即断せず、Worklet 内の独立した連番と、原音の独立レンダリングを併用する。
同じ原音を OfflineAudioContext でも再生し、収録した原音との最大サンプル差を全区間で調べる。
差が 1e-6 以上、収録の連番の欠落、Worklet / ページ例外、参照経路の予約不足、SDK の再生失敗は
無効な測定として扱う。currentFrame の異常も結果に残す。

録音中にソースや音源が変わった測定も採用しない。ブラウザ、ソース、測定コード、音源の
ハッシュを記録し、解析前に PeerConnection と復号を停止して、解析中の入力の追加を防ぐ。

## 再現した波形の変化と修正

従来の時間圧縮は、周期の相関を検査した後、常にフレームの中央で 1 周期分を混ぜて削っていた。
弱い音から強い音へ変わる区間では、周期の相関が高くても振幅は等しくない。
中央で混ぜると、既に届いている発声の強まりまで弱い音と混合する。

200 Hz の周期波をフレームの後半で強める回帰試験では、従来の出力と、強まりを保った出力との
最大差は約 0.0173 だった。前半には同じ周期が続くため、そこへ切断位置を移せば強まりを残せる。
修正後の誤差は 1e-7 未満となった。これはこの合成信号の検証であり、日本語全体の評価値ではない。

削る周期と圧縮の可否は従来どおり中央で決める。その後、同じ長さを削る位置だけを選ぶ。
中央と左右の計 9 候補を比較し、次の条件を満たす場合だけ移動する。

- 混合による打ち消し量の合計が、中央より小さい。
- すべてのチャンネルで、その量が中央より増えない。
- 各チャンネルの移動先でも相関が 0.9 以上、または混ぜる区間全体が -60 dBFS 未満である。
- フレームの先頭と末尾に原音を 1 サンプル以上残せる。

評価量は、混ぜる 2 区間を a、b、線形混合の重みを w としたときの
`sum(w * (1 - w) * (a - b)^2)` とする。線形混合で元の重み付きエネルギーから失われる量に等しい。
これは発声全体の誤差、ノイズの量や MOS ではない。同点や丸め誤差程度の改善では中央を保つ。
静かなチャンネルの悪化を、大きいチャンネルの改善で相殺することも許さない。

この位置の選択は独自の変更である。[NetEq の time_stretch.cc](https://webrtc.googlesource.com/src/+/main/modules/audio_coding/neteq/time_stretch.cc)
は 30 ms の入力の 15 ms 付近を解析する。SDK の 20 ms の入力へ、その位置選択をそのまま移植したものではない。
新しい入力の待ち、目標遅延や圧縮する長さの変更は加えない。

## 測定結果

最終の測定は 12 条件すべてで有効だった。各 335 フレーム、合計 4020 フレームを得た。
原音の収録と独立したレンダリングの差は全条件で 0 だった。
同じ PCM と同じ圧縮上限を与えた DSP 比較では、圧縮の可否と削るサンプル数は全フレームで一致した。

以下は繰り返す 60 ms の遅着の結果である。打ち消し量は実再生で圧縮したフレームについて、
同じ入力・同じ圧縮量で再評価した合計の削減率である。
待ち時間は push 時の到着記録から予約開始までの p95 であり、音源から実機出力までの遅延ではない。
隙間は 6 秒の発話と起動・終了を含む収録中の累積値とする。

| 音源 / 出力       | 圧縮したフレーム | 打ち消し量の削減 | 待ち時間 p95 修正前 → 修正後 (ms) | 予約の隙間 修正前 → 修正後 (ms) |
| ----------------- | ---------------: | ---------------: | --------------------------------: | ------------------------------: |
| Julius / 44.1 kHz |               16 |           11.5 % |                       89.5 → 89.7 |                   121.8 → 121.9 |
| Julius / 48 kHz   |               16 |           19.6 % |                       93.8 → 93.5 |                   123.8 → 123.9 |
| Kyoko / 44.1 kHz  |               22 |           30.4 % |                       83.7 → 83.3 |                   113.9 → 114.1 |
| Kyoko / 48 kHz    |               22 |           41.6 % |                       80.9 → 80.6 |                   116.0 → 116.5 |

正常到着の 4 条件は、修正前後とも時間圧縮 0 ms、予約の隙間 0 ms だった。
0〜30 ms の遅着では時間圧縮は動かず、約 12〜16 ms の累積の隙間が残った。
最終の 12 条件における待ち時間 p95 の最大増加は約 0.4 ms、隙間の最大増加は約 0.52 ms だった。
push の処理時間 p95 の最大増加は約 0.1 ms だった。
これを待ち時間が厳密に同一である証拠とは扱わない。

測定器を整理する前の同時比較でも、同じ本体の実装で 12 条件を測った。
実行識別子は `2026-10-31T01-49-50.598Z-49070-webrtc` である。
その試行では待ち時間 p95 が最大約 1.73 ms、隙間が最大約 4.93 ms 増えた。
打ち消し量の削減は繰り返す遅着の 4 条件で約 14〜50 % だった。
到着列を再取得した試行間の差と、修正前後を同じ到着で比べた差を混同しない。
波形の打ち消しが減ったことから、音切れが改善したと結論しない。

最終測定の実行識別子と SHA-256 は次のとおり。

- 修正前のソース: `69c8057e9bcccfb2f000558397b6b98879539a40f52d728542104f05bb6c1d99`。
- 修正後のソース: `8d36f15b4eb6e24ea1a3b01970332540e7ba06c9523073490a6514134f6200ca`。

## 検証

発声の強まりを保つ回帰試験は、修正前のコードで失敗することを先に確認した。
位相、音量、発声位置と既存のサンプルレートを変える PBT と、小さいチャンネルを犠牲にしない
ステレオの回帰試験も追加した。

- 単体テスト / PBT: 4293 件成功。
- Google Chrome の再生 / 音声 codec E2E: 81 件成功。
- Google Chrome の production ビルド E2E: 10 件成功。
- vp check、型検査、SDK と DevTools のビルド: 成功。

## 再実行

音源は既存の prepare-playout-japanese.mjs で用意する。修正前の比較には、コミット 8927c50c の
src 全体を別の場所へ展開し、その src の場所を PLAYOUT_COMPARE_SOURCE_ROOT に指定する。
比較なしでも WebRTC と現在の SDK を収録できる。

```sh
PLAYOUT_BROWSER_CHANNEL=chrome \
PLAYOUT_AV_SECONDS=6 \
PLAYOUT_COMPARE_SOURCE_ROOT="<修正前の src>" \
vp exec node scripts/investigate-playout-audio.mjs webrtc
```

PLAYOUT_CASE_FILTER で音源名、パターンやレートを絞れる。JSON と比較用 WAV は実行ごとに保存する。
JSON の compressionQuality は、収録後に同じ PCM と同じ圧縮上限で比較した値である。
available は圧縮可能な全フレーム、scheduled は修正後の実再生で圧縮したフレームを対象とする。
WebRTC と SDK の出力は伸縮によって時間軸が異なるため、全体を 1 回ずらして算出した波形の
SDR を音質の順位に使わない。

## 残る課題

今回の変更は時間圧縮の混合位置を改善するもので、途絶時の無音を減らすものではない。
到着後に AudioBufferSourceNode を予約する現在の構成では、到着が止まって直前の音が鳴り終わると、
後からの補間で過去の無音を取り消せない。引き続き、出力の周期に合わせて不足を判断する処理と、
少ない先行予約で到着の揺らぎを吸収する制御を、同じ音切れと遅延の指標で検証する必要がある。

今回の結果だけで Bluetooth で増える症状を説明しない。実機の出力経路を通した測定と、
日本語の発話での聴感確認が残る。
