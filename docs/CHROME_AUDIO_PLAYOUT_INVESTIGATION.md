# Chrome の音声 playout の継続調査

記録日: 2026-10-31 (Asia/Tokyo)。

遅延の短縮とノイズの削減を両方の要件とし、Google Chrome 156.0.8078.79 / macOS arm64 で調査した。
Playwright から headless の Google Chrome を起動した。
実利用で報告されたノイズの原因を特定できたとは扱わない。今回再現できた欠陥、修正の効果、
WebRTC との差が残る設計上の課題を分けて記録する。

## WebTransport / QUIC の再生に必要な制御

WebTransport が提供するのは転送の手段である。[WebTransport の説明](https://github.com/w3c/webtransport/blob/main/explainer.md)
には、信頼性のあるストリームと信頼性を保証しない Datagram が区別されている。
[RFC 9221 §1 / §5](https://www.rfc-editor.org/rfc/rfc9221.html#section-5) の Datagram は再送を要求しない。
媒体の再生期限、到着順序の修復、欠落の補間は、この転送層だけでは実現しない。

[NetEq の設計資料](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_coding/neteq/g3doc/index.md)
では、パケットの投入と 10 ms ごとの音声の取り出しを分けている。取り出すときに、次の媒体時刻の
パケットを復号し、バッファ量に応じて伸縮し、不足すれば補間し、実音が戻れば接続する。
遅延の目標値の調整だけを取り入れても、この一連の動作と同じ品質にはならない。

現在の AudioPlayoutSession は、復号の出力を受け取った時点で AudioBufferSourceNode を予約する。
この構成では、後続の到着が止まったことに気付くまでに、直前の音が既に鳴り終わる場合がある。
後から届いた音の処理で補間を生成しても、過去に出力された無音は修復できない。
今回の修正も、この制約そのものは解消していない。

Opus のパケットを状態と無関係に復号できるとも扱わない。
[Opus WebCodecs Registration §4](https://www.w3.org/TR/webcodecs-opus-codec-registration/#encodedaudiochunk-type)
は、パケットが `key` であっても期待した音になるとは限らないことを注記している。
現在の受信処理は重複を除外する一方、復号へ渡す順序は到着順である。
順序逆転の影響は、復号後の PCM を並べ直すだけでは取り消せない。

また、[OpusEncoderConfig](https://www.w3.org/TR/webcodecs-opus-codec-registration/#opusencoderconfig)
の `useinbandfec` と、受信側で欠落分の復号を要求する操作は別である。
[AudioDecoder の API](https://www.w3.org/TR/webcodecs/#audiodecoder-interface) は NetEq の取り出し API ではない。
調査時点の [Chromium の OpusAudioDecoder](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/media/filters/opus_audio_decoder.cc)
も、通常のパケット復号で `decode_fec = 0` を渡している。
送信側の FEC の設定だけで、現在の WebCodecs の受信経路が欠落を復元すると判断しない。
WebCodecs と Opus 登録文書はいずれも策定中であり、API とブラウザの実装は今後変わり得る。

## 再現した欠陥と修正

### レート変換後の境界で振幅が加算される

一定値 0.25 の連続する 20 ms のバッファを実 Web Audio へ渡した。
48 kHz のバッファを 44.1 kHz の Context へ予約する条件などで、境界だけが 0.5 になった。
これは入力波形に元からある変化ではなく、前のバッファの末尾と次の先頭の加算である。
開始位置の端数やバッファの長さに依存するため、レートが異なるすべての予約で発生するわけではない。

各 Source を予約上の終端で明示的に停止するようにした。開始時刻とバッファの長さは変えない。
補間用の Source と、処理中に開始を押し直した Source にも同じ規則を適用する。

Opus の通常の購読では、既に Context を復号レートの 48 kHz に合わせている。
この修正の主な対象は、Context の作成時のフォールバックや、利用者が異なるレートの Context を渡す場合である。
48 kHz 同士の通常再生で起きているノイズの説明には使えない。
バッファごとにリサンプラーの状態が分かれることによる波形の変化まで、すべて解消した修正でもない。

### 低い声の補間の解析材料が足りない

従来は直前の 20 ms のフレームだけを補間へ渡していた。
周期の探索上限 15 ms と末尾の相関窓 9.75 ms を同時に確保できず、68 Hz と 80 Hz の
倍音を含む合成音では、20 ms の欠落が無音になった。

受信済みの連続した PCM の末尾を最大 30 ms 保持する AudioConcealmentHistory を追加した。
媒体時刻が途切れた場合、逆行した場合、レートやチャンネル数が変わった場合は連結しない。
出力を作り直す場合も履歴を破棄する。先のフレームを待つ処理は追加していない。

長い履歴を常に優先する試作では、日本語音声の一部で以前の補間を拒否した。
振幅を変調した 492 Hz の合成音でも、20 ms の解析は成功し、30 ms の解析だけでは失敗した。
最終実装は、従来の直前フレームの解析が失敗し、より長い連続履歴がある場合だけ再解析する。
短い窓で補間できた波形は、その結果をそのまま使う。

この変更で失われた発話内容を復元できるとは扱わない。
相関と継ぎ目の検査は維持しており、非周期的な子音などは引き続き補間できない場合がある。

## 計測の範囲

決定論的な波形の比較は、実 AudioData、実 AudioPlayoutScheduler、実 AudioPlayoutSession と
実 OfflineAudioContext を使った。時計の学習や通信の揺らぎを分離し、予約後の Chrome の
レンダラーが出すサンプルを検査した。オーディオ API のモックやスタブは使っていない。

実時間の A/V 比較は、同じ Opus 復号済み PCM と同じ到着列を、同じ AudioContext の
修正前後の再生へ同時に投入した。作成順を入れ替えて反復し、各フレームの投入順も交互に変えた。
これは実回線の再試行でも、メインスレッドを実際に停止させる試験でもない。
到着の停止を表す列と、実メインスレッドの停止は区別する。

日本語の入力は既存の Julius 公開発話と macOS の Kyoko、Eddy、Grandpa の読み上げ音声を使い、
実 Opus の符号化と復号を通した。同じ音源を使った比較であり、話者数を増やした主観評価ではない。

音声の遅延は、媒体時刻から `getOutputTimestamp()` で換算した出力予定までの値である。
スピーカー、イヤホンやマイクによる音響ループバックの測定ではない。
同時比較の音声と映像の p95 は媒体の最初の 1 秒を除き、予約の隙間や補間量は起動を含む累積値とする。
日本語の最大サンプル差分には自然な子音の変化も含まれるため、その値だけをノイズの点数にしない。

各測定は Chrome のバージョン、ソース、測定コード、音源の SHA-256 とともに保存する。
収録量、収録連番、Worklet の例外、ページ例外、測定中のソース変更を採否へ反映する。
実時間の収録では Worklet 内の連番を使い、`currentFrame` の重複や飛びを収録の欠落と混同しない。

## 最終実装の計測結果

### 決定論的な波形

レートの組み合わせ 5 種、固定長 / 可変長の 2 種、開始位置の端数 4 種の計 40 条件で、
各 100 バッファを予約した。開始と終了のフェードを除き、一定値 0.25 との差が 0.001 を超える
サンプルを数えた。可変長は、時間圧縮後と同様に次の開始が出力のサンプル格子から外れる条件である。

| 指標                     |             修正前 |             修正後 |
| ------------------------ | -----------------: | -----------------: |
| 異常がある条件           |             7 / 40 |             0 / 40 |
| 異常なサンプルの合計     |                312 |                  0 |
| 異常がある条件の最大振幅 |                0.5 |               0.25 |
| 予定の終端との誤差の最大 | 約 1.8 × 10^-15 秒 | 約 1.8 × 10^-15 秒 |

68 / 80 / 100 / 170 Hz の定常の倍音波と、492 Hz の非定常音を、44.1 / 48 kHz で測った。
40 ms の音を渡した後に 20 ms を欠落させ、その後の実音を元の予定へ置いた。

| 条件                        | 修正前の補間 | 修正後の補間 | 補間区間の波形差 修正前 → 修正後 |
| --------------------------- | -----------: | -----------: | -------------------------------: |
| 68 Hz / 44.1 kHz            |         0 ms |        20 ms |                     0 → -25.7 dB |
| 68 Hz / 48 kHz              |         0 ms |        20 ms |                     0 → -25.7 dB |
| 80 Hz / 44.1 kHz            |         0 ms |        20 ms |                     0 → -26.4 dB |
| 80 Hz / 48 kHz              |         0 ms |        20 ms |                     0 → -26.4 dB |

小さいほど基準に近いが、聴感の品質スコアではない。意図した補間の減衰も含む。
後続の実音の開始と終了は、全 10 条件で丸め誤差の範囲内に収まり、補間のための待ちは増えていない。

### 実 QUIC Datagram を通した比較

Worker の Opus、実 QUIC Datagram、実購読 API、実 AudioWorklet の収録で、各条件を 20 秒動かした。
正常到着と独立損失は Kyoko、連続損失は Julius を使った。音源は 6 秒のバッファを繰り返している。
損失は実際に到着した Object を復号前に落として注入する。連続損失は 3 Object を 1 秒ごとに落とす。
以下の p95 は計測開始後の最初の 1 秒を除き、予約の隙間は起動を含む累積値である。

| 条件                           | 音声 p95 修正前 → 修正後 | 映像 p95 修正前 → 修正後 | 予約の隙間 修正前 → 修正後 |
| ------------------------------ | -----------------------: | -----------------------: | -------------------------: |
| 正常到着、1 コピー             |         142.7 → 151.2 ms |         149.6 → 150.9 ms |             51.6 → 71.3 ms |
| 5 % の確率の独立損失、2 コピー |         130.6 → 127.4 ms |         133.3 → 133.5 ms |             36.4 → 20.3 ms |
| 3 Object の連続損失、1 コピー  |         129.2 → 534.5 ms |         132.7 → 501.1 ms |         1094.9 → 1478.2 ms |

すべて収録の連番欠落、収録器の例外、配信中のエラーは 0 で、測定は有効だった。
535 ms の試行も採用している。別の到着列と出力時計を持つ実回線の比較であり、差をそのまま修正の効果へ帰属させない。
同時に、この結果から全体の低遅延を維持できたと結論することもできない。
正常到着と独立損失は境界の段差カウンターが 0、535 ms の連続損失は 6 だった。

連続損失の悪化した試行では、playout へ渡る前の遅れの最大が約 517.5 ms になっていた。
20 秒時点では、Object の入力の遅れが 63.0 ms、復号が足した遅れが 0.2 ms へ戻っても、
復号出力から鳴り始めまでの待ちは 215.1 ms、目標からの遅れは 163.1 ms 残った。
到着の大きな停滞と、その後の余分なキューの回復が遅い問題を分けて扱う必要がある。
停滞の発生源を、この記録だけから回線、送信、受信のいずれかへ確定することはできない。

比較元の実行識別子は `2026-10-30T20-32-20.265Z-99683-avRelay`、
修正後は `2026-10-30T20-42-24.519Z-2925-avRelay` である。
メソッドの整理前の先行試行では連続損失の音声 p95 が 133.5 ms だったが、上の 534.5 ms を置き換える根拠にはしない。

### 大きな遅れの切り分け

535 ms の試行に残っていた音声の復号出力の到着列を正規化し、映像は一定の 20 ms 遅延の列を生成した。
PCM は同じ日本語音源から再生成し、修正前後へ同時に投入した。
元の映像の復号到着列と入力 PCM は保存していなかったため、これは元の実回線の完全な再現ではない。
到着停止に対する制御の応答を比べる対照実験である。

この同時比較では、音声 p95 が修正前後とも 505.9 ms、最後の 2 秒の p95 も両方 311.8 ms になった。
この到着列に対しては、既存の制御も大きな待ちを残すことを確認した。
試行は `2026-10-30T20-47-43.927Z-3948-av`、到着列の SHA-256 は
`3b1cf40778f76856028045b47844cc342b1ea1ad3e664e2de77aec658827bb84` である。

追加で、実リレーの測定へ音声と映像の復号出力の到着列と、`pushAudio` の処理時間を記録する機能を加えた。
連続損失を各 20 秒再試行した結果は以下のとおりである。

| 指標                              |          修正前 |          修正後 |
| --------------------------------- | --------------: | --------------: |
| 音声 p95                          |        153.8 ms |        145.7 ms |
| playout 到着までの遅れ p95 / 最大 | 80.9 / 150.0 ms | 75.4 / 121.0 ms |
| `pushAudio` の処理時間 p95 / 最大 |    0.6 / 2.1 ms |    0.7 / 2.9 ms |

この再試行では 535 ms の停滞は再発しなかった。上の処理時間は、535 ms が発生した試行自体を後から測った値ではない。
到着の遅れも異なるため、145.7 ms を総合的な改善量としては扱わない。
試行は `2026-10-30T20-48-11.267Z-4001-avRelay` と `2026-10-30T20-48-36.613Z-4046-avRelay` である。

さらに、この修正後の試行から実際の音声と映像の復号到着列を保存し、同じ AudioContext へ再投入した。
音声 p95 は修正前 152.1 ms、修正後 151.2 ms、最後の 2 秒は 137.8 → 136.4 ms だった。
PCM は再生成しており、元の符号化入力をそのまま再生したものではない。
試行は `2026-10-30T20-49-01.806Z-4131-av`、到着列の SHA-256 は
`0151d53c0337e0696b2eb271d083e4fe77df472f36df24712ed45ca86d213172` である。

今回確認できたのは、境界の加算と、低い周期の補間材料の不足への改善である。
大きな到着停止の後にも低遅延と音質を両立する制御は、引き続き課題として残る。

## 検証

- 単体テスト / PBT: 4,290 件成功
- Chromium E2E: 232 件成功
- 配布ビルドの E2E: 10 件成功
- Google Chrome の playout 関連 E2E: 68 件成功
- 型検査、フォーマット、lint、SDK と DevTools のビルド: 成功

Google Chrome で全体の E2E を試した際は、非対応の映像 codec を選ぶ既存の 2 件が、
候補のすべてを Chrome がサポートしていて成立しなかった。この 2 件を音声の不具合として数えていない。
また、試験の保存先を共有した並列実行で記録の競合が起きたため、その実行を成功の根拠へ含めず、
保存先を分けて再実行した。

単体テストの並行実行中には、既存の publisher の再開試験が 1 回失敗した。
その後、単体テスト全体を単独で再実行して 4,290 件が成功した。失敗の原因は今回の調査では確定していない。

## 次に検証する設計

1. 大きな停滞の後に残るキューの回復を検証する。既に届いた複数フレームを使い、20 ms 単位の解析では扱いにくい低い周期の音を、追加の先読みなしで時間圧縮する方法を候補とする
2. 出力の時計で一定量の PCM を取り出し、到着処理とは独立して不足を判断する構成を検証する。AudioWorklet への移行を候補とし、実メインスレッド負荷に対する波形と遅延を同時に測る
3. 音声の復号前の順序を、既存の再生期限までの余裕の範囲で整える方法を検証する。並べ替えの固定待ち時間を現在の予算へ単純に上乗せしない
4. 送信、復号、再生の時計のドリフトを長時間の入力で分離し、小さな時間補正を繰り返すことによる変調を測る
5. 同じ入力を使った Chrome の WebRTC と WebTransport の比較を追加し、音響ループバックでも遅延と欠落を照合する

これらは今回の実装に含めていない検証方針である。今回の改善だけで WebRTC と同等の品質を確認したとはしない。

## 再現

`investigate-playout-audio.mjs` に `waveform` モードと `PLAYOUT_BROWSER_CHANNEL=chrome` を追加した。
既存の `av` / `avRelay` モードでもインストール済みの Google Chrome を選べる。
未指定時は従来の Playwright Chromium を使う。

`waveform` は `resampling` と `low-pitch` を測り、後者には 492 Hz の非定常音の対照も含む。
`PLAYOUT_COMPARE_SOURCE_ROOT` へ修正前のソースツリーを指定すると、同じ条件で修正前後の結果を保存する。
`av` でも同じ変数を使え、作成順の反転には `PLAYOUT_SOURCE_ROOT` と入れ替えて指定する。
実リレーは `PLAYOUT_RELAY_URI` で接続先を渡し、`PLAYOUT_VARIANT` で試行を区別する。
接続先の実値や認証情報は記録本文へ書かない。

回帰テストは `media-playout-resampling.spec.ts`、`media-playout-low-pitch.spec.ts` と
AudioConcealmentHistory の PBT を参照すること。
