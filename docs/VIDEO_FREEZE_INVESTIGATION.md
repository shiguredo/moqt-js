# 映像の復号失敗とキーフレーム待ちの調査

2026-10-30、マイクが無音のときに映像が止まり、話すと動くという報告と停止時の統計を調べた。
音声と映像を一律に待たせる変更は行わず、送信前の破棄と復号失敗後の復旧を実測した。

## 停止時の統計

報告された配信は VP9、1280×720、30 fps、キーフレーム間隔 10 秒で、音声は Opus Datagram だった。
映像の復号エラーは 92 回、参照フレーム不足による破棄は 6,052 枚で、受信側が数える
Object の欠落、Group の欠落、stream reset はいずれも 0 件だった。
音声は受信、復号、再生が続き、再生側の破棄は 0 件だった。

直近の長い停止には約 7.4 秒のものがあり、停止後は次の Group の Object 0 で復帰していた。
通常の表示遅延の p95 は約 158 ms、表示 fps はコピー時点で 30 だった。
直近の正常なフレームから求めた分布や、最後の 1 秒の fps だけでは、その前の数秒の停止を検出できない。

音声の振幅を映像の開始条件にする処理はない。別途、音声トラックなし、音声再生の ON / OFF、
無音化、有音への復帰、音声トラック停止を実 DevTools と実 QUIC で確認したところ、
7 条件すべてで映像が継続した。合成入力での成功は、実機の停止を否定する根拠にはしない。

## 同じ timestamp の出力を捨てる不具合

送信側は、符号化を依頼したフレームの timestamp と配信の世代を対応づけ、停止前の古い出力を
送らないようにしていた。しかし、同じ世代で同じ timestamp の入力が重なると、記録が上書きされ、
最初の出力を送った時点で記録を消していた。後から届くもう一つの出力を送れなくなる。

この破棄は Object ID の採番より前に起きるため、受信した Object ID が連続していても、
参照する映像データが欠け得る。受信側の欠落カウンターが 0 件でも、この経路は否定できない。

Chrome 156.0.8078.74 の実 WebCodecs で、2 枚ずつ同じ timestamp を持つ異なる映像を符号化した。
同じタスクで 2 枚を投入し、出力の前に依頼が重なる条件を確実に作った。
同じ符号化出力を対照、旧処理、新処理の 3 経路へ渡した結果は次のとおりだった。

| 経路                       | 符号化出力 | 送信対象 | 復号成功 | 復号エラー |
| -------------------------- | ---------: | -------: | -------: | ---------: |
| 送信前の処理を通さない対照 |        120 |      120 |      120 |          0 |
| 旧処理                     |        120 |       60 |        1 |          1 |
| 新処理                     |        120 |      120 |      120 |          0 |

API の置き換え、偽のマイク、偽のコーデックは使っていない。
同じ timestamp でも未出力の枚数を数え、依頼した枚数だけ出力を送るように修正した。
DevTools と公開 publisher API はこの管理処理を共有している。
配信停止時に記録を消す処理と、異なる世代の出力を送らない判定は維持している。
今回修正したのは同一世代内の重複である。停止前後の世代で同じ timestamp を再利用した場合、
旧出力と新出力の識別を timestamp だけでは保証できない、という既存の制約は残る。

実際のカメラが重複 timestamp を渡していたかは、提供された統計には記録されていない。
この不具合を再現して修正したことと、今回の実機の唯一の原因を特定したことは区別する。

## timestamp の仕様と重複の発生箇所

同じ timestamp が付いたことだけでは、同じフレームとは判定できない。
[WebCodecs §6.5](https://www.w3.org/TR/2026/WD-webcodecs-20261026/#dom-videoencoder-encode) の
`VideoEncoder.encode()` の入力検証は、timestamp の一意性を要求していない。
[§6.6 の出力手順](https://www.w3.org/TR/2026/WD-webcodecs-20261026/#output-encodedvideochunks) は、
対応する入力 `VideoFrame` の timestamp を `EncodedVideoChunk` に写す。
したがって、同じ値を持つ複数の入力を渡した場合、出力の timestamp も同じ値になり得る。
前述の VP9 の実測でも、異なる 120 枚すべてを符号化して復号できた。

[LOC draft-04 §2.3.1.1](https://www.ietf.org/archive/id/draft-ietf-moq-loc-04.html#section-2.3.1.1) は、
TIMESTAMP の意味と単位を定めるが、一意性を要求していない。
[MOQT draft-22 §2.1](https://www.ietf.org/archive/id/draft-ietf-moq-transport-22.html#section-2.1) では、
Object を Track Namespace、Track Name、Group ID、Object ID の組み合わせで識別する。
timestamp をフレームの一意な ID として使って出力を失う処理は、moqt-js の不具合である。

入力の `VideoFrame.timestamp` と、ネットワーク上の LOC TIMESTAMP は、壁時計への換算を挟む。
今回の不具合はエンコーダーの入力と出力を対応づける段階で起き、LOC TIMESTAMP の生成と
Object の送信より前に出力を破棄していた。リレーを通さない対照試験でも再現した。

重複が新たに発生する箇所がないか、Chrome 156.0.8078.74 で別途、次の照合を行った。

| 経路                                    | 入力と照合対象                                                                                     | 結果                                                                                 |
| --------------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 実リレーの Subgroup Stream              | 異なる Object ID の 12 個を送信し、同じ接続先内と異なる接続先間でそれぞれ受信                      | 24 個すべての Object の位置、TIMESTAMP、Properties、Payload が送信時と一致           |
| 実リレーの QUIC Datagram                | 異なる Object ID の 12 個を送信し、同じ接続先内と異なる接続先間でそれぞれ受信                      | 24 個すべての Object ID、TIMESTAMP、Properties、Payload が送信時と一致               |
| canvas の取得から符号化、壁時計への換算 | `captureStream()`、実 `MediaStreamTrackProcessor`、実 worker エンコーダーを約 12 秒動かした 361 枚 | 入力、符号化出力、換算後の重複はすべて 0 件。出力に対応する入力の欠落とエラーも 0 件 |

リレーの試験では、12 個中の timestamp は 9 種類とし、異なる Object ID に同じ値も与えた。
この試験では値の改変、新たな重複、欠落を観測しなかった。
この結果は試験した経路とデータの範囲に限り、リレーのすべての状態を保証するものではない。

実カメラについては画像を保存せず timestamp だけを読む計測を試みたが、
`getUserMedia()` が計測の期限内に完了せず、取得フレームは 0 枚だった。
元の停止時に実カメラが重複した値を出していたか、その値がどの段階で生じたかは未確認である。
通常の canvas 入力では重複を観測せず、意図的な重複入力では不具合を再現した、という区別を保つ。

## 復号失敗後の復旧

既存の処理は復号器を作り直した後、自然に次のキーフレームが届くまで待っていた。
間隔が 10 秒の配信では、失敗した位置によって数秒の停止が残る。
新しい処理は復号器の再構成後にキーフレーム待ちへ戻し、対応する配信へ新しい Group を要求する。
復号済みの Group と Object の位置は保ち、遅着した古い映像へ巻き戻らないようにする。
再構成中に届いたキーフレームを捨てないよう、要求は再構成の後に送る。

要求できるのは `DYNAMIC_GROUPS=1` を広告する Track に限る。
これは MOQT draft-22 §9.20.19 の `REQUEST_UPDATE` による `NEW_GROUP_REQUEST` の条件である。
対応しない配信では要求を送らず、次の定期キーフレームを待つ。仕様はドラフトであり変更され得る。

実 QUIC リレーへ DevTools の音声と映像を配信し、配信開始から約 3 秒後に壊れた VP9 chunk を
実復号器へ渡して、ブラウザ本体の復号エラーを発生させた。
旧処理は 2 秒以内の復帰条件を満たさなかった。
修正後の Chrome 156.0.8078.74 は約 485 ms で、新しい Group の受信、キーフレームの復号、
11 枚の追加表示を確認できた。同じ間に音声も 25 フレーム進んだ。
この値は実カメラの停止時間の改善量ではなく、制御した復号失敗からの復旧時間である。

復号エラーは Console に加えてコピー対象の Debug Logs にも記録するようにした。
最後に受信した Object の位置を添え、復号失敗と長い表示停止を照合できるようにしている。

## 検証の範囲

重複 timestamp の回帰テストは実 VP9 の符号化と復号を通し、対照側も全数を復号できることを要求する。
世代管理の PBT では、入力の重複、出力順の変更、配信停止を含めて、現在の世代の入力枚数と
送信対象の出力枚数が一致することを確かめる。

実リレーの回帰テストは音声の振幅だけでなく、映像の送信、受信、復号呼び出し、表示件数と
canvas の画素の変化を 500 ms ごとに観測する。復旧テストでは、新しい Group の要求が実際に
publisher まで届き、音声も継続していることを必要とする。

この修正では音声の圧縮、補間、フェードと再生の予算は変えていない。
実カメラで停止が解消したかは、修正版を使った同じ入力で確認する必要がある。
