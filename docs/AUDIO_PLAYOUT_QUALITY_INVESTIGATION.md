# 音声の出力波形の測定と改善

記録日: 2026-10-29。

本稿は `1c0dbcb9` までの音声波形の修正と計測、および差分レビュー後の
短フレーム、timestamp、再生基準の切り替えの修正と、計測の採否条件の改善を記録する。
続く A/V の低遅延化と旧遅延制御の削除は
[A/V 再生の低遅延化の計測](AV_LOW_LATENCY_INVESTIGATION.md) を参照すること。

`d6893cb2` の実装を起点に、音源を実際の WebCodecs / Web Audio へ通し、
圧縮、補間、境界処理、遅延回復の不具合を再現して修正した。
音声 API のモックやスタブを追加せず、修正前に回帰テストの失敗を確認した。
再現したクリックの原因は修正したが、長い欠落の内容の復元と、あらゆる到着列での
超低遅延の維持は未達である。50 ms は通常の待ちの設定であり、実測の上限ではない。

## 測定の条件

- macOS / arm64、Playwright Chromium 156.0.8078.4
- 基本条件は 48 kHz、mono、20 ms / 960 サンプル、Opus 64 kbps
- 周期推定は 44.1 / 48 kHz、80〜440 Hz、純音、倍音を含む有声音、発話状の包絡で比較
- ステレオでは左 200 Hz に対し、右を 200 / 233 / 333 / 400 / 440 Hz に変更
- 正常入力、20 ms 欠落、目標時刻の上昇 / 下降、圧縮直後の欠落、180 ms の到着停滞を比較
- 実時間の検証は `createMediaPlayout`、実 `AudioData`、実 `AudioContext`、実 `AudioWorklet` を使用
- 実リレーでは高レベル API、Worker の Opus、QUIC Datagram、購読者の実 MediaStream 出力も使用
- 決定論的な出力の比較は、実スケジューラーと実 DSP を `OfflineAudioContext` へ接続
- 60 秒の制御の再現では、時刻を引数に取る実クラスだけを合成時計で駆動

測定環境の原本は `investigation-logs/playout-quality-2026-10-28/environment-*.json` にある。
調査開始時の日付をディレクトリ名に残しており、翌日も同じ場所へ結果を保存している。
ローカルの実時間試験は、事前に実 Opus で復号した PCM を所定の到着間隔で投入する。
符号化と復号の実時間の負荷は、実リレーの試験で扱う。

## 日本語の音源

を使用した。取得先をコミットで固定し、同梱の MIT ライセンスと書き起こしも保存した。
このサンプルは約 2.06 秒であり、多話者の自然会話を代表する量ではない。

Kyoko は通常と高速の 2 条件である。これらは合成音声であり、人の録音とは区別する。
生成した文には、無声子音、破裂音、促音、長音、数字、休止、語尾を含めた。
音源全体を 6 秒ずつに分け、先頭だけに偏らず検証する。

## 再現して修正した不具合

### 圧縮によって次の補間に必要な材料が失われる

修正前は `AudioPlayoutSession` が圧縮後の約 14 ms の音を保持していた。
140〜180 Hz の一部では末尾の周期を解析する長さが足りず、20 ms の材料なら成功する
補間が失敗した。48 kHz / 170 Hz の有声音では、100 フレーム中の成功が
圧縮前 100 回、圧縮後 0 回だった。

Opus を通した発話状の音でも、圧縮直後に欠落を与えると約 5.28 ms の穴が残った。
圧縮前の材料を保持する変更で、その穴を補間できた。実ブラウザの入口でも
圧縮と補間が実際に行われ、`gapCount = 0` になることを回帰テストで確認する。

圧縮は音の中央を削り、末尾の波形は変えない。このため、末尾の周期の推定には
圧縮前のフレームを保持する。長さを確保するために音声を先読みする遅延は追加しない。

### 左の周期だけで右の音も圧縮する

修正前は第 1 チャンネルの相関だけで圧縮を許可していた。
左 200 Hz / 右 333 Hz でも 5 ms を両方から削り、右のエネルギーが約 0.80 dB 落ちた。
右の局所波形差は +1.27 dB だった。これは音質評価の点数ではなく、切断位置が右の周期に
一致していないことを示す測定値である。

候補の周期で、全チャンネルの残りの波形全体も一致することを確認するようにした。
相関の閾値は既存の 0.9 を維持した。左右で同じ周期を使えない場合は圧縮しない。

補間についても別に検証した。左 200 Hz / 右 233 Hz と 333 Hz では、
100 フレーム中それぞれ 4 回、先頭の段差だけが小さい位相で不適切な補間を許可していた。
右の波形差は、それぞれ +4.76 dB / +3.32 dB だった。
補間にも他チャンネルの同じ末尾窓の相関検査を加え、この生成を 0 回にした。
共通の周期を使える左 200 Hz / 右 400 Hz は 100 回とも補間できること、
同じ音の左右への複製で判定が変わらないことも確認する。

### 低い声の倍音を基本周期と誤認する

共鳴を持つ 80 Hz の合成有声音では、修正前は 100 フレーム中 40 回で
2.5 ms を切っていた。真の基本周期は 12.5 ms である。
短い切れ目だけでは一致して見えるが、残りの波形全体の相関は約 0.116 だった。
全体の相関も確認する変更で、この入力の誤圧縮を 0 回にした。

### 周期推定の端と振幅変化で粗い格子の誤差が残る

2026-10-27 の端数補間には改善があったが、140 Hz など探索の上端では
348 サンプルのまま切っていた。真の周期との差は約 5.14 サンプルだった。
元のサンプルレートで近傍の整数位置を正規化相関で比較し、実際に切る位置を選ぶようにした。

下表は定常の倍音を含む有声音を 100 フレーム処理した局所波形差である。
`10 log10(差の二乗和 / 対応する入力の二乗和)` を使い、小さいほど元の周期波に近い。
非定常の発話をこの値だけで音質評価してはならない。

| 基本周波数 |    修正前 |    修正後 |
| ---------- | --------: | --------: |
| 140 Hz     | −13.38 dB | −42.16 dB |
| 180 Hz     | −29.42 dB | −33.98 dB |
| 220 Hz     | −32.20 dB | −38.66 dB |
| 260 Hz     | −28.90 dB | −31.73 dB |

### 穴の両側を必ず 0 へ落とす処理が周期的な音量変動を作る

補間できた場合も、補間の末尾と実音の先頭をそれぞれ 2 ms で 0 へ落としていた。
目標を毎フレーム 1 ms 後ろへ動かす条件では、出力の間隔は 21 ms になる。
この条件の周期成分は 50 Hz 固定ではなく約 47.62 Hz で測る必要がある。

補間の続きを実音の先頭へクロスフェードする方式へ変更した。
同じ波形ならゲインの合計が 1 になり、一度 0 へ落ちない。
形式が変わった場合や補間できない長い穴は、無音へ滑らかに移行する。

フェードを単純に外す対照実験では、純音で約 0.297 の段差が復活した。
したがって、一律に無効化する変更は採用しなかった。

### 日本語の子音では短い穴にも周期補間を使えない

日本語音源を Opus に通すと、周期性の弱い部分では 1 ms の穴の補間も失敗した。
Julius の区間では、目標上昇時に合計 219 ms の短い無音が繰り返された。

既存のフェード幅 (2 ms) 以内に限り、既に届いている直前の末尾と次の先頭を
直接補間するようにした。長い欠落には使わない。
Julius の同じ条件で追加の無音はサンプル丸めの誤差以内になり、最大差分も
0.325 から 0.172 に下がった。0.172 は正常な同じ音源にも含まれる自然な差分である。

### 入力が途絶える側の端を後からフェードできない

実ブラウザで振幅 0.3 の音を 1 フレームだけ渡すと、開始 / 途絶で 0.3 の段差が出た。
次の音が届いてから先頭を落とす処理だけでは、既に鳴り終わる前の音を救えない。

各バッファに GainNode で末尾フェードを仮予約し、連続する後続が届けば実行前に取り消す。
最初の音も滑らかに開始する。通常の境界にはフェードを残さず、先読みの遅延を追加しない。
1 / 8 フレームの実出力で、元の振幅を保ったまま段差が 0.01 未満になること、
通常の境界の振幅が 0.299 を下回らないことを回帰テストで検証する。

実装中の再計測では、開始時刻の端数によって先頭の 1 サンプルだけ既定の gain 1 が通る
現象も再現した。最初の GainNode の初期値も 0 にし、この単発スパイクを除去した。

### 補間のサンプル丸めの後に 1 サンプルの無音が残る

実リレーの Kyoko の WAV で、約 `0.205 → 0 → 0.196` と飛ぶ 1 サンプルの穴を検出した。
このとき内部の境界の最大差分は約 0.037 であり、境界カウンターだけでは検出できなかった。

切り分けの対照実験では、一定値 0.25 のバッファの間に 0.1〜0.49 サンプル分の隙間を
置くと、実 OfflineAudioContext が 1 サンプルの 0 を出した。開始を独立にサンプル格子へ
丸める対策も比較したが、半サンプルの条件で逆に穴と重なりを作ったため採用しなかった。

原因は、補間の長さをサンプル数へ丸めた後も、実音を丸める前の時刻へ置いていたことだった。
20.008 ms の穴では、補間は 960 サンプルで終わるが、実音はその 8 µs 後に始まる。
実際の再生 API を使う回帰テストで、`0.273 → 0 → 0.273` の穴を再現した。
補間で接続できた場合は、実音を補間バッファの実際の終わりへ正確に繋ぎ、
次の予約も実際のバッファの終わりへ合わせるようにした。

また、200 ms の穴に対して補間が上限の 100 ms で終わる条件では、無音の後へ
補間の続きをクロスフェードし、約 0.153 の段差を作っていた。
補間が実音に届かない場合は無音から立ち上げる。
両方の実 Web Audio の回帰テストで、修正後の最大差分が 0.01 未満になることを確認した。
修正後の最終の実リレー配信では、同じ Kyoko / 独立 5 % / 2 回送りの設定で最大差分が約 0.074 となり、
滑らかな波形の間に 1 サンプルだけ 0 が入る候補は検出されなかった。
実回線の到着列は毎回異なるため、この別実行の差だけを修正の因果的な証明には使わない。
原因の再現と修正の判定は、同じ入力を与える実 Web Audio の回帰テストで行った。

### 音声のみの再生で、一度の停滞の遅延が残る

修正前は 180 ms の到着停滞の後、到着基準の再生が約 320 ms の遅延を保ち続けた。
実時間の 6 秒の入力と、実スケジューラーの 60 秒の再現の両方で確認した。
上限や下限を調整しても、後ろへ動かした基準そのものを戻す経路がなかった。

到着 + 目標の深さを超えて溜まった分だけを、既存の 20 ms の不感帯とキューの余裕の中で
圧縮する。実際に圧縮できた分だけ基準も前へ戻す。
60 秒の同じ再現では、最後の遅延が 320.0 から 155.5 ms へ戻った。
回復のために音を捨てず、回復後の新しい穴も作らないことを回帰テストで確認する。
この数値は旧来の 140 ms の深さを残した対照実験であり、最終設定の遅延ではない。

### Datagram の欠落が復号器の出力 timestamp から消える

実 Opus を Object Datagram に格納し、復号前に一部を落とすと、この Chromium の復号器は
入力に 20 / 60 ms の欠落があっても、出力の timestamp を連続した間隔で返した。
たとえば入力 `100000 → 140000` に対して出力は `100000 → 120000` だった。
復号後の AudioData を落とす実験だけでは、この問題を検出できない。

raw Opus の入力パケットの時刻を保持し、対応する復号出力に戻すようにした。
待ち、並べ替え、復号器の再起動は追加しない。PCM は変更しない。
description 付きの形式と他の codec は対象外である。
TIMESTAMP がない入力は `null` として復号器の連続時計を保つ。正当な媒体時刻 `0` は
復元の対象とし、欠落や媒体時刻の巻き戻りの後も `0` へ戻せるように区別する。
2.5 / 5 / 10 / 20 / 40 / 60 ms の実 Opus と直接 / Worker の 12 条件で、
連続欠落を含む入力時刻の保持を検証した。別の実 AudioData の検証で、
ステレオの PCM が完全一致することと所有権の解放も確認した。

raw Opus のチャンクがパケットを持つこと、description の有無で形式が変わることは
[W3C の Opus WebCodecs Registration](https://www.w3.org/TR/webcodecs-opus-codec-registration/)
も参照する。この資料自体から、今回の Chromium の timestamp の挙動は推定していない。

### 短い音声の連続予約で先頭のフェードが消える

2026-10-29 の差分レビュー後、公開 API と実 AudioContext / AudioWorklet で再現した。
振幅 0.3、48 kHz、120 サンプル (2.5 ms) の音声を 2 件続けて予約すると、
最大隣接段差が 0.300000012 になった。1 件の最大段差は約 0.005 だった。
短いバッファでは先頭 ramp の終点と末尾フェードの始点が一致し、末尾を取り消す操作で
先頭 ramp も消えていた。4 ms では時刻の丸め誤差で末尾の始点が先頭の終点より前に入る
場合もあった。

取り消した終点を ramp として復元し、丸め誤差でも末尾の始点が先頭の終点より前へ
入らないようにした。先読みや待ちは追加しない。2.5 / 4 / 5 / 20 ms と、開始時 / 再開後 /
欠落補間後の計 12 条件を 3 回ずつ実行し、全 36 回で最大段差が 0.006 未満になった。
無音化による見かけの改善を除くため、出力の振幅と有効サンプル数も検査する。
現在の回帰テストでは準備音とその補間は振幅 0.1、検査対象は振幅 0.3 とし、0.2 を超えたサンプルだけを
数える。準備音だけが鳴って短い実音が無音になった場合は成功しない。

### 映像の購読解除で音声の予約が逆転する

再レビューで、時刻基準から初めて到着基準へ切り替わる経路を調べた。
公開 API の `hasCounterpart` が `true` から `false` へ変わると、既に予約した音声の終端を
見ずに到着基準を作っていた。100 ms の明示目標で音声を予約し、映像だけの購読解除を
通知すると、後続音の開始が先行音より約 49 ms 前へ戻った。
実 AudioContext / AudioWorklet で、振幅 0.3 の入力に対して出力の最大振幅が
0.600000024 となる重なりを再現した。

到着基準の初期化でも、先行予約の終端より前に置かないようにした。
残った待ちは既存の時間圧縮で回復し、固定の待ちや先読みは追加しない。
任意の目標とフレーム長の PBT、および公開 API と実波形の回帰テストは修正前に失敗し、
修正後に成功した。実波形は最大振幅 0.301 未満を保ち、予約は実際の圧縮後の長さも含めて
順序を維持する。

### 媒体の欠落まで遅延不足として学習する

20 ms の Datagram が失われても、後続の音を遅らせて失われた子音を復元することはできない。
以前は補間できない穴をすべて閉ループへ渡していた。
復号した音の元の timestamp と長さから媒体の欠落を求め、その分を遅延増加の根拠から除外した。
穴そのものは表示用の計器へ残す。実際の到着停滞による不足は引き続き区別して記録する。

### 初期の 80 ms と音声のみの 140〜160 ms の待ちが低遅延を妨げる

音声のみの下限を 50 ms に下げただけでは、壁時計を持つ音声に初期推定値 80 ms が残った。
実ブラウザではメディア時刻の条件が 65 ms 未満でも、壁時計の条件だけが失敗した。
初期値を 50 ms に揃え、同じ検証が両方で通るようにした。

実リレーでは、過去の穴で目標を広げた後に、正常に届く音まで 150 ms 以上待つ回もあった。
超低遅延を優先し、映像へ合わせる相手がない到着基準の深さは 50 ms に収める。
また、既に遅れて届いた音の再開時には、目標の深さをもう一度足さず、
Web Audio が予約できる最も早い位置へ置く。旧処理が余分な待ちを足すことは、
同一入力の単体テストでも失敗を再現して確認した。

50 ms は配送全体の遅延の保証ではない。出力デバイスの先行バッファ、予約の余裕、
一時的なキューの増加も実測する必要がある。
深いバッファで隠せる到着停滞を短い予算で扱うため、穴を完全に消すこととの交換条件がある。
この点は実到着列を固定した 50 / 80 / 100 / 140 ms の再投入でも比較する。

### 日本語の補間の開始にも自然な変化幅を超える段差が残る

Eddy の一部では、周期補間の先頭が直前の末尾から約 0.138 飛ぶのに対し、
正常な同じ音源の最大差分は約 0.110 だった。補間の相関が高いだけでは十分でない。
直前のフレームの自然な差分を超えた開始位置だけを、既存の 2 ms 以内で滑らかにする。
通常の接続と定常の同じ波形には、この処理を加えない。

### キューの遅れが媒体の欠落を吸収すると、穴の計器が 0 でもクリックになる

Grandpa の末尾区間で、圧縮直後にパケットを落とした条件には約 0.215 の段差が残った。
正常な同じ音源の最大差分は約 0.087 だった。
遅れたキューに欠落分が吸収され、再生上の隙間がないと判定されるため、
欠落前後の非連続な波形を直接繋いでいた。

実 AudioPlayoutScheduler と実 AudioPlayoutSession、実 Web Audio を組み合わせたテストで、
20 ms の媒体の欠落と再生上の穴 0 を同時に作り、0.6 の段差を再現した。
再生上の穴がなくても媒体が飛んだ場合は、自然な変化幅を超える先頭だけを 2 ms で滑らかにする。
無音や先読みの遅延は追加しない。実テストの最大差分は 0.01 未満となり、
Grandpa の同じ条件も約 0.087 に戻った。

小さな時計補正を 1 パケットの欠落と取り違えて音を加工しないよう、
この処理は現在のフレーム長の半分以上の跳びに限る。
8 µs の時計補正では元の PCM の変化を保ち、20 ms の欠落だけを接続することも
実 Web Audio で検証した。

## 日本語の全区間の結果

`speech-<音源名>:<区間番号>.json` の 21 件を集計した。
旧実験の区間番号を持たない 5 件は、この集計へ混ぜていない。
毎フレームの目標上昇で生じる 1 ms の人工的な隙間は、21 区間すべてで
サンプル丸めの誤差以内になった (残差の最大は約 `3.0e-9 ms`)。
この条件の最大の隣接サンプル差分は、すべて正常な同じ音源の最大値以下だった。
フレームの周期に対応する包絡成分は、修正前より 8.9〜26.1 dB 小さくなった。
これは操作が加えた周期成分の比較であり、聴感評価の点数ではない。

## 実 QUIC Datagram の日本語配信

実リレーへの配信と購読は同じブラウザで行い、音源を実 AudioContext の MediaStream にし、
高レベル API と実 Worker の Opus へ通した。出力は購読者の MediaStream から記録した。
出力の実形式は 48 kHz / 2 ch であり、下表の波形の解析には第 1 チャンネルを使う。
各条件を約 20 秒観測し、1 秒ごとの統計と出力 WAV を保存した。

| 音源 / 追加の損失            | 届いた Datagram | 追加破棄 | 全 copy が欠落した Object | 受信から再生までの p95 | 補間できなかった穴の合計 |
| ---------------------------- | --------------: | -------: | ------------------------: | ---------------------: | -----------------------: |
| Julius / なし / 1 回送り     |            1004 |        0 |                         0 |                70.2 ms |                 109.0 ms |
| Julius / 独立 5 % / 1 回送り |            1002 |       48 |                        48 |                77.0 ms |                 931.1 ms |
| Eddy / 3 個連続 / 1 回送り   |            1002 |       60 |                        60 |                81.0 ms |                1299.3 ms |
| Kyoko / 独立 5 % / 2 回送り  |            2002 |       90 |                         2 |                69.4 ms |                 193.5 ms |

p95 は計器の末尾 10 秒の窓の値である。観測全体の p95 と同一視しない。
穴の合計には実際の到着停滞も含み、音源中の自然な無音は含めていない。
追加の損失率は乱数への指定値であり、実現した破棄数を別に示した。
4 条件ともエラー通知、再生側の棄却、サンプルレート不一致は 0 だった。
この最終試行の 4 条件では、出力の最大差分は実際の復号入力のフレーム内の最大差分以下だった。

同じ 50 ms の深さでも、中間試行では独立 5 % の p95 が 144.1 ms、3 個連続欠落で
114.0 ms だった回がある。最終値だけから遅延上限を保証してはならない。
後の変更はクリックの接続対策であり、別実行の到着列の違いを遅延の改善へ帰属させない。
これらの中間値は `relay-run-observations.json` にツール出力から転記して残した。
元の JSON は再実行で上書きされており、この要約は生データではない。

また、受信後の待ちだけを送出からの総遅延とは扱わない。
同じフレームの `playoutCatchUp.lagMs + playoutTiming.lastStartDelayMs` を 1 秒おきに
20 点ずつ読むと、送出 TIMESTAMP からデジタル再生開始までの算出値の中央値は
約 121.9〜126.7 ms、観測した最大は約 167.4 ms だった。
これは同一ホスト内の時計による算出値であり、20 点から配送全体の p95 や最大値を推定しない。
物理的な音響の遅延でもない。内訳は `capture-to-start-snapshots.json` に残した。

同じ設定でも実回線の到着列は変わるため、旧設定との別々の実行の差を、そのまま因果的な
改善量にはしない。待ちの深さを比較するため、Julius の 1003 フレームの実復号出力と
スケジューラーの入力を記録し、同一の到着列を実スケジューラーと実 DSP へ再投入した。
この再投入は出力のブラウザグラフを回す実時間試験とは区別する。

| 固定の深さ | 全 20 秒の再生待ち p50 | 全 20 秒の再生待ち p95 | 補間できない穴 |   圧縮量 | 棄却 |
| ---------- | ---------------------: | ---------------------: | -------------: | -------: | ---: |
| 50 ms      |                60.9 ms |                75.7 ms |       109.0 ms | 111.3 ms |    0 |
| 80 ms      |                83.6 ms |                96.2 ms |        20.9 ms |  32.0 ms |    0 |
| 100 ms     |               101.6 ms |               114.7 ms |         2.6 ms |  14.0 ms |    0 |
| 140 ms     |               141.6 ms |               154.7 ms |         2.6 ms |  14.0 ms |    0 |

50 ms では通常の待ちが最小になるが、一時的なキューが増えた区間まで常に 50 ms で鳴るわけではない。
この同一列では最大 113.3 ms、全体の p95 は 75.7 ms だった。
また、相関が足りず圧縮を拒否した出力が 117 件あった。
深い設定が穴を隠せることも確認できたため、「低遅延化してもあらゆる穴が減った」とは結論しない。
今回は常時の深い待ちを避ける判断を採用した。

この再投入の入力は `relay|julius|clean|1.json` の `arrivalTrace`、結果は `budgetReplay` にある。

さらに、実スケジューラーへ渡した `currentTime + minLead - arrivalSeconds` を求めた。
4 条件の予約の下限の最大は 43.4〜43.6 ms だった。今回の 100 ms 超の待ちは、
この出力時計の制約だけでは説明できない。通常の深さを 50 ms にしても、
周期圧縮を適用できない音や、一度に届く音のキューには別の制限が必要である。
この算出値は現在の時計対応による予約の下限であり、機器の物理遅延ではない。

既存の `backlogSeconds` の余裕だけを 250 ms から 0 / 20 / 50 ms へ変える対照も測った。
下表は最も厳しい 0 ms の場合である。到着基準の 50 ms は維持し、
既存の判定で `currentTime + 50 ms` を超える音を捨てる。実回線を再実行せず、
保存した同一の PCM と到着時刻を実スケジューラーと実 DSP へ再投入した値である。

| 実到着列                     | 現設定の最大待ち | 余裕 0 ms の最大待ち |           追加の棄却 | 補間できない穴の合計の変化 |
| ---------------------------- | ---------------: | -------------------: | -------------------: | -------------------------: |
| Julius / なし / 1 回送り     |         113.3 ms |              82.6 ms |   3 フレーム / 60 ms |           109.0 → 117.6 ms |
| Julius / 独立 5 % / 1 回送り |          98.1 ms |              81.6 ms | 19 フレーム / 380 ms |          931.1 → 1205.2 ms |
| Eddy / 3 個連続 / 1 回送り   |          99.1 ms |              82.5 ms |  9 フレーム / 180 ms |         1299.3 → 1396.9 ms |
| Kyoko / 独立 5 % / 2 回送り  |         143.9 ms |              82.5 ms |   4 フレーム / 80 ms |           193.5 → 192.8 ms |

待ちの最大は減ったが、受信済みの発話も失うため、この一律の短縮は採用しなかった。
特に Kyoko は穴の合計がほぼ増えなくても、80 ms の音を追加で捨てている。
穴の計器だけを良くすることと、音を保つことは同じではない。
20 ms / 50 ms の余裕でも、Julius の正常到着の最大はそれぞれ 102.2 / 113.3 ms となり、
値を少し下げるだけで上限が解決するわけではなかった。
結果と入力ファイルの SHA-256 は `replay-relay|*.json` に保存した。
この棄却の比較はブラウザの出力グラフの再収録ではなく、採用する場合は実出力での再検証も必要である。

60 秒のローカル実時間試験も 2 条件で実行した。
Julius の正常到着は 3000 フレーム、穴 0、末尾 10 秒の再生待ち p95 は 66.9 ms だった。
Kyoko に 180 ms の到着停滞を 2 回与えた条件は、3000 フレーム、穴の合計 326.8 ms、
末尾 10 秒の p95 は 67.4 ms だった。両方とも再生側の棄却、開始の予約遅れ、停止時の切断は 0 である。

## 復号前に落とす比較と処理負荷

21 区間それぞれに、損失なし、独立 1 / 5 / 10 %、2 / 3 / 5 個連続欠落、
独立 5 % の 2 回送り、3 個連続欠落の 2 回送りを与えた。計 189 条件である。
実 Opus を実 Object Datagram へ格納し、欠落させた後に実 AudioDecoder へ渡す。
欠落 Object の数、復号出力数、出力の媒体位置の一致も検査する。

固定 seed の Julius の例では、301 Object に対して独立 5 % の 1 回送りで 18 個、
2 回送りで 2 個が欠落した。一方、3 個連続の欠落では、1 回送りと 2 回送りの両方で 18 個を失った。
同時 copy を増やすだけで連続欠落も防げるとは結論できない。
届いたパケットの復号波形にも Opus の状態による差が残る。
元の媒体位置に対応する無損失の復号波形との誤差は、この例の 1 回送りで −16.9 dB、
2 回送りで −52.5 dB だった。復号後だけに欠落を与える実験では、この差を取りこぼす。

DSP の計算負荷も別に測定した。Node.js v24.22.1、48 kHz / mono / 170 Hz の正弦波に
最大 10 ms の圧縮を要求し、500 回のウォームアップ後に 3000 回を 7 組処理した。
組ごとの処理時間の中央値を 1 フレームへ割り戻すと、修正前 4.59 µs、修正後 44.39 µs だった。
約 9.7 倍の増加である。修正後でも、この単独条件の処理時間は 20 ms の 0.23 % 未満だが、
ブラウザ全体、弱い端末、GC の最悪時間の測定ではない。
負荷増加を隠して「音質だけ改善した」とは扱わない。生データは `dsp-cpu-node.json` にある。

## 残る課題

- 非周期的な子音の 20 ms 以上の欠落は、今の周期補間で復元できない。実リレーの連続欠落でも穴が残った
- 48 kHz / 80 Hz の純音と有声音は、現行の 20 ms の履歴では 100 フレームとも補間できなかった。低い声のための過去の履歴の拡張は、先読みを足さずに検討できるが、今回は実装していない
- 同時送信の copy は、同じ連続損失で一緒に失われ得る。独立損失での冗長化の効果と区別する必要がある
- 実到着列の比較で、50 ms の予算でも瞬間的な待ちが 143.9 ms になった。既存のキューの余裕だけを減らすと受信済みの発話を失う。低遅延を維持するためのキューの制限と、非周期音を保った短縮は残る課題である
- ブラウザ内の PCM の連続性と、聞き取りやすさ、機器から実際に出る音は同じ評価ではない。人の自然会話の音源量、話者数、実機の音響評価も不足している
- 今回の追加損失の列は固定 seed で再現可能にしている。すべての損失列、順序逆転、物理回線上の輻輳を網羅したものではない

欠落がない場合の余計な音量変調と、失われた発話の内容の復元は別の課題である。
計器の穴を 0 にするために 140〜160 ms の待ちを戻すことや、相関の閾値を下げて
無理に子音を周期音へ変えることは、今回の改善には含めない。

## 測定器の検証

実時間の AudioWorklet では `currentFrame` に重複と飛びが観測された。
初版の収録器がこの値を配列の書き込み位置に使ったため、上書きと偽の無音を作っていた。
収録順に PCM を連結し、時刻の異常は別の値へ保存する方式に修正した。
時刻の重複を音声欠落と同一視してはならない。

この影響を受けた `run-1/` / `run-2/` の実時間の波形差分は、改善量の根拠から除外する。
`before-fix/` の実時間データは収録器を修正した後の値である。
音声中の自然な無音もあるため、日本語の `silenceMs` の全量を playout の欠陥として数えない。

サンプルレート不一致の対照実験では、48 kHz の 20 ms の一定値のバッファを
44.1 kHz の OfflineAudioContext に並べると 98 サンプルで振幅が 2 倍になり、
48 kHz に揃えると 0 サンプルだった。一方、今回の実時間の正弦波では同じ異常を
検出しなかった。不一致カウンタは条件の検出器であり、クリックが実際に出た証拠ではない。

## 評価を変える必要がある点

- `gapCount = 0` と境界カウンタだけでは、周期的な音量変動を検出できない
- 日本語の自然な子音は純音より差分が大きい。固定の振幅閾値だけでクリックと判定しない
- 圧縮量だけで良否を決めない。音を保つための拒否と、遅延を回復できない状態を区別する
- 遅延上限を増やす実験には、到着停滞を止めた後の回復も含める
- 元の音に含まれる無音、Opus による変化、playout の追加の穴を分ける

`AUDIO_PLAYOUT_RESULT.md` の「格子に乗らない純音では補間が働かない」という記述は、
現在の実装と測定結果には当てはまらない。また、過去の到着の裾と圧縮量の相関だけでは、
到着の裾が圧縮を直接発生させたとは判断できない。目標の移動とキューの余裕も必要である。

## 確認の範囲

出力グラフと購読者の MediaStream の PCM を測定している。
HTML の audio 要素と機器から実際に鳴るまでの追加の待ちは測っていない。
実リレーでは QUIC Datagram を使うが、指定した追加の欠落は受信境界で復号前に注入する。
物理回線上のパケットを破棄した場合の輻輳制御の変化までを再現した実験ではない。
スピーカーからマイクへ戻す音響ループバック、Bluetooth 機器、Safari / Firefox は含めていない。
長い欠落や未来の子音の内容を復元できることも保証しない。
今回確認したのは、再現した不連続を滑らかにすること、短い人工的な穴を埋めること、
通常の音を周期的に弱めないこと、停滞後の余分な遅延を回復できることである。

実リレーへの接続では、途中の試行に Opening handshake failed / session closed もあった。
これらを音質の成功として数えず、20 秒の実出力と十分な Datagram 数を確認できた回だけを
測定結果へ採用する。

測定ケースを開始前に確定し、フィルターに一致するケースが 0 件なら、環境記録も更新せずに
失敗する。実行対象のケースの一覧は環境記録へ残す。
A/V の音声、映像、対応する組の必要数は、集計から除外する初期 1 秒を引いた観測時間で
求める。最短の 2 秒でも正常な出力を採用し、空の観測は拒否する。
測定中の未処理のページ例外はケースごとに記録し、収録できていても不採用にする。
音声だけの実リレーの計測も配信中と停止時のエラーを分け、配信中のエラーを採否へ反映する。

音源が見つからない場合の 3 経路も、実ブラウザの WebAudio 状態通知で検査した。
修正前は失敗後もリアルタイムの AudioContext が running のまま残っていた。
