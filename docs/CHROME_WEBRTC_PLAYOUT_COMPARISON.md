# Chrome の WebRTC と SDK の音声再生の比較

記録日: 2026 年 10 月 31 日。

この文書は、続き音を準備する改善前の SDK を固定した比較結果である。
その後の実装と比較測定は CHROME_AUDIO_CONTINUATION_IMPROVEMENT.md に記録する。

36 条件の同時比較では、SDK は WebRTC より短い遅延を保つ一方、遅着時に活動中の無音が残った。
繰り返す 60 ms の遅着では、WebRTC の遅延の中央値は、対になる SDK より約 34.1〜57.7 ms 長かった。
今回の設定のままで、短い遅延と WebRTC と同程度の連続性を両立できたとは判断しない。

## 結果

Google Chrome 156.0.8078.79 / macOS arm64 で、12 条件を各 3 回測定した。
36 条件すべてが有効で、各 335 パケット、合計 12,060 パケットの受信内容と送信内容が一致した。
再復号 PCM と原音の独立レンダリングの最大差は、どちらも全条件で 0 だった。
空のペイロードの通知は合計 880 件で、別の受信列に保存した。

繰り返す遅着の遅延 p95 は、Julius で SDK が約 100.4〜103.0 ms、WebRTC が約 114.4〜130.0 ms、

未分類の数値上の無音も残った。全条件の範囲は SDK が 0〜173.1 ms、WebRTC が 0〜68.5 ms だった。
自然な休止や発声前後も含み、この値の全量を音切れとはしない。
逆に、未分類を取り除いた活動中の無音の列だけで、欠落の全量を測れたとも扱わない。

局所照合の採用率は、活動窓に対して SDK が約 62.6〜100 %、WebRTC が約 68.3〜100 % だった。
採用率が低い条件の中央値は、採用した窓に対する値であり、残りの窓の遅延を保証しない。
すべての活動窓の候補相関と、採否を解析結果に保存した。

WebRTC 側で観測した 10 ms の無音も結果に含めた。
これは受信 track を Web Audio に接続して収録した経路の観測であり、NetEq 単体の欠落と特定していない。
NetEq の統計と、その後のブラウザー内の接続を切り分ける必要がある。

遅延と活動中の無音の散布図を latency-and-silence.png、
Julius / 繰り返す 60 ms の遅着 / 48 kHz / 1 回目の推移を latency-trajectory.png として保存した。
推移の図では、WebRTC の遅延が増加した後も、SDK は短縮しながら遅延を戻していることが分かる。
無音や相関の低下が残ることも併記し、短縮だけを改善と扱わない。

## 比較の対象

方式を変更する前に、Chrome の実 WebRTC と現在の SDK の音声再生を比較する。
同じ受信パケットを使い、遅延と波形の変化を同時に測定する。
対象は音声のみの再生であり、本測定中は再生本体を変更しない。

日本語音声の Julius と Kyoko を各 6 秒使う。
正常到着、0〜30 ms の遅着、繰り返す 60 ms の遅着を、44.1 / 48 kHz の出力で測定する。
各条件を 3 回ずつ、同時に走らせず収録する。
遅着の条件は送信変換で後続を追い越させずに作る。
パケット損失、順序逆転、WebTransport / QUIC の接続を再現する試験ではない。

SDK の設定は従来の 50 ms の予算を保つ。
WebRTC の受信バッファは Chrome の自動制御のままとする。
同じ名前の目標値を設定した比較や、実出力遅延を揃えた比較ではない。

## 同じ入力と時計の確認

[WebRTC Encoded Transform §2 / §5](https://www.w3.org/TR/webrtc-encoded-transform/) の受信変換で、
復号前の Opus フレームを複製する。これは策定中の仕様であり、実装は変わり得る。
元のフレームを変更せずに Chrome へ戻し、複製だけを SDK の実 WebCodecs デコーダーへ渡す。
送信側も保存して、受信側の RTP タイムスタンプと全ペイロードのバイトを照合する。

受信変換には空のペイロードの通知も届いた。
固定した上流コミット `031cc215615895d7ae039d4098c2716d7acf2dc3` の
[ChannelReceive::OnReceivedPayloadData](https://webrtc.googlesource.com/src/+/031cc215615895d7ae039d4098c2716d7acf2dc3/audio/channel_receive.cc) は、
空のペイロードを NetEq に投入しない。
計測器もこれらを音声パケットや復号エラーに混ぜず、別の受信列に保存する。
空でないパケットの不一致は失敗とする。

収録する経路は次の 4 つである。

1. 符号化前の原音
2. Chrome の実 WebRTC の受信音声
3. 現在の SDK の再生音声
4. 同じ Opus の復号 PCM を加工せず、200 ms の余裕で連続予約した参照音声

全経路を同じ AudioContext の AudioWorklet へ接続する。
受信音声は音声要素で取り出しを駆動し、同じ track を Web Audio の接続で収録する。
受信統計と PCM の両方で、WebRTC の取り出しが動いていることを検査する。
200 ms は解析用の参照経路だけの値であり、SDK の設定は変えない。

原音の収録は独立した OfflineAudioContext のレンダリングと照合する。
AudioWorklet 内の独立した連番、例外、参照の予約不足、SDK の再生結果も検査する。
保存した Opus を別の実デコーダーへ再投入し、全フレームの時刻、長さと全サンプルの一致も確認する。
API のモックやスタブは使わない。

解析用には全経路の PCM を量子化前の Float32 / little endian で保存する。
視聴用の PCM16 WAV と分け、微小な値が量子化で 0 になることを無音判定へ混ぜない。
ソース、測定コード、音源と実行環境を記録する。解析時には JSON と各 Float32 ファイルの SHA-256 も残す。

## 測定値の定義

### 遅延と波形の照合

120 ms の窓を 40 ms ごとに移し、平均を除いた正規化相互相関で局所的に時間を合わせる。
全出力へ 1 個の遅延を当てはめると、時間伸縮を波形の誤差と混同するため、区間ごとに求める。
粗い探索だけに平均化した信号を使い、採用する遅延と相関は元の全サンプルで求める。

参照の RMS が 0.003 以上の窓を活動窓とする。
相関が 0.8 以上で、3 ms より離れた別の相関ピークとの差が 0.015 以上の場合に採用する。
採用できなかった窓も件数と候補の相関を保存する。
相関が高い区間だけを選んで、その中央値を音質全体の順位に使わない。

まず加工しない復号参照と原音を照合する。
この参照経路の採用窓が 10 個以上あり、遅延の p10〜p90 が 2 ms 以内の場合に、その中央値を基準にして、
WebRTC と SDK の復号参照に対する局所遅延を原音基準へ換算する。
参照の推定に十分な区間がない場合や、安定しない場合は換算値を出さない。
原音との直接の照合結果と、参照経路の推定の分布も残す。

ここでいう遅延は、符号化前の Web Audio 原音から収録用 Worklet までの波形上の時間差である。
ブラウザー内の異なる経路の待ちを含み、NetEq 単体のバッファ遅延ではない。
Bluetooth やスピーカーまでの実音響遅延も含まない。
相関は波形の一致度であり、MOS や聴感品質の推定値ではない。
整数サンプルで時間を合わせているため、再標本化やサンプル未満の位相差でも相関は低下し得る。
この相関から、雑音の量やその原因を確定しない。

### 活動区間中の数値上の無音

出力の絶対値が 1e-7 未満で 0.5 ms 以上続く区間を調べる。
このしきい値は -140 dBFS に相当する。
前後 250 ms 以内にある相関 0.95 以上の照合点から、対応する参照位置の範囲を作る。
前後で遅延が変わる場合は、その間のすべての遅延に、さらに左右 2 ms の余裕を加える。
どの位置に対応させても復号参照の RMS が 0.003 以上の場合だけ、活動区間中の無音とする。

すべての候補が静かなら原音の休止として区別する。
両方の可能性がある場合、前後の照合点がない場合や収録範囲を外れる場合は未分類とする。
活動区間中と確認できた無音は下限であり、未分類を 0 ms と解釈しない。
また、補間音は無音にならなくても劣化し得るため、この値だけを音質の順位にしない。

SDK の予約空白も別の値として残す。
WebRTC の jitterBufferDelay / jitterBufferEmittedCount は平均の受信バッファ遅延であり、
上記の波形による原音基準の遅延とは異なる。
concealedSamples、挿入と削除のサンプル数はウォームアップを含む累積値であり、発話中の劣化量とは扱わない。
統計の定義は [WebRTC Statistics §8.5](https://www.w3.org/TR/webrtc-stats/#rtcinboundrtpstreamstats-dict*) による。

## 再実行と計測器の検証

PLAYOUT_BROWSER_CHANNEL を chrome、PLAYOUT_AV_SECONDS を 6 として、
investigate-playout-audio.mjs の webrtc モードを 3 回順番に実行する。
各実行の保存先を summarize-webrtc-playout.mjs に渡すと、収録完了、入力と再復号を検査して解析する。
収録中はソースを固定し、他の実時間計測、解析、ビルドや全テストと同時に走らせない。

計測器では既知の遅延、音量比、途中で変わる遅延、自然な休止、活動区間中の欠落を試験する。
遅延を一意に決められない単一周期波を採用しないこと、長さ違いと非有限値を拒否することも確かめる。
粗い探索が隣の小ピークを選ぶ問題は、既知の遅延を全採用窓で検査する試験で検出した。
別ピークと区別しない 3 ms の範囲全体を、元のサンプルで探索し直すよう修正してから本解析した。

保存した解析結果は、別プロセスの NumPy でも検証した。
採用した 8,767 窓の相関を再計算し、最大差は約 1.98e-14 だった。
活動中と分類した 84 区間の無音と、対応位置の全候補の参照 RMS も直接再計算して一致を確認した。
単体テストと PBT は 4,310 件成功し、vp check と型検査も成功した。

## 結果の解釈

本測定では、現在の設定による待ちと連続性の違いを確認する。
バッファの増加で無音が減った場合も、遅延を併記する。
同程度の実出力遅延での優位性、日本語の聴感、Bluetooth の症状の解消は、別途確認する。
次の比較では実出力遅延の差を揃え、時間伸縮、補間と復帰の違いを確認する。
