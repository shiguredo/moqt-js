# 音声 playout の見直し (2026-11-06)

「途切れ、プチプチ音が出る」という報告を受け、復号出力の時刻対応、予約、時間伸縮、
欠落補間、レート変換、停止と再開、DevTools の出力を確認した。
比較元は `8dfbdbcb`、修正側はこの変更を含む作業ツリーである。
最終の音声計測に使ったソース全体を fingerprintTree で集計した SHA-256 は
`48474b6c1cd6bec89d9aac1a16e98a0a1379382a11788cca17ef5acd2eee3cb3` である。
計測後は audioPlayout.test.ts と audioPlayoutTimingStats.ts の説明コメントだけを更新した。
実行コードは変更していない。

## フレーム境界での波形破損

欠落のない連続波形でも、短いフレームに分割すると出力に誤差が出た。
従来の出力はフレームごとに AudioBufferSourceNode を開始、停止していた。
端数の出力位置では隣のフレームのサンプルを補間に使えず、末尾へ追加した一定値の余白も
元の波形の続きにはならない。入出力がともに 48 kHz の場合も再現した。

実音の PCM と予約位置を同じメッセージで AudioWorklet へ渡し、AudioRenderQueue が
連続した PCM として読む方式へ変更した。出力時計から入力の端数位置を求め、
連続する次フレームが届いていれば、その先頭を補間に使う。
欠落を挟む次フレームは先読みに使わない。音の加算や通常境界へのフェードは必要ない。

線形補間は、確認した [Chromium の AudioBufferSourceNode の処理](https://chromium.googlesource.com/chromium/src/+/HEAD/third_party/blink/renderer/modules/webaudio/audio_buffer_source_handler.cc)
と同じ方式である。チャンネルの拡張は [Web Audio API §4.4](https://webaudio.github.io/web-audio-api/#channel-up-mixing)
に従い、ステレオへのモノラルの複製と 5.1 の中央チャンネルの割り当てを区別する。

## 欠落からの復帰中に起きる再欠落

復帰の 2 ms のクロスフェード中に再び欠落すると、未加工の PCM の末尾から予測音を
作っていた。最後に描画した混合済みの音とは異なるため、固定した入力で約 0.444 の
振幅段差が出た。最後に描画した値から新しい予測音へ接続するよう修正した。
通常の欠落開始も、自然な波形の変化幅を超える段差がある場合は滑らかに接続する。

## 描画中のチャンネル拡張

欠落補間中にモノラルからステレオの先行予約を受けると、出力幅の拡張時に履歴と予測音を
捨てていた。実 OfflineAudioContext で出力が 0 へ落ち、約 0.267 の振幅段差を再現した。
停止フェード中の拡張も、追加したチャンネルへ停止値を引き継いでいなかった。

出力幅を広げるときは、履歴、予測、最後の出力、停止値をチャンネル配置に沿って複製する。
履歴は左右で別の配列を持ち、後続のステレオを書き込んでも相互に上書きしない。
復帰と停止の進行位置も保つ。

描画前にすべてを予約する従来の試験では、この途中の状態消失を検出できなかった。
描画を補間中に止めて予約する試験と、実時計で 20 回拡張する試験を追加した。
各回で補間区間を収録し、後続の左右逆相のステレオも独立して出力することを検査する。
実時計の試験は、実行環境が止まって拡張や予約が間に合わなかった回を判定に使わず、
間に合った 20 回を最大 60 回から集める。

## Firefox のステレオ出力

Firefox `157.0` では、入力未接続の Worklet は channelCount を 2 にしても、出力が
1 チャンネルのままだった。左右が異なる PCM を渡しても、左の音が両側へ出た。
SDK とは独立したネイティブの Worklet でも、Offline と実時計の両方で同じ挙動を再現した。

チャンネル配置を伝える無音の ConstantSourceNode を接続し、出力幅を伝播させる。
実音は PCM キューから生成する。終了と処理例外のどちらでも無音入力と graph を解放する。
出力数と入力の関係は [Web Audio API §1.32.4.3.2](https://www.w3.org/TR/webaudio/) を参照した。
修正後は Firefox と WebKit `27.2` のステレオ、形式変更、実時計での 20 回の拡張が成功した。

## 波形の比較

Chromium `156.0.8078.4` の実 OfflineAudioContext を使った。
173 Hz と 3,109 Hz を重ねた 2 秒の波形を可変長フレームに分け、同じ入力を単一の
AudioBufferSourceNode で鳴らした出力と比較した。開始位置は出力サンプルの格子から
0.37 サンプルずらし、開始と終了の各 10 ms を評価から除いた。

| 入力 → 出力 (Hz) | 修正前の最大振幅誤差 | 修正後の最大振幅誤差 | 修正後の信号対誤差比 (dB) |
| ---------------- | -------------------: | -------------------: | ------------------------: |
| 48,000 → 48,000  |             0.022034 |       0.000000014901 |                    163.65 |
| 48,000 → 44,100  |             0.030163 |       0.000000014901 |                    153.35 |
| 16,000 → 48,000  |             0.086993 |       0.000000014901 |                    153.23 |
| 16,000 → 44,100  |             0.093245 |       0.000000014901 |                    158.34 |
| 44,100 → 48,000  |             0.031801 |       0.000000014901 |                    151.11 |

振幅は Float32 PCM の値である。信号対誤差比は参照出力と差分のエネルギー比であり、
聴感の品質スコアではない。これは欠落のない連続区間の比較であり、失われた発話を
完全に復元できるという意味でもない。

最終版でも同じ 5 通りを再測定し、ソース版と SDK の配布物の両方で表と同じ値を得た。
配布版も同じ比較関数を使い、dist から読み込んだ実セッションの出力を評価する。

## 日本語音声と制御した欠落

Google Chrome `156.0.8078.80` で Julius と Kyoko の音源を使い、44.1 / 48 kHz と
通常到着、最大 30 ms のジッター、周期的な 60 ms の追加遅延、途中からの 60 ms の
追加遅延を組み合わせた 16 条件を各 10 秒で測定した。
受信 transform で複製した Opus を使い、保存パケットの再復号と PCM の一致も検査する。

全 16 条件で入力 PCM と保存パケットの再復号誤差は 0、収録連番の欠落と処理例外も 0 だった。
ブラウザーが報告した出力の underrun は 0、発話区間と確認できた位置での完全な無音も 0 だった。
ただし、発話の有無を判定できなかった完全な無音は、条件ごとの合計で 0 ms から 152.04 ms 残る。
この判定不能区間を正常と扱って、音切れが無いと断定しない。

復号参照の遅延が 10 窓以上で推定でき、中央 80 % の幅が 2 ms 以下の条件だけで、
原音の時刻へ換算した遅延を集計した。13 条件が成立し、Kyoko の 48 kHz の通常到着、
ジッター、途中からの追加遅延の 3 条件は遅延集計から除外した。

| 到着条件                | 成立した条件数 | 条件ごとの遅延 p95 の範囲 (ms) |
| ----------------------- | -------------: | -----------------------------: |
| 通常到着                |              3 |                 45.77 ～ 48.23 |
| 最大 30 ms のジッター   |              3 |                 69.94 ～ 74.08 |
| 周期的な 60 ms の遅延   |              4 |                99.08 ～ 104.15 |
| 途中からの 60 ms の遅延 |              3 |               106.94 ～ 109.46 |

これはブラウザー内で対応が確認できた波形の遅延であり、機器から耳までの遅延ではない。
比較元と修正側へ同じ PCM と予約を再投入する検査も、全 16 条件で開始位置と長さの差は 0 だった。

比較元と修正側は同じ Context で鳴らす。Worklet の登録名が衝突した最初の収録は無効として
除外した。採用した比較元は `8dfbdbcb` から取り出し、audioOutputRenderer.ts と
audioRenderProcessor.ts の登録名だけを別名にした。DSP と予約の処理は変更していない。

符号化パケットへ欠落を加えるローカル試験も、各 6 秒で測定した。
これは回線の輻輳を含む試験ではない。

## 60 秒の出力と実リレー

各 60 秒の日本語音声を実出力で収録した。到着停止は約 1 秒と 31 秒の位置で各 180 ms とした。
通常到着では 3,000 フレームを再生し、補間不能区間は 0 だった。
停止条件も 3,000 フレームを再生したが、最大 100 ms の予測音では埋めきれず、
2 回、合計 129.33 ms の補間不能区間が残った。最大の 1 区間は 73.35 ms だった。

10 秒から 28 秒、および 40 秒から 58 秒の開始待ち時間の中央値は、通常到着で 50.20 → 50.50 ms、
停止条件で 67.19 → 68.74 ms だった。この 60 秒では待ちが積み上がる挙動は見られなかった。
数時間の実出力を連続収録した結果ではない。

6 つの欠落条件と 2 つの 60 秒条件では、収録連番の欠落、収録器と描画器の例外、
drain による切断はすべて 0 だった。すべて予約終端より後まで収録した。
ブラウザーの currentFrame の重複と飛びは別に記録し、Worklet 内の処理サンプル連番で
収録メッセージの欠落を検査した。重複する時計表示を、欠けた PCM と同一視しない。

実リレーの全体試験は 36 件が成功した。ただし、60 秒の実配信では最大受信遅延が
182 ms となり、約 27 ms の補間不能区間が 1 回あった。
合格件数を、実回線で音切れが一切ないという意味では使わない。

採用した最終収録は、investigation-logs/playout-quality-2026-10-28/runs/ の次の記録にある。

- 日本語音声: `2026-11-05T18-56-56.662Z-21008-webrtc`
- 制御した欠落: `2026-11-05T19-02-32.690Z-22126-datagramLive`
- 60 秒の出力: `2026-11-05T19-03-18.153Z-22335-long`

## 検証する境界

- 任意の Float32 PCM、分割位置、描画量子、入出力レートを変えても、単一 PCM と同じ出力になること
- 6 時間以上先のサンプル位置を与える境界試験でも、時刻の丸め誤差でフレーム境界を切らないこと
- DC と周期波の連続性、短いフレーム、圧縮と伸長、低い声の欠落補間
- 60 ms の実メインスレッド停止、到着の停滞、A/V 同期と遅延からの回復
- モノラル、ステレオ、複数チャンネル、停止後の予測音、drain と出力の再作成
- 閉じた出力への投入を失敗として報告し、元の AudioData と PCM の所有権を壊さないこと
- SDK の配布物からの AudioWorklet の読み込みと実出力

再実行には `vp test run` と、通常版および配布版の Playwright プロジェクトを使う。
出力のブラウザー間の確認には `--project=firefox-playout --project=webkit-playout` を使う。
両プロジェクトでは、ネイティブのリサンプラーとの一致を要求する 44.1 kHz の試験を除外する。
実リレーの条件は接続設定を環境から読み込み、relay のプロジェクトで別に検証する。
Bluetooth 機器やスピーカーからの実音はこの波形比較に含まない。

検証結果は、単体およびプロパティテスト 4,462 件、計測器の検査 6 件、
通常版および配布版の E2E 300 件、Firefox と WebKit の出力 E2E 11 件、
実リレー E2E 36 件が成功した。実リレーの調査専用など 11 件は、既定の実行条件に従って
スキップした。Firefox の OfflineAudioContext の途中停止は未対応のため 1 件をスキップし、
実時計の 20 回の拡張試験で補った。
SDK と DevTools のビルド、型検査、型情報付き lint、変更したファイルの整形も成功した。
初回の全体の `vp check` は、既存 Markdown の整形違反 1 件で未通過だった。
コミット前に当該ファイルの整形だけを修正し、全体の `vp check` も成功した。
