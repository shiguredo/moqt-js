# 音声の再生遅延の下限の実測 (調査メモ)

到達点のまとめは `docs/AUDIO_PLAYOUT_RESULT.md` にある (数値・規格との対応・既知の限界)。

この文書は調査の記録である。決定の記録は `docs/AV_SYNC_DECISIONS.md` が持つ。ここには
測り方、生の値、判断に至った理由、未解決のまま残したことを書く。

## 目的

音声の再生遅延の下限 (`AUDIO_PLAYOUT_DELAY_FLOOR_MS` と `AUDIO_DELAY_FEEDBACK_MIN_MS`) は
80 ms であり、libwebrtc の NetEq の初期値 (`AUDIO_DELAY_START_MS`) をそのまま採った値で、
この経路では測られていなかった (`docs/AV_SYNC_DECISIONS.md` 決定 4 の「根拠が薄い点」)。
「超低遅延」を名乗るには、この値を実リレーで測り直す必要がある。

## 方法

- 実リレー `moqt://sora-moq.shiguredo.co.jp/` へ、1 つのブラウザのページから音声と映像を
  配信し、同じページで購読する (`tests/e2e/relay/devtools-both-audio.spec.ts` の
  「長時間の配信で、送信の遅れと受信の遅れが悪化しない」と同じ条件)
- 観測は 60 秒。`AUDIO_PLAYOUT_DELAY_FLOOR_MS` と `AUDIO_DELAY_FEEDBACK_MIN_MS` の 2 つを
  30 / 50 / 80 ms に変えて、各 3 回を交互に実行する (時間帯による経路の条件の違いを、
  下限の違いと混ざらないようにするため)
- 実行は、定数を書き換えて各条件を交互に繰り返す (当時の A/B 用のスクリプトは作業環境の
  ものであり、リポジトリには含めていない)。生のログは `investigation-logs/` へ置く
  (`.gitignore` に登録済み)
- 1 秒ごとの観測は `tests/e2e/relay/investigation-audio-delay.spec.ts` が行う。調査専用であり、
  CI を遅くしないよう `MOQT_INVESTIGATION=1` のときだけ動く (既定では skip する)。実行例:

  ```
  MOQT_INVESTIGATION=1 npx vp exec playwright test --project=relay \
    --grep "調査: A/V 同期と音声の遅延の内訳を"
  MOQT_INVESTIGATION=1 npx vp exec playwright test --project=relay \
    --grep "調査: 音声の出力の遅れを測る"
  ```

  `音声の出力の遅れを測る` の方は、`AudioContext` の `getOutputTimestamp()` と `outputLatency`、
  `baseLatency` を外から読む (`installAudioOutputProbe` でページへ仕込みを入れる)。値は
  `investigation-logs/audio-output-*.jsonl` に書く

  別プロジェクトが port 5173 を使っている環境では、`playwright.config.ts` と
  `tests/e2e/relay/support.ts` のポートをずらしてから実行する
  (`MOQT_DEVTOOLS_URL` でも devtools の URL を差し替えられる)

- 見た値は、適用中の目標 (`avSync.delays.audioDelayFeedback.appliedMs`)、鳴り始め
  (`audio.playoutTiming.startDelayMs` の p50)、時間圧縮 (`audio.playoutCompressedMs`)、
  補間 (`audio.playoutConcealedMs`)、鳴らせなかった音 (`missedFrames`)、基準の取り直し
  (`audio.playoutRebases`)、警告

## 結果

下限ごとの範囲 (60 秒の観測、3 回ずつ。経路が静かな回の値である)。

| 下限  | 適用中の目標 | 鳴り始め p50 | 時間圧縮 / 60 秒 | 補間     | 基準の取り直し  | 警告 |
| ----- | ------------ | ------------ | ---------------- | -------- | --------------- | ---- |
| 80 ms | 80 ms        | 78.6〜95.3   | 5〜9 ms          | 0〜17 ms | 0               | 0    |
| 50 ms | 50 ms        | 45.6〜67.7   | 32〜65 ms        | 0〜8 ms  | 0               | 0    |
| 30 ms | 30〜40 ms    | 34.6〜56.8   | 496〜1143 ms     | 0〜48 ms | 3 回中 1 回で 2 | 0    |

- 適用中の目標は、揺らぎの学習 (NetEq) が下限を超えていなければ下限そのものになる。
  下限を 80 から 50 へ下げると、鳴り始めが約 30 ms 下がる (実測 78.6〜95.3 → 45.6〜67.7 ms)
- 揺らぎの学習が下限を超えた回 (jitter 100〜140 ms) は、どの下限でも適用中の目標が上限の
  100 ms になり、鳴り始めは 111〜115 ms だった。下限は経路が静かなときだけ効く
- 30 ms は時間圧縮が 1 桁増える (496〜1143 ms / 60 秒)。目標が小さいほど、到着の尾
  (0.95 分位を超える 5 %) が目標を超えて詰めの対象になるためである。加えて 3 回のうち
  1 回で基準の取り直しが 2 回出た
- 50 ms の圧縮 (32〜65 ms / 60 秒) は鳴らす音の 0.1 % 程度であり、語尾が切れる捨て
  (`missedByReason.backlog`) と鳴らせなかった音は増えない

## 判断

`AUDIO_PLAYOUT_DELAY_FLOOR_MS` と `AUDIO_DELAY_FEEDBACK_MIN_MS` を 50 ms にする。遅延を
約 30 ms 下げ、品質の劣化 (時間圧縮) を 0.1 % 程度に保てるためである。30 ms は採らない。

`AUDIO_DELAY_START_MS` (NetEq の開始値 80 ms) は移植元の値であり、変えない。閉ループの
初期値 (`AUDIO_DELAY_FEEDBACK_START_MS` = 100 ms) の方が大きいため、実際の経路では観測が
始まるまで 100 ms が使われ、開始値は見えない。観測が 1 つでも届けば閉ループが実測から
下げる。

## 規格との突き合わせ

- ITU-T G.114 (05/2003) は「対話性の高い用途は 100 ms 未満の遅延でも影響を受け得る」
  「150 ms 未満に抑えれば多くの用途で有意な影響はない」とする。鳴り始め 45.6〜67.7 ms に
  経路の遅れ (実測 17〜23 ms) を足した値はこの範囲の内側である
- ITU-R BT.1359-1 (11/1998) は「許容できる遅れは 30 ms、進み側の限界は 22.5 ms」とする。
  不感帯 (`SYNC_MIN_DELTA_MS`) の 30 ms はこの許容限界と同値であり、進み側だけを見ると
  規格より広い。実測の定常のずれ (`baseDifferenceMs`) は 6〜8 ms であり、規格の内側に収まって
  いる
- EBU R37 (2007) は各段で「音声が 5 ms 進み〜15 ms 遅れ」、端から端まで「40 ms 進み〜
  60 ms 遅れ」を推奨する。E2E の判定に使う 150 ms (`AV_SKEW_MAX_MS`) はこの推奨より広い。
  これは利用者に見えるずれの目標ではなく、runner の処理能力と実装の不具合を分けるための
  上限である

## 経路が跳ねた回の観測 (未解決)

18 回の観測のうち 6 回で jitter が 100〜140 ms になり、そのうち 2 回で警告
`syncExtraDelayPinnedAtLimit` が出た。出た回の値は次のとおりである。

| 下限  | jitter | applied | 鳴り始め p50 | syncExtraDelayMs | baseDifferenceMs | 持続  |
| ----- | ------ | ------- | ------------ | ---------------- | ---------------- | ----- |
| 80 ms | 140    | 100     | 98.2 ms      | 100 ms           | 47.1 ms          | 13 秒 |
| 30 ms | 140    | 100     | 78.8 ms      | 100 ms           | 48.6 ms          | 15 秒 |

jitter が 140 ms でも警告が出ない回があり (4 回)、警告の条件は「音声の jitter buffer が
上限の 100 ms まで伸びる」ことと「2 つのトラックの基準の差 (`baseDifferenceMs`) が普段の
6〜8 ms から 47〜49 ms へ広がる」ことが重なったときである。同期の補正は 100 ms で頭打ちに
なるため、`|表示の遅れの差| - 100 ms` に当たる 47〜49 ms が A/V のずれとして残る。

未解決の点は、この 47〜49 ms の基準の差が「実在の相対遅延」なのか「跳ねに押し上げられた
窓の最小値 (計測の跡)」なのかである。次の計測で切り分ける。

1. `baseDifferenceMs` と、トラックごとの `baseDelayMs` を 1 秒ごとに 60 秒採る
   (`tests/e2e/relay` の観測ループに 1 行足す)
2. 跳ねの前後で両方のトラックの最小値が同時に動くなら計測の跡、片方だけ動くなら実在の
   相対遅延である
3. 実在なら補正の予算 (100 ms) の掛け方を、計測の跡なら基準の推定の窓の取り方を直す

1 秒ごとに採る」で 60 秒 × 8 回採った (`investigation-logs/av-sync-samples-*.jsonl`)。

| 1   | 120 ms        | 130 ms           | 7.2〜8.8 ms    | 16.8〜17.5 ms | 8.7〜9.6 ms  | 0    |
| 2   | 140 ms        | 220 ms           | 6.6〜8.7 ms    | 16.6〜17.5 ms | 8.8〜10.0 ms | 0    |
| 3   | 160 ms        | 161 ms           | 5.6〜8.8 ms    | 16.5〜17.5 ms | 8.5〜10.4 ms | 0    |
| 4   | 120 ms        | 117 ms           | 7.0〜9.7 ms    | 16.8〜17.8 ms | 8.1〜9.8 ms  | 0    |
| 5   | 280 ms        | 159 ms           | 6.9〜8.6 ms    | 16.7〜16.9 ms | 8.9〜9.9 ms  | 0    |
| 6   | 120 ms        | 121 ms           | 6.5〜9.1 ms    | 16.6〜17.3 ms | 7.7〜10.0 ms | 0    |
| 7   | 100 ms        | 118 ms           | 7.5〜9.2 ms    | 16.7〜17.1 ms | 8.5〜9.5 ms  | 0    |
| 8   | 120 ms        | 119 ms           | 6.4〜9.4 ms    | 16.7〜17.3 ms | 7.9〜10.4 ms | 0    |

回 8 は E2E の全 20 テストを通したときに採ったものである (同じ観測が suite の中でも同じ値を
出し、基準の差は 6.4〜9.4 ms、警告は 0 だった)。

- 仮説は否定された。受信の遅れが 220 ms まで跳ね、jitter (NetEq の 0.95 分位) が 280 ms まで
  上がった回でも、トラックごとの基準はどちらも動かず、差は 5.6〜9.7 ms のままである。跳ねは
  基準の差を広げない
- 回 5 から 7 では配信側の値も同時に採った。`timestampOffset.appliedMs` は一定で、傾き
  (`slope10sMsPerSecond`) も 0.00〜0.02 ms/秒、棄却 (`droppedMs`) も 0 のままで、配信側の
  TIMESTAMP の補正も動いていない
- したがって、47〜49 ms の基準の差が出た 2 回は、跳ねではなく別の (まれな) 条件である。
  25 回の観測のうち 2 回であり、再現条件はまだ分かっていない。分かっていることは「跳ねでは
  ない」ことである

### 同じ観測で分かった別の 2 点

**目標遅延の上限 (100 ms) が効いている。** 7 回のすべてで jitter が 100 ms を超え、適用中の
目標 (`appliedMs`) は上限の 100 ms に張り付いた。鳴り始めは 110〜115 ms、時間圧縮は 60 秒で
585〜1267 ms である。経路が静かな回 (同じ日の午前、時間圧縮 5〜65 ms) と比べて 1 桁以上多く、
圧縮は「声では粗さとして聞こえる」量である。上限が無ければ jitter の分 (100〜280 ms) まで
バッファを伸ばせるため、圧縮は減るが遅延が増える。どちらを取るかは実測で決める必要がある
(`AUDIO_DELAY_FEEDBACK_MAX_TARGET_MS` と `AUDIO_PLAYOUT_ARRIVAL_DELAY_MS` を変えて比べる)。

### 目標遅延の上限の比較 (2026-10-15、各 3 回)

`AUDIO_PLAYOUT_ARRIVAL_DELAY_MS` と `AUDIO_DELAY_FEEDBACK_MAX_TARGET_MS` を 100 ms と 160 ms に
して、同じ時間帯に交互に 3 回ずつ測った。下限は 50 ms のままである。

| 上限   | jitter   | applied  | 鳴り始め p50    | 時間圧縮 / 60 秒 | 補間 / 60 秒 | 追いつきが飛ばした音 | 受信の追いつきの回数 |
| ------ | -------- | -------- | --------------- | ---------------- | ------------ | -------------------- | -------------------- |
| 100 ms | 120      | 100      | 95.7〜113.8 ms  | 914〜1393 ms     | 12〜53 ms    | 80〜200 ms           | 7〜16                |
| 160 ms | 100〜140 | 100〜140 | 111.4〜135.5 ms | 447〜850 ms      | 0〜165 ms    | 0〜740 ms            | 3〜16                |

- 上限を上げると時間圧縮はおよそ半分になる (914〜1393 → 447〜850 ms)。代わりに鳴り始めが
  20〜25 ms 遅くなる
- 補間と、追いつきが飛ばす音は、上限を上げた回でむしろ増えた (補間 165 / 126 ms、飛ばした音
  740 / 500 ms)。上限 160 の 2 回は E2E の判定 (飛ばした音 500 ms 未満) に掛かった
- 経路の跳ね (受信の遅れの最大 117〜182 ms) はどちらの上限でも同じように出ており、上限が
  補間と飛ばしの原因ではない。跳ねのたびに受信側の追いつきが働き、復号器を作り直して
  溜まっている音を捨てるためである (決定 10)。上限 100 ms のままでは時間圧縮が増え、
  上限を上げると遅延が増える。**いまの 100 ms を維持する** (遅延を 20〜25 ms 犠牲にして
  圧縮を半分にするより、遅延を優先する。飛ばしと補間は上限では説明できない)

**経路が跳ねる時間帯の最大の品質要因は、受信側の追いつきが音を飛ばすことである。**
60 秒で 500〜740 ms (0.8〜1.2 %) の音が飛び、補間も 126〜165 ms 入る。上限を動かしても
変わらないため、次に測るのは追いつきの開始条件 (`AUDIO_RECEIVE_CATCH_UP_*` の閾値と確認時間)
と、跳ねの持続時間の分布である。

**A/V のずれは規格の限界のあたりにある。** 不感帯を 5 ms にしてからは `skewMs` の代表値は
−14〜−19 ms である (負は音声が映像より遅れる側。実測: スイート実行時に p50 −13.8 ms、
絶対値の最大 26.5 ms)。ITU-R BT.1359-1 の許容は「音声の遅れ 30 ms、進み 22.5 ms」であり、
EBU R37 は各段で「5 ms 進み〜15 ms 遅れ」、端から端で「40 ms 進み〜60 ms 遅れ」である。
いまの代表値は BT.1359-1 の許容の内側に入り、EBU R37 の各段の推奨に近づいた
(不感帯 30 ms のときは −20〜−44 ms で、許容の外に出ることがあった)。

ただし `skewMs` は推定値であり、音声の時計の対応付けの不感帯 (30 ms) と映像の表示周期
(16.7 ms)、`AudioContext` の出力の遅れ、実際に画面へ出るまでの遅れを含まない。真の
リップシンク誤差を独立に測る道具はまだ無い。ここは次に作る。

### 不感帯 (SYNC_MIN_DELTA_MS) の比較 (2026-10-15、各 2 回)

不感帯を 30 ms と 15 ms にして、`tests/e2e/relay/audio-timestamp.spec.ts` が 1 秒ごとに 25 回
採る `skewMs` を比べた (BT.1359-1 の許容の内側へ余裕を持たせる案の検証)。

| 不感帯 | 回  | 最小     | p50      | 最大     | 絶対値の最大 |
| ------ | --- | -------- | -------- | -------- | ------------ |
| 30 ms  | 1   | −35.2 ms | −30.8 ms | −17.3 ms | 35.2 ms      |
| 30 ms  | 2   | −30.6 ms | −26.6 ms | −10.3 ms | 30.6 ms      |
| 15 ms  | 1   | −27.2 ms | −23.3 ms | +8.3 ms  | 27.2 ms      |
| 15 ms  | 2   | −28.5 ms | −26.1 ms | +0.9 ms  | 28.5 ms      |

- 不感帯を半分にすると、代表値 (p50) は 0〜7 ms、最悪値は 3〜7 ms だけ良くなった。ばらつき
  (回ごとの差 4〜7 ms) と同じ大きさであり、効果があるとは言い切れない
- 不感帯を狭めても 20〜26 ms の系統的なずれ (音声が遅れる側) が残る。この分は不感帯ではなく、
  推定の作り方 (音声の時計の対応付けの不感帯 30 ms、映像の表示周期 16.7 ms、`AudioContext` の
  出力の遅れを入れていないこと) から来ている可能性が高い

### 不感帯をさらに狭めた比較と副作用 (2026-10-15、30 / 15 / 5 ms を各 3 回)

不感帯を 30 / 15 / 5 ms にして、同じ時間帯に交互に 3 回ずつ測った (`skewMs` は 25 サンプル)。

| 不感帯 | skewMs (p50 の 3 回)     | 絶対値の最大 (3 回)   | E2E  |
| ------ | ------------------------ | --------------------- | ---- |
| 30 ms  | −24.2 / −22.4 / −14.3 ms | 38.0 / 34.8 / 34.3 ms | 成功 |
| 15 ms  | −20.1 / −30.3 / −30.9 ms | 23.4 / 39.6 / 33.1 ms | 成功 |
| 5 ms   | −22.0 / −17.5 / −15.1 ms | 24.2 / 21.7 / 19.1 ms | 成功 |

- 最悪値 (絶対値の最大) は 5 ms が最も小さい (19〜24 ms。30 ms は 34〜38 ms)。15 ms は

### 不感帯 30 / 5 ms の交互比較と映像側の副作用 (2026-10-15、各 2 回)

250 ms ごとの観測 (60 秒) で、映像の表示待ちと映像の取りこぼしも同時に採った。

| 不感帯 | `skewMs` p50 | p95          | 絶対値の最大 | 映像の表示待ち p50 | 映像の取りこぼし |
| ------ | ------------ | ------------ | ------------ | ------------------ | ---------------- |
| 30 ms  | −34 / −35 ms | −15 / −16 ms | 49 / 48 ms   | 95 / 96 ms         | 18 / 19          |
| 5 ms   | −16 / −17 ms | +2 / −13 ms  | 24 / 19 ms   | 112 / 112 ms       | 7 / 19           |

- 同じ時間帯の交互比較で、p50 は −34/−35 → −16/−17 ms と半分になった。実測のずれは
  ITU-R BT.1359-1 の許容 (音声の遅れ 30 ms、進み 22.5 ms) の外から内側へ入る
- 代わりに映像は 16 ms 余計に待つ (95 → 112 ms)。上限の 500 ms、ITU-T G.114 の 150 ms には
  遠い。映像の取りこぼし (`catchUpFramesSkipped`) は増えていない
- **5 ms を採用する** (`src/playout/timeline.ts` の `SYNC_MIN_DELTA_MS`)。映像の遅れが
  150 ms を超え続けたら見直す (決定 1 の再考の条件に追加した)

### 却下: 音声が先行しているときだけ許す幅を広げる案 (2026-10-15、各 3 回)

不感帯を 5 ms にすると、先行する側 (多くの場合 映像) を余計に待たせる。待たせる相手が
音声になることもあり、その分だけ到着から鳴るまでの時間が増える (実測: 音声へ足した分の
最大が 56〜66 ms)。そこで、音声が先行しているときだけ許す幅を 20 ms
(ITU-R BT.1359-1 の進み側の限界 22.5 ms の内側) に広げる案を実装して測った。

| 許す幅 (音声が先行) | `skewMs` p50 (3 回)      | 音声の表示待ち p95 (3 回) | 映像の表示待ち p95 (3 回) | 音声へ足した分の最大 |
| ------------------- | ------------------------ | ------------------------- | ------------------------- | -------------------- |
| 5 ms (対称)         | −18.6 / −19.2 / −11.6 ms | 131 / 126 / 129 ms        | 136 / 131 / 131 ms        | 56.3 / 56.3 / 65.8   |
| 20 ms (非対称)      | −20.0 / −12.3 / −18.7 ms | 140 / 136 / 144 ms        | 136 / 146 / 147 ms        | 60.3 / 66.1 / 75.9   |

- ずれは良くならず (p50 の中央値はどちらも約 −19 ms)、音声の表示待ちの p95 は
  129 → 140 ms、映像は 131 → 146 ms と**両方**遅くなった
- 音声を許す分だけ映像を遅らせる機会が増え、その映像の遅れが次の合わせ直しで音声へも
  乗る、という連鎖が起きているとみられる (音声へ足した分の最大も 56 → 66 ms へ増えた)
- **対称の 5 ms を維持する**。実装は戻し、単体テストで「音声が先行していても不感帯まで
  詰める」ことを固定した (`src/playout/timeline.test.ts`)

### 47〜49 ms の基準の差の正体: 復号出力の遅れの段差 (2026-10-15)

25 回に 2 回出ていた「基準の差が 47〜49 ms のまま 13〜15 秒続く」現象を、`investigation-logs/`
の 33 回分の観測から追った。

| 条件 (即時追いつき) | 回  | 音声の基準の最大 | 基準の差の最大 | 20 ms 超が続いた時間 |
| ------------------- | --- | ---------------- | -------------- | -------------------- |
| 有効 (現行)         | 30  | 17.3〜18.1 ms    | 8.0〜10.1 ms   | 0 秒 (全回)          |
| 無効 (実験)         | 3   | 56.7 / 36.8 ms   | 47.6 / 27.7 ms | 48.3 秒 / 1.8 秒     |

- 出た回の内訳は、音声の基準が 18.0 → 37.0 → 56.6 ms と **20 ms ずつ 2 回段差で上がり**、
  そのまま戻らなかった。この間、映像の基準は 8.4〜9.5 ms のまま、受信の遅れも 18〜20 ms の
  ままで、経路は悪化していない。上げたのは**復号の出力の遅れ**である
- 段差が 20 ms では、受信側の追いつきの閾値 (床 + 40 ms) にも、即時開始の閾値 (床 + 100 ms)
  にも届かない。しかも床は直近 5 秒の最小値であるため、段差が続くと床自体がその値へ上がり、
  追いつきは「異常」を見失う。音声の表示時刻はその分だけ後ろへずれ、ずれ (基準の差) として
  47 ms が残り、同期の制御が映像を遅らせて合わせ込む
- 即時追いつきを無効にした 3 回のうち 2 回で出て、有効な 30 回では 1 回も出ていない。跳ねの
  たびに復号器を作り直して溜まった分を捨てるため、遅れが床へ染み込む前に戻る
- **決定 10 の「床 + 100 ms で即時開始」は、短時間のずれを守るだけでなく、遅れが床へ定着
  するのを防いでいる。** この機構が無いと、基準の差 47 ms が 48 秒続く (追いつきを無効に
  した 3 回のうち 2 回)

### 受信側の追いつきが働く条件 (2026-10-15、250 ms ごとの観測 3 回)

`MOQT_INVESTIGATION_INTERVAL_MS=250` にして、受信側の追いつき (`audio.playoutCatchUp.*`) を
細かく採った。

| 回  | catchUpStarts | 飛んだ音 | 補間  | maxLagMs | jitter | 受信の遅れの最大 | 開始の瞬間の lag と床 |
| --- | ------------- | -------- | ----- | -------- | ------ | ---------------- | --------------------- |
| 1   | 3             | 59.8 ms  | 20 ms | 132.6 ms | 100 ms | 119.5 ms         | lag 20〜21 / 床 17 ms |
| 2   | 3             | 0 ms     | 18 ms | 119.1 ms | 100 ms | 118.7 ms         | lag 20〜26 / 床 17 ms |
| 3   | 13            | 80.2 ms  | 18 ms | 171.1 ms | 140 ms | 161.3 ms         | lag 18〜29 / 床 17 ms |

- 開始の瞬間の lag は健全時の値 (18〜29 ms) であり、250 ms の観測では捉えられない短い跳ねで
  始まっている。lag が床から `AUDIO_RECEIVE_CATCH_UP_JUMP_MS` (100 ms) を超えた瞬間に
  持続を待たずに始める条件が効いている
- 回 3 では 13 回の開始が 1 秒間隔で並んだ (t=13.8〜26.4 秒に 8 回)。やめた後 1 秒は始めない
  という条件 (`AUDIO_RECEIVE_CATCH_UP_COOLDOWN_MS`) の間隔であり、跳ねが続く間は作り直しを
  繰り返す
- 1 回で飛ぶ音は 3〜28 ms (回 3 は 13 回で 80 ms) と小さい。飛んだ分は補間 (18〜20 ms) で
  概ね埋まる
- 同じ経路の別の回では 60 秒で 500〜740 ms 飛ぶこともある (目標遅延の上限を 160 ms にした
  実験)。飛ぶ量は復号器に溜まっている量で決まるため、目標遅延が深いほど 1 回の作り直しで
  捨てる量が増える
- 次の検証: 「持続を待たずに始める」条件を外したときに、飛ぶ量が減り、かつ A/V のずれ
  (`skewMs`) が予算内に収まるかを A/B で測る

### 「持続を待たずに始める」条件の A/B (2026-10-15、各 3 回)

`AUDIO_RECEIVE_CATCH_UP_JUMP_MS` を 100 ms (現行) と 100000 ms (実質無効) にして、同じ時間帯に
交互に 3 回ずつ測った (250 ms ごとの観測、60 秒)。

| JUMP   | 回  | 追いつきの回数 | 飛んだ音 | 補間  | 時間圧縮 | 受信の遅れの最大 | skewMs (p50 / 絶対値の最大) |
| ------ | --- | -------------- | -------- | ----- | -------- | ---------------- | --------------------------- |
| 100 ms | 1   | 5              | 60.1 ms  | 0 ms  | 561 ms   | 122 ms           | −32 / 54 ms                 |
| 100 ms | 2   | 3              | 79.5 ms  | 19 ms | 480 ms   | 112 ms           | −27 / 54 ms                 |
| 100 ms | 3   | 6              | 19.6 ms  | 20 ms | 597 ms   | 124 ms           | −31 / 44 ms                 |
| 無効   | 1   | 0              | 0 ms     | 0 ms  | 1240 ms  | 113 ms           | −43 / 74 ms                 |
| 無効   | 2   | 2              | 99.6 ms  | 18 ms | 906 ms   | 121 ms           | −34 / 71 ms                 |
| 無効   | 3   | 0              | 0 ms     | 0 ms  | 946 ms   | 157 ms           | −38 / 84 ms                 |

- 無効にすると、追いつきの回数 (5/3/6 → 0/2/0) と飛ぶ音 (20〜80 → 0〜100 ms) は減る
- 代わりに、A/V のずれは悪化する (p50 −27〜−32 → −34〜−43 ms、絶対値の最大 44〜54 →
  71〜84 ms)。遅れた音を鳴らし続けるためである
- 時間圧縮はおよそ 2 倍になる (480〜597 → 906〜1240 ms / 60 秒)。復号器を作り直さない分を、
  鳴らす側の時間圧縮が取り返そうとするためである
- **いまの 100 ms を維持する。** 飛ぶ音は 1 回あたり 3〜28 ms で補間 (18〜20 ms) に概ね収まり、
  聞こえにくい。それと引き換えに守っている A/V のずれの方が大きい

### 音声の出力の遅れと、ずれの推定の基準点 (2026-10-15、2 回)

`skewMs` の音声側は「`AudioContext` の時計で予約した時刻を、`getOutputTimestamp()` の対応で
実際の時刻へ換算した値」である。この換算が**デバイスが今鳴らしている位置**を指すのか、
**再生のために処理した位置**を指すのかで、真のリップシンク誤差との差が変わる。ページの
仕込み (`installAudioOutputProbe`) で実際の `AudioContext` をつかまえて測った。

| 回  | 処理済みで未再生 (`currentTime - contextTime`) | `outputLatency` | `baseLatency` | デバイス位置の実時刻 (`now - performanceTime`) | 未再生 − outputLatency |
| --- | ---------------------------------------------- | --------------- | ------------- | ---------------------------------------------- | ---------------------- |
| 1   | p50 29.4 ms (p95 32.0、最大 32.1)              | p50 24.0 ms     | 5.3 ms        | p50 4.9 ms (0.1〜9.8)                          | 5.3 ms                 |
| 2   | p50 30.0 ms (p95 32.0、最大 32.0)              | p50 25.0 ms     | 5.3 ms        | p50 5.5 ms (0.1〜9.9)                          | 5.3 ms                 |

- 未再生の長さ (30 ms) は、ブラウザが申告する出力の遅れ (25 ms) と、`AudioContext` 自身の
  バッファ (5.3 ms) の和に一致する。つまり `contextTime` は「まだ鳴っていない分」を含んだ
  **デバイスが鳴らしている位置**である
- その位置の実時刻 (`performanceTime`) は「今」の 5 ms 前である。対応付け
  (`toPerformanceMs`) は予約した時刻を**鳴る時刻**へ換算している
- したがって、`skewMs` の音声側に出力のバッファの分の偏りは無い (測れる範囲で 5 ms 以内)。
  `devtools` の「`start` は `AudioContext` の時計で予約した時刻であり、出力の遅れは入って
  いない」という説明は予約した時刻そのものについてであり、ずれの推定には入っている
- 残る未計測は、スピーカーの振動板までの遅れ (数 ms) と、描いたフレームが実際に画面へ
  出るまでの遅れである。映像は `requestAnimationFrame` の中で描いており (既定の
  `requestFrame`)、描いた時点がその frame の描画機会なので、後者は小さい
- 真のリップシンク誤差は、実測のずれ (−14〜−19 ms) に「映像の合成の遅れ (0〜16 ms)」を
  足し「スピーカーの遅れ (0〜5 ms)」を引いた範囲、およそ −19〜+2 ms と見積もれる

### パケロス下で「作り直しを減らす」2 案の実測 (2026-10-15、実リレー 5 % 損失)

ラウンド 16 の計測で、5 % の損失では受信した Object の穴は 1 音 (40 ms) が 69 回であるのに
対し、復号の出力の穴は 3〜6 音 (60〜120 ms) が 23 回であり、23 回は作り直しの回数と一致して
いた。1 音の損失が 3〜6 倍の無音として現れているため、作り直しを減らす 2 案を実装して測った
(各 2 回、40 秒。60 秒の案だけ 1 回 30 秒)。

| 案                                  | 作り直し | 飛ばした音 | 1 回あたり | lag の最大  | 鳴らした長さ        |
| ----------------------------------- | -------- | ---------- | ---------- | ----------- | ------------------- |
| 現行 (冷却 1 秒)                    | 31 回    | 2220 ms    | 72 ms      | 約 200 ms   | 37.7 秒 / 40 秒     |
| 効かないとき間隔を 2 倍 (上限 8 秒) | 31 回    | 2220 ms    | 72 ms      | 約 200 ms   | 37.7 秒 / 40 秒     |
| 穴の直後 1 秒は始めない             | 30 回    | 2220 ms    | 74 ms      | 約 200 ms   | 37.7 秒 / 40 秒     |
| 穴の直後 60 秒は始めない            | **1 回** | **60 ms**  | 60 ms      | **1458 ms** | **27.8 秒 / 30 秒** |

- 間隔を伸ばす案は効かない。損失下では遅れが一度上限へ戻ってからまた跳ぶため、「戻らない
  まま作り直す」という伸ばす条件が成立しない
- 穴の直後を 1 秒始めない案も効かない。穴は 0.4 秒ごとに空くため 1 秒の待ちはすぐ明ける
- 60 秒にすると作り直しは 1 回になり飛ぶ音も 60 ms になるが、**遅れが 1458 ms まで育ち、
  鳴らした長さも 30 秒で 27.8 秒へ落ちる**。復号器に溜まった分を捨てないと、損失の分
  (5 %) だけ遅れが積み上がる (毎秒およそ 50 ms)
- **作り直しは、損失下でも live を保つ役目を果たしている。** 決定 10 の判定 (冷却 1 秒 +
  床 + 100 ms で即時 + 確認 100 ms) を維持する。飛ぶ音 (5 % 損失で 40 秒に 2.2 秒) は
  遅れを積み上げないための代価である

### パケロス対策: 音声 Object の 2 回送り (2026-10-15、実リレー、5 % の損失)

音声は datagram で届き、再送されない (RFC 9221)。受信側だけでは失った音は戻らないため、
配信側で同じ Object を 2 回送る案を実装して測った (devtools の `audioRedundancy=2`)。受信側は
同じ識別子 (groupId と objectId) の 2 回目を捨てる (`src/createMediaSubscriber.ts` の
`receiveAudioObject` と `devtools/src/hooks/useSubscriber.ts`)。

| 送信回数 | 観測      | 欠落率        | 鳴らした長さ            | 復号器の作り直し | 飛ばした音     |
| -------- | --------- | ------------- | ----------------------- | ---------------- | -------------- |
| 1 回     | 40 秒 × 2 | 0.056 / 0.056 | 37.7 秒 / 40 秒 (94 %)  | 31 / 31 回       | 2220 / 2220 ms |
| 2 回     | 40 秒 × 2 | 0.016 / 0.002 | 38.9 / 39.7 秒          | 3 / 1 回         | 600 / 80 ms    |
| 2 回     | 60 秒 × 2 | 0.002 / 0.002 | 59.8 / 59.5 秒 (99.4 %) | 1 / 3 回         | 80 / 60 ms     |

- 5 % の損失が 0.2 % まで下がる (両方の copy が落ちる確率は損失率の 2 乗)。鳴らした長さは
  94 % → 99.4 %、飛ぶ音も 2220 ms → 60〜80 ms になった
- 代わりに音声の帯域が 2 倍になる (音声 Object の数が 2 倍。映像に比べれば小さい)
- 40 秒の 2 回目の観測だけ 1.6 % と高めに出たのは、その時間帯の経路の乱れとみられる
  (60 秒の 2 回はどちらも 0.2 %)
- 送信側の冗長化は devtools の設定 (`audioRedundancy`) として入れた。受信側の重複の判定は
  ライブラリ (`src/createMediaSubscriber.ts`) にも入れてある

#### 2 回送りを既定にするかの判断 (2026-10-15、損失 0 / 5 / 10 %、各 1 回 40 秒)

| 注入した損失 | 1 回送り (欠落 / 鳴った割合 / 飛ばし) | 2 回送り (欠落 / 鳴った割合 / 飛ばし) |
| ------------ | ------------------------------------- | ------------------------------------- |
| 0 %          | 0.001 / 99.3 % / 0 ms                 | 0.000 / 100.4 % / 0 ms                |
| 5 %          | 0.055 / 94.5 % / 2220 ms              | 0.003 / 99.4 % / 80 ms                |
| 10 %         | 0.108 / 88.7 % / 4360 ms              | 0.012 / 97.3 % / 460 ms               |

- 損失の無い経路では品質が変わらない (欠落 0、飛ばし 0)。損失のある経路では 5 % で
  94.5 % → 99.4 %、10 % で 88.7 % → 97.3 % と鳴る割合が上がる
- 代わりに音声の datagram の数と帯域が 2 倍になる (実測で 50 個/秒 → 100 個/秒。音声は
  映像に比べて小さい)
- **既定を 2 回送りにする** (`devtools/src/signals/connectionSettings.ts` の
  `audioRedundancy`)。1 にすると今までどおり 1 回だけ送る

#### 損失が厳しい経路 (2026-10-15、10 % / 20 % を注入、各 1 回 30 秒)

| 注入した損失 | 1 回送り (欠落 / 鳴った割合 / 飛ばし) | 2 回送り (欠落 / 鳴った割合 / 飛ばし) | 3 回送り                |
| ------------ | ------------------------------------- | ------------------------------------- | ----------------------- |
| 10 %         | 0.099 / 89.3 % / 3020 ms              | 0.009 / 96.9 % / 240 ms               | -                       |
| 20 %         | 0.203 / 77.6 % / 6200 ms              | 0.037 / 96.3 % / 1080 ms              | 0.010 / 99.4 % / 280 ms |

- 全ての copy が落ちる確率は損失率の冗長度乗になる (10 % の 2 回で 0.9 %、20 % の 2 回で
  3.7 %、20 % の 3 回で 1.0 %。いずれも理論値どおり)
- 損失が 20 % を超えるような経路では 3 回が効く (鳴った割合 96.3 % → 99.4 %、飛ばした音
  1080 ms → 280 ms)。**冗長度はライブラリと devtools のどちらも 1〜3 の整数**であり、
  4 以上は帯域を無駄にするため `start()` がエラーにする

### 穴が補間されない理由は試験信号にあった (2026-10-15)

実リレーの E2E では、復号器の作り直しの直後にできる 60〜120 ms の穴がほとんど補間されない
(`concealedMs` が小さい)。補間の実装 (`concealSamples`) を周波数ごとに測ると、これは
**E2E の音が正弦波であること**によるものだった。

| 周波数  | 4 kHz での周期            | 20 ms の穴の補間 |
| ------- | ------------------------- | ---------------- |
| 1000 Hz | 4.0 サンプル (格子に乗る) | 960 サンプル生成 |
| 440 Hz  | 9.1                       | 960              |
| 300 Hz  | 13.3                      | 0                |
| 220 Hz  | 18.2                      | 0                |
| 150 Hz  | 26.7                      | 0                |
| 100 Hz  | 40.0                      | 0                |

- 補間は「4 kHz へ間引いた格子での周期」を探し、その周期 1 つ分を繰り返す。格子に乗らない
  純音では繰り返しの継ぎ目で波形が飛ぶため、実装は補間せず無音のままにする (NetEq が相関の
  足りない音を無音にするのと同じ)
- 会話や音楽は周期が格子に乗りやすいため、この条件には当てはまりにくい。E2E の
  `concealedMs` が小さいのは実装の欠陥ではなく、試験信号 (正弦波) の性質である
- 境界は `src/playout/audioTimeStretch.test.ts` にテストとして固定した

### まとめて落ちる経路 (バースト損失) と、2 個目を送る間隔 (2026-10-15)

実際の経路の損失は、輻輳で送信キューがあふれたときにまとめて落ちる。1 個ずつ落とす注入では
「続けて送った冗長化の 2 個目」も生き残ってしまうため、5 個連続で落とす注入 (全体で 2 %) を
使い、2 個目を何個後の Object と一緒に送るかを測った (30 秒、各 2 回。1 個目はどの案でも
今すぐ送るため、遅延は増えない)。当時は配信側に間隔の定数を置いて切り替え、**測った後に
削除した**ため、いまはリポジトリに無い。

| 2 個目を送る間隔 | 欠落率         | 鳴った割合        | 復号器の作り直し | 飛ばした音   |
| ---------------- | -------------- | ----------------- | ---------------- | ------------ |
| 0 (続けて送る)   | 0.016 / 0.018  | 98.9 % / 98.6 %   | 6 / 9 回         | 480 / 560 ms |
| 2 (40 ms 後)     | -0.001 / 0.000 | 100.3 % / 100.6 % | 0 / 0 回         | 0 / 0 ms     |
| 5 (100 ms 後)    | 0.001 / 0.002  | 100.8 % / 100.7 % | 0 / 0 回         | 0 / 0 ms     |

- 続けて送ると、5 個連続で落ちる経路では両方の copy が落ちる (欠落 1.6〜1.8 %)。**間を空けると
  欠落は 0.1 % 前後まで下がり、作り直しも飛ばした音も 0 になった**
- 2 と 5 は同じ結果であるため、短い方 (2 = 40 ms) が良さそうに見えた
- RFC 2198 (RTP の冗長化) が直前のフレームを次のパケットに載せるのと同じ考え方である

**間を空ける案は、受信側で復旧の分を除いたうえで採る。** 間を空けると、1 個目を失ったときに
届く 2 個目が「遅れて届いた音」として受信側の**遅れの推定を膨らませる**。損失を注入しない
長時間の観測 (60 秒) で測ると、この副作用がはっきり出た (2026-10-15)。

| 2 個目を送る間隔 | 揺らぎの推定 | 目標遅延      | 鳴り始めの遅れ | 判定         |
| ---------------- | ------------ | ------------- | -------------- | ------------ |
| 0 (続けて送る)   | 20 ms        | 50 ms         | 65 ms 前後     | 2 回とも成功 |
| 2 (40 ms 後)     | 80 ms        | 上限の 100 ms | 130 ms         | 2 回とも失敗 |

- 目標遅延が上限に張り付くと、A/V 同期を保つために映像へ最大 100 ms の遅れを足すため
  (決定 1)、同期の補償が上限に張り付いた警告 (`syncExtraDelayPinnedAtLimit`) も出た
- **順番を揃えた比較 (交互に各 3 回) でも同じ差が出た。** 続けて送る側は 3 回とも成功
  (鳴り始めの遅れ 64.0 / 66.2 / 66.7 ms、受信の遅れの最大 35 / 34 / 144 ms)、間を空ける側は
  1 回だけ成功した (鳴り始め 122.7 / 125.2 / 151.3 ms、受信の遅れの最大 62 / 61 / 155 ms)。
  揺らぎの推定は 20 ms に対し 80 / 80 / 140 ms であった。経路の変化では説明できない
- **遅れて届いた復旧の分を推定から除く案も実装して測り、棄却した。** 直近に観測した
  TIMESTAMP より少しだけ古い音を遅れの推定に入れないようにして同じ A/B を行うと、枠を
  60 ms にした場合は続けて送る側が 2 回とも成功、間を空ける側が 2 回とも失敗した。枠を
  120 ms へ広げても結果は同じ (続けて送る側 3 回とも成功、間を空ける側 1 回だけ成功、
  鳴り始めの遅れは 123.2 / 130.8 / 231.6 ms) であり、**除く案では足りない**
- 音声の時間軸へ記録する経路は 1 つだけ (`src/playout/audioPlayoutSession.ts`) であり、そこを
  止めても変わらなかった。原因は TIMESTAMP の古さで見分けていたことで、遅れて届く音は
  **60〜224 ms** と幅広く、60 ms / 120 ms の枠の外へ落ちる分があった
- **位置 (Group ID と Object ID) の順序で見分ける形にしても、副作用は消えなかった。**
  既に受け取ったどの Object よりも古い位置の音を復旧の分として推定から除き、間隔 0 と 2 を
  交互に各 3 回測った。

  | 2 個目を送る間隔 | 揺らぎの推定     | 鳴り始めの遅れ        | 受信の遅れの最大  | 判定         |
  | ---------------- | ---------------- | --------------------- | ----------------- | ------------ |
  | 0 (続けて送る)   | 140 / 20 / 20 ms | 99.9 / 64.3 / 66.8 ms | 155 / 31 / 130 ms | 3 回とも成功 |
  | 2 (40 ms 後)     | 80 / 80 / 80 ms  | 120.4〜122.2 ms       | 58 / 60 / 61 ms   | 3 回とも成功 |

  間を空ける側は、推定も鳴り始めの遅れも **そろって高い**。受信の遅れの最大が 58〜61 ms と
  間隔 (40 ms) に揃っていることから、遅れて届く復旧の分が推定に入っている。TIMESTAMP の
  古さで見分ける案 (枠 60 ms / 120 ms) でも、位置の順序で見分ける案でも捉えきれない

- **間隔を空ける案は採らない。** まとめて落ちる経路での利得 (欠落 1.6〜1.8 % → 0.1 %) より、
  常時の遅延 (鳴り始め +55 ms、揺らぎの推定 20 → 80 ms) の方が大きい
- ライブラリの配信側 (`src/createMediaPublisher.ts`) も 0 (続けて送る) である
- ライブラリの配信側 (`src/createMediaPublisher.ts`) は 0 (続けて送る) のままである。
  受信側 (位置で見分けて推定から除く) をライブラリへも入れてから、同じ A/B を行う

### 揺らぎを注入して目標遅延の上限を測る (2026-10-15)

これまで揺らぎは経路任せだった。条件を決めて測れるよう、受信する datagram に揺らぎを与える
注入 (`tests/e2e/relay/investigation-audio-delay.spec.ts` の `installDatagramJitter`) を足した。
普段は静かで時々遅れる形 (`MOQT_INVESTIGATION_JITTER_SPIKE_RATIO` /
`MOQT_INVESTIGATION_JITTER_SPIKE_MS`) も指定できる。

音声の目標遅延の上限 (`AUDIO_DELAY_FEEDBACK_MAX_TARGET_MS`。現在 100 ms) を変えて測った
(30 秒、各 2 回。注入は datagram の到着のみを遅らせ、落とさない)。

| 注入                          | 上限 | 揺らぎの推定 | 鳴り始め p50    | 鳴った割合      | 補間      | 飛ばし | 圧縮      |
| ----------------------------- | ---- | ------------ | --------------- | --------------- | --------- | ------ | --------- |
| 0〜60 ms の揺らぎ             | 100  | 80 ms        | 58.4 / 62.9 ms  | 99.4 / 99.5 %   | 20 ms     | 0      | 292 / 299 |
| 0〜60 ms の揺らぎ             | 60   | 80 ms        | 57.7 / 58.9 ms  | 99.0 / 99.4 %   | 0         | 0      | 292 / 305 |
| 2 % の datagram が 80 ms 遅れ | 100  | 80 ms        | 99.2 / 100.0 ms | 100.5 / 100.2 % | 0 / 17 ms | 0      | 33 / 34   |
| 2 % の datagram が 80 ms 遅れ | 60   | 80 ms        | 59.8 / 64.8 ms  | 100.4 / 100.5 % | 0         | 0      | 0         |

- 上限を 60 ms にすると**鳴り始めの遅れが約 40 ms 小さくなる**。跳ねを吸収できずに音が
  欠けることを予想したが、この注入では補間も飛ばしも圧縮も 0 で、品質の差は出なかった
- つまり**この経路では上限は効いていない**。2 % × 80 ms の跳ねに対して揺らぎの推定が 80 ms
  へ上がり、上限 100 はそのまま、上限 60 は切り捨てる。切り捨てても遅れとして現れない
  (基準の遅れが注入に合わせて動くため)
- 上限を下げる判断はしない。決定 1 の実測で、経路が大きく跳ねた回 (受信の遅れの最大
  208〜432 ms) には目標遅延が上限に張り付き、A/V 同期の補償も上限に達した。この注入では
  その条件を作れていないためである (注入の上限を 250 ms まで上げても、上限 100 ms では
  吸収できない)。**跳ねの深さと頻度を変えた条件での測定が残っている**

### 復号の入出力の timestamp の対応を測る (2026-10-15)

配信側の冗長化で後から届いた復旧の分を再生側へ伝えるには、復号へ渡した Object と復号の出力の
対応が引けなければならない。実リレーで 20 秒ぶんの出力を数えた (1014 件)。

| 見たもの               | 実測                                                |
| ---------------------- | --------------------------------------------------- |
| 完全一致した出力       | 1〜3 件 (ほぼ無い)                                  |
| 最も近い記録との差     | p50 0.30 ms、p90 0.40 ms、p99 0.40 ms、最大 0.40 ms |
| 対応が引けなかった出力 | 0 件                                                |

- 復号の出力の timestamp は、投入した値と **0.4 ms ほどずれる**。完全一致では引けないが、
  許容は 1 ms であるため引ける (実測でも 0 件の取りこぼし)
- 「最も古い記録だけを候補にする」規則は、**出力が返らなかった記録が 1 つ残るだけで以降の
  対応がすべて引けなくなる** (この関数の docstring に書かれていた失敗)。許容の中では最も
  近い記録を対応させる形へ直した。実測では取りこぼしは 0 件のままで、失敗の形が消える
- **許容をフレームの長さに合わせる形へ直した** (2026-10-15)。復号の出力の長さ
  (`numberOfFrames / sampleRate`) の半分を許容として渡す。音 1 つの間隔の半分であるため、
  隣のフレームと取り違えない範囲で最大まで広げられる
- 実測 (実リレー、20 秒、CPU を絞って負荷をかける):

  | CPU  | 1 ms の枠 (変更前)       | フレームの長さの半分 (20 ms のフレームでは 10 ms) |
  | ---- | ------------------------ | ------------------------------------------------- |
  | 1 倍 | 引けない 0 件 / 1015     | 引けない 0 件 / 1015                              |
  | 8 倍 | **引けない 5 件 / 1013** | **引けない 0 件 / 1013**                          |

  負荷時のずれは 9.7 ms であり、1 ms の枠では引けない。引けないと、その音は共有の時間軸へ
  記録されず、A/V 同期の基準が更新されないまま固定される

- Opus の最短フレームは 2.5 ms であり、その半分 (1.25 ms) では 9.7 ms のずれは引けない。
  フレームの長さを渡す形にしたのはこのためである

### 遅れの推定は「窓ごとの最大」で決まる (2026-10-15)

`src/playout/audioDelayEstimator.ts` を読み、計測で確かめた。推定は libwebrtc の `DelayManager` と同じで、
**500 ms ごとの「基準からの最大の遅れ」だけをヒストグラムへ入れ、その 0.95 分位**を目標にする。
窓はおよそ 25 件であり、**1 件の遅れで推定が動く**。計測では、区間の最大が p50 6〜7 ms・
p90 9〜10 ms でも、遅れが 1 件混じると最大が 121〜224 ms になり、目標遅延が上がった。

#### 遅れて届いた音は、冗長化が吸収する

到着を遅らせる注入 (1 % / 5 % の datagram を 60 ms 遅らせる) では、**推定がほとんど動かなかった**。

| 遅らせる割合 | 区間の最大 p50 / p90 / 最大 | 鳴り始め p50 |
| ------------ | --------------------------- | ------------ |
| 0 %          | 6 / 10 / 11 ms              | 63.6 ms      |
| 1 %          | 6 / 10 / 21 ms              | 65.9 ms      |
| 5 %          | 6 / 10 / 121 ms             | 68.1 ms      |

- 既定の冗長化 (2 回送り) では、**先に届いた copy が使われ、遅れた copy は同じ識別子として
  捨てられる**。そのため到着の遅れは推定に入らない。冗長化は欠落だけでなく揺らぎにも効く
- 復旧の形 (1 個目を落として 2 個目を 60 ms 遅らせる) の影響は、経路そのものの跳ね
  (区間の最大が 1 回の観測で 121〜224 ms) に埋もれ、1 回ずつの観測では分離できなかった。
  **同じ経路条件で対にして測る**必要がある
- 除外の枠を 60 ms と 120 ms にして効かなかったのは、遅れて届く音が **60〜224 ms** と幅広く、
  枠の外へ落ちる分があったためである。次は「位置 (Group ID と Object ID) の順序」で
  見分けたうえで、同じ経路条件で対にして測る

### 表示時刻の差が観測できる割合 (2026-10-15)

`skewMs` は「音声と映像それぞれの表示の実績が 1 秒以内にある」ときだけ値が出る
(`src/playout/timeline.ts` の `skewMs`)。観測の割合を 2 つの条件で測った。

| 条件                                               | 観測できた割合        |

| `audio-timestamp.spec.ts` (600 ms、3 件で打ち切り) | 3 件そろうまで 3.0 秒 |

### 波形の尖り (crest) の判定が跳ねで落ちる (2026-10-15)

実リレーの E2E を 3 回通したうち 1 回、`devtools-both-audio.spec.ts` の
「配信した音声が、レベルと波形を保ったまま購読側で鳴る」が落ちた。

```
受信した音声の波形が崩れている (peak - rms が 5.6 dB。サイン波は 3.0 dB。
status=connected, objects=164, decoded=164, peakDbfs=-25.0, rmsDbfs=-30.6, crestDb=5.6,
playedMs=2921, missedFrames=0, rebases=0, compressedMs=68, concealedMs=0, catchUpStarts=1,
skippedMs=0, catchUpLagMs=18, receiveDelayMs=19, maxReceiveDelayMs=115, warnings=0)
```

- 定常の回は peak −22.9 / rms −25.9 (crest 3.0 dB) である。落ちた回は peak −25.0 に対して
  rms が −30.6 と 4.7 dB 低く、レベルが下がるフレームを引いている
- 原因は判定の作りである。`audio.peakDbfs` / `audio.rmsDbfs` は**直近に復号した 1 フレーム
  (20 ms) の値**であり (`devtools/src/hooks/useSubscriber.ts` の `summarizeAudioLevel`)、
  1 回読むだけでは跳ねや復号器の作り直しの直後のフレームを引く。同じ回に受信側の追いつきが
  1 回働いていた (skippedMs は 0、補間も 0)
- 直した: 鳴り始めから 3 秒待った後に 6 秒間 (200 ms ごとに 30 回) 観測し、**中央値**が許容の
  内側にあることと、**8 割のサンプル**が許容の内側にあることで判定する。実装の不具合なら
  定常的に崩れるため、8 割の条件で捕まる。1 フレームだけの読みは使わない
  (実装が保証する性質だけを見る、という決定 9 の方針に揃える)
