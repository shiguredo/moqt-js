# Chrome の音声の未着区間を埋める改善

記録日: 2026 年 10 月 31 日。

この文書は SHA-256 `02c61e0e0c817193c4a83888483c5e70223bc96cf53c31d196140d610fb3f98c` の版を固定した記録である。
その後の出力側への移行と負荷削減は [AudioWorklet での改善](CHROME_AUDIO_RENDERER_IMPROVEMENT.md) に記録する。
以下の「最終コード」と測定結果は、この固定版を指す。

## 修正した問題

Chrome の WebRTC との比較で、現在の SDK は短い遅延を保つ一方、繰り返す遅着で活動中の無音が残った。
予約の判断を保存して調べると、次の音声が届いた時点で、空白の一部はすでに再生済みだった。
また、未来に残る短い空白でも、10 ms の予約余裕の内側では補間が呼ばれない例があった。
到着を待ってから補間用のバッファを作る方式では、過去の空白へ戻れない。

## 変更した再生の仕組み

実音を予約するときに、その直後に使える最大 100 ms の続き音も同じバッファへ用意する。
次の音声が通常どおり届けば、前のバッファを実音の終端で止め、続き音を出さない。
次が未着なら、メインスレッドのタイマーや次のコールバックを待たず、音声の出力側がそのまま続き音を取り出す。
実音が届いたときは、続き音と実音を短くクロスフェードして復帰する。

実音の開始を補間のために遅らせず、受信した音声を捨てて埋め合わせることもしない。
音声のみの既定の目標は 50 ms のままとする。
停止が分かった場合は続き音を取り消し、最後の実音の終端で閉じる。
補間の上限を超えた長い途絶まで、連続性を保証するものではない。

続き音は、有声と非周期の成分を分けて扱う。
周期が十分に確かなら既存の周期補間を使い、低い声の解析には連続する 30 ms の履歴も使う。
周期を推定できない場合は、線形予測フィルターと非周期の励振を使う。
声の子音を 20 ms ごとに反復する処理にはしない。
解析に古い大きな音を使っても、最新の実音の RMS とピークを超えないよう制約する。

これは [NetEq の Expand / Merge](https://webrtc.googlesource.com/src/+/031cc215615895d7ae039d4098c2716d7acf2dc3/modules/audio_coding/neteq/g3doc/index.md) の
欠落時の出力と実音への復帰を参考にした変更である。
上流 NetEq 全体の移植ではなく、コーデック内部の PLC、FEC、パケットバッファと適応制御まで置き換えたものではない。

## 計器の扱い

実音の長さと、準備した補間の長さを分ける。
次の実音との間に使った補間を計上し、その分を無音の空白には数えない。
将来使う可能性があるという理由だけで、100 ms 全量を補間の実績にしない。
使用量は次の実音または停止時に確定するため、未着が継続している途中の実時間の使用量ではない。
元の媒体が届かなかったことと、出力が無音になったことは同じではない。

補間後に計器の gapMs が減っただけでは、改善を確認したとはしない。
実 AudioWorklet の Float32 PCM でも無音を調べ、別の計算で照合する。
従来の CHROME_AUDIO_DROPOUT_MEASUREMENTS.md の予約空白は、固定した旧版に対する測定である。
準備した続き音を出す変更後は、実音の予約間隔だけで出力の欠落を判断しない。

## 比較方法

Google Chrome の実 WebRTC、修正前の SDK、修正後の SDK を同じ出力時計で同時に収録する。
Opus は受信変換で複製し、両 SDK へ同じ復号 PCM を渡す。
SDK の呼び出し順はフレームごとに反転する。
修正前の再生コードは、前回の比較で使った SHA-256 と一致するスナップショットへ固定する。

Julius と Kyoko の日本語音声を各 6 秒使い、正常到着、0〜30 ms の遅着、繰り返す 60 ms の遅着を扱う。
44.1 / 48 kHz の出力を各 3 回、同時に走らせず測定する。
原音の独立レンダリング、送受信ペイロードと保存後の再復号も照合する。
計測中は本体と計測器を固定し、他の実時間計測、解析やビルドを同時に実行しない。

無音、局所照合、原音基準への遅延の換算は CHROME_WEBRTC_PLAYOUT_COMPARISON.md と同じ定義を使う。
活動中の無音は、前後の照合点から考えられるすべての参照位置で活動を確認できた区間だけを数える下限である。
未分類の区間は別に残す。
相関は整数サンプルの局所照合であり、雑音量や MOS として扱わない。

## 最終コードの測定結果

Google Chrome 156.0.8078.79 / macOS arm64 で 36 条件すべてが有効だった。
各 335 パケット、計 12,060 パケットについて、受信した非空ペイロードと送信内容が一致した。
保存後の別デコーダーによる再復号と、原音の独立レンダリングの最大サンプル差は全条件で 0 だった。
全反復のコードが同一であり、測定対象と最終コードの SHA-256 も一致した。
修正後は全条件で目標 50 ms を保ち、受信した音声の破棄は 0 件だった。

振幅の絶対値が 1e-7 未満である状態が 0.5 ms 以上続く区間を調べた。

遅延が完全に不変だったとは判断しない。

## 処理負荷の測定と削減

続き音を準備する初版でも、最初の 36 条件で活動中の無音は 0 ms になった。
一方、実 Chrome の投入処理の p95 は最大約 2.4 ms に増えていた。
CPU プロファイルから、無声成分の合成と音量制約に処理時間が集中することを確認した。
履歴のコピーをリングバッファへ変え、音量の集計をコールバックと一時配列を使わないループへ変えた。

同じ保存済み PCM 4,020 フレームから生成した 19,296,000 サンプルについて、
負荷削減前後の出力は全サンプルが一致した。
プロファイルを取得しない同じ Node.js v26.13.0 で、両者の実行順を交互にし、各 3 回測定した。
各測定は 2 周を準備運転とし、その後の 3,350 呼び出しを集計した。
補間生成の p95 は負荷削減前の約 0.563〜0.591 ms に対し、削減後は約 0.191〜0.207 ms だった。

最終コードの実 Chrome の投入処理の p95 は、36 条件で約 0.7〜1.1 ms だった。
補間を準備しない修正前は約 0.2〜0.3 ms であり、追加の処理負荷は残る。
単体ベンチマークと実ブラウザーの投入処理は測定範囲が異なるため、同じ値として比較しない。

## 回帰試験

実ブラウザーで次の音声の投入を遅らせ、次の到着時にはすでに再生済みになる空白を作った。
44.1 / 48 kHz の両方で、修正前は長い無音を残す試験が失敗し、修正後は成功した。
音量を重ねて増やさないことと、drain 後に続き音を残さないことも実出力で確認する。

非周期音、有声音、80 Hz の低い声、同一 / 逆相チャンネル、無音を使って続き音を検証する。
過去の強い音を持ち戻す問題は、最新の音量を保つ回帰試験で検出して修正した。
任意の有限 PCM に対して、補間が有限で入力を変更せず、ピークを超えない性質も PBT で確かめる。

メインスレッドを実際に 60 ms 停止する試験でも、同じ連続性と停止後の無音を確認する。
補間の対応範囲外である 192 kHz の実 AudioData は、補間を省いて正常に再生できることも確認する。

最終コードで単体テストと PBT の 4,318 件、実 Chrome の再生の E2E 73 件、
production ビルドの E2E 10 件が成功した。
フォーマット、lint、型検査、SDK と DevTools のビルドも成功した。

## 評価の範囲

本測定は Chrome 内の機器出力前の PCM を対象とする。
無音を合成音で埋めた結果だけで、日本語の聴感が WebRTC と同等になったとは判断しない。
PLC 中の聞こえ方と実音への復帰、Bluetooth の実出力は引き続き確認が必要である。
36 条件の比較は順序を保った遅着を対象とし、実回線の損失や順序逆転を再現したものではない。
100 ms を超える途絶での連続性と、NetEq 全体と同程度の聴感品質も未確認である。
